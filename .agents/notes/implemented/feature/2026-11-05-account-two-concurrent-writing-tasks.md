# Agent Note: 每个账号最多同时运行 2 个 AI 写作任务，超限提示忙碌

Status: superseded by [账号并发限制优先保障写作可用性](2026-11-05-account-concurrency-availability-first.md)

## Problem

会话生成槽只保证同一聊天会话一次一个运行。同一账号可以在多个会话、项目、标签页和设备上同时开任意多个运行，模型调用和成本随之叠加；预扣额度只限制每日条数，不限制同时运行的数量。

## Decision

- 所有账号的 `/agent/stream` 写作任务合计最多 2 个（`agent/core/account_run_limit.py` 的 `ACCOUNT_MAX_CONCURRENT_RUNS`），不分套餐，跨项目、会话、设备和进程共享。上限按完整用户任务计：路由、内部模型调用、审稿、工具和 `/steer` 不另占名额。`/suggest`、`/editor/natural-polish` 和素材任务不是写作任务，不计入。既有会话忙碌保护不变。
- 请求顺序：鉴权 → 项目权限 → 限流 → 会话忙预检 → 额度预检 → **原子获取名额** → 预扣额度 → `process_stream`。超限返回 409 `ERR_ACCOUNT_RUNS_BUSY`，此时没有预扣额度，也没有任何模型调用；不排队、不自动重试。
- 存储沿用会话生成槽的模式：Redis ZSET `agent:account_runs:{user_id}`，成员是任务 id，score 是最近心跳；Lua 脚本先回收失效成员再判断容量。每 20 秒续租，90 秒没有心跳即失效，所以进程被杀后名额最多占 90 秒。
- 续租不用 `ZADD XX`：Redis 丢数据时，还在运行的任务要回到计数里。续租与释放用同一把锁互斥，在途的续租不会把已释放的成员写回去。只靠续租写回不足以保证上限（下一次心跳前新请求可能先占满），所以另有两层：
  - **数据全丢的拒绝窗口**：获取脚本发现 `agent:account_runs:epoch` 不见了（重启无持久化、FLUSHALL），就开 30 秒窗口（`SLOT_RECOVERY_WINDOW_S`，长于 20 秒心跳加 Redis 超时），窗口内所有账号的新任务返回 503。窗口结束时所有存活进程的老任务至少续租过一次，再按实际数量判断。
  - **本进程老任务随获取写回**：每次获取把本进程还在运行的任务（`_live_slots`）在同一个脚本里先写回再判断，不等心跳。Redis 单键丢失、断开超过 90 秒后恢复（数据还在）都不会多放行。
- 获取被取消：线程可能已经占位而没有 slot 对象，取消后等线程结束，占位成功就撤销，不留到 90 秒失效。
- 释放归属：`process_stream` 走到自己的 `try` 时接管（`adopt`），之后由它的收尾释放，顺序在会话生成槽释放之后；取消路径（作者停止、断线、时限）在后台残稿补存和会话释放完成之后才释放，生成器退出不算结束。接管之前的失败（额度预扣失败、会话解析失败、会话忙）由路由释放。响应从未开始迭代时，生成器被回收同样走取消路径。释放幂等。
- 泄漏兜底：续租只持续到墙钟时限加 300 秒。墙钟时限由 `SSEStreamPump` 强制，之后只剩有上限的收尾，超过这个时长还在续租只可能是泄漏，停止续租并记 ERROR，名额 90 秒后失效。
- Redis 故障行为：`REDIS_URL` 已配置但获取失败，或 `ENVIRONMENT` 为 staging / production 却没配 `REDIS_URL`，都返回 503 `ERR_ACCOUNT_RUN_LIMIT_UNAVAILABLE`，不放行新任务，也不扣额。已在运行的任务不中断，续租失败只记日志，恢复后写回计数。只有未配 `REDIS_URL` 的本地开发和测试使用进程内计数。
- 前端：两个错误码都通过 `ERR_*` i18n 文案显示在现有错误面板，标题改用 `chat:panel.accountRunsBusyTitle`，不写「生成中断」。消息气泡移除，文字退回输入框（已输入的新内容保留在后面），随这条消息发出的技能选择恢复（文字和技能 id 都对得上才恢复），附件和引用不随这一轮结束而清除。退回输入框后不显示「重试」，避免再发一份没有气泡的副本；重试已存消息和停止后的「重新发送」保留气泡和手动重试按钮，后者的旧附件只存在于这次请求里，不能只退回文字。`agentApi` 不自动重发。

## Alternatives considered

- **Redis 故障时退回进程内计数**（`steering` 和限流都这样做）。最强理由：Redis 故障时写作仍然可用，生产目前只有一个 API 进程。否决：发布交接和未来扩容时存在多个进程，退回后每个进程各放行 2 个，正是要防止的静默绕过；这个上限保护成本，Redis 短暂不可用时拒绝新任务的代价低于超发。
- **用数据库行或 PostgreSQL advisory lock 记名额**。最强理由：不依赖 Redis 可用性，事务语义强。否决：长任务要占连接或频繁写库，崩溃恢复仍要心跳；Redis 心跳模式已在会话生成槽上验证过。
- **在 `process_stream` 里和会话槽一起获取**。最强理由：生命周期集中，路由改动最小。否决：额度预扣在 `process_stream` 之前，名额必须先于扣额获取；挪动预扣顺序会改变既有退款约定。
- **把名额合并进 `steering` 模块**。最强理由：常量和心跳模式相同。否决：两者的键、语义和 Redis 故障策略都不同，混在一起会让 steering 的内存回退也变成上限的回退路径。
- **排队等名额**。否决：已确认范围是立即提示；SSE 占着连接排队还会增加超时和取消分支。

## Consequences

- 收益：单账号同时运行的任务数有了硬上限，第三个请求不产生模型调用和扣额，作者的文字和技能选择不丢。
- 代价：Redis 故障期间所有账号都不能开始新写作任务；Redis 数据丢失后（含首次上线的第一个请求）约 30 秒内所有新任务 503。上线前必须确认 staging / production 已配置 `REDIS_URL`，否则写作全部 503。
- **不是任意故障下的严格上限**，已知例外：
  - 别的进程的心跳中断超过 90 秒而数据还在（多实例局部断联或发布交接重叠时才可能）：这边分不清它是崩溃还是断联，会回收后放行；它恢复后写回，账号短暂超过 2。此后满额前不放行新任务，超出不扩大，最多持续到这些任务结束（不超过墙钟时限），续租时记 WARNING（`active_runs` / `over_limit`）。任务还在运行时不中止，这是有意的取舍。
  - Redis 只丢了部分数据（旧快照恢复、键被淘汰）而 epoch 还在：别的进程的老任务要到下一次心跳才回来，最多 20 秒的窗口内同样可能多放行。本进程的老任务不受影响。
  - 事件循环阻塞超过 90 秒时本进程不受影响（获取时写回），别的进程看到的情形同第一条。
- Redis 卡住超过 socket 超时时，已写入 socket 的获取脚本可能在 503 之后才执行，留下没有主人的成员，最多让账号被误判已满 90 秒。方向是少放行，不是绕过；不加墓碑键或依赖时钟比较来消除它。
- 成本：每个运行 1 次获取、每 20 秒 1 次续租、1 次释放，都作用在一个账号最多几个成员的集合上，开销不随站点规模增长。
- 每个运行每 20 秒多一次 Redis 写。各实例时钟偏差会等额影响 90 秒失效判断（与会话槽相同），秒级偏差无实际影响。
- 同一会话的并发请求在没带 `session_id` 时，要到 `process_stream` 里才发现会话忙，期间短暂占一个名额；这个窗口内另一个任务可能被误判为已满，作者再试一次即可。
- 进程被杀后最多 90 秒内，名额仍算占用，作者可能看到忙碌提示。
- 事件循环阻塞超过 90 秒时，活着的运行可能被回收，让账号短暂超过 2 个；恢复续租后回到计数里，满额前不放行新任务。

## Verification
