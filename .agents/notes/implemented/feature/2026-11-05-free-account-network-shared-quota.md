# Agent Note: 免费账号按客户端网络共享每日 AI 额度

Status: implemented

## Problem

免费账号每天 3 条 AI 消息只按账号计算，同一网络上多开账号可以线性放大模型成本。产品规则已确认：账号自身 3 条不变；同一可信客户端 IP 上的免费账号每个北京时间自然日合计最多 9 条，且最多 3 个不同账号使用 AI。有效 Pro 不受影响，只限制新的 AI 生成，不限制登录、阅读和导出。

## Decision

- **入口**：`/agent/stream` 和 `/editor/natural-polish` 是仅有的两个预扣 AI 消息的入口，都把 `get_client_ip(request)` 和本次预约 id（运行 id / 新 uuid）传给 `reserve_ai_conversation`。`/suggest` 不占 AI 消息（见 [2026-10-05 决策](2026-10-05-suggest-separate-daily-cap.md)），不在规则内。守卫测试扫描生产代码，新入口不带这两个参数会失败。
- **存储与原子性**：新表 `free_ai_network_reservation` 一笔预扣一行，和账号计数在**同一个 PostgreSQL 事务**里写入：账号 `UPDATE ... used < limit`（行锁）→ 按「网络 + 北京日期」取 `pg_advisory_xact_lock` → 统计未释放的行 → 插入 → 提交。计数由行统计得出，没有第二份计数器可漂移。网络拒绝时回滚账号扣减，抛 `FreeNetworkQuotaExceeded`。SQLite（测试和本地）依靠账号 `UPDATE` 已持有的全局写锁。锁顺序固定为账号行→网络锁；退还不取网络锁，所以不存在环。
- **判定**：先判账号自身额度（用完走原有 `None` 和标准 402，不提网络），再判 9 条，再判「新账号且已满 3 个」。已入选账号在 9 条内继续可用。日期取自账号预扣返回的 `period_start`，和账号额度记在同一天。
- **`user_id` 不设外键**：外键检查要对 user 行取 `FOR KEY SHARE`。已有流程（发送验证码）会持 `FOR UPDATE` 跨 await，`/natural-polish` 又在事件循环上同步预扣，外键等待会卡住整个进程，并在持网络锁时阻塞同网络的其他账号。预约行本来就短命，孤儿行最多留到清理。
- **退还**：`release_ai_conversation` 接收 `reservation_id`，用带 `user_id` 和 `released_at IS NULL` 条件的 `UPDATE` 标记释放，和账号减扣同一事务。重复结算或别的账号拿这个 id 都不改任何计数。账号在这个网络当天的最后一条被退还后，名额随之让出，因为它实际没有用到 AI。午夜后才到的退还释放旧日预约、不动新一天的账号计数，并返回 False（与既有语义一致）。
- **中断与重启**：与账号额度完全一致，没有独立的恢复任务。优雅退出沿用既有后台退还任务的等待；进程被杀时账号扣减和网络占用都保留到当天结束，一起在北京午夜失效。两者同一事务写入，不会只有一边生效。
- **Redis 故障**：这条规则不依赖 Redis，Redis 故障不改变判定，也没有降级路径。数据库故障时预扣抛错，请求失败且不调用模型，与账号预扣相同。退还失败沿用既有 WARNING，额度到午夜恢复。
- **可信 IP**：只用 `get_client_ip`（CF 来源校验、`TRUSTED_PROXY_HOPS`，见 [信任边界决策](../architecture/2026-10-05-client-ip-trust-boundary.md)和 [Railway 实测](../architecture/2026-11-06-railway-client-ip-two-hops.md)），请求自带的 `X-Forwarded-For` 前缀不影响结果。入库的是以 `JWT_SECRET_KEY` 为密钥的 HMAC，日志只记前 12 位，不存原始 IP。IPv4 映射地址按 IPv4 算；IPv6 按 /64 算，因为一个用户通常持有整个 /64，可以在其中随意换地址。6to4 和 Teredo 地址由客户端自选，按内嵌的公网 IPv4 算；内嵌的不是公网地址时按地址本身算，不走跳过路径。
- **缺失或不可用的 IP**：`unknown`、非法值、内网/回环等非公网地址不构成客户端网络，跳过网络规则，只保留账号 3 条和成本兜底，记 WARNING `free_ai_network_limit_skipped`。行仍然写入（`ip_key` 为 NULL），退还同样幂等。
- **Pro**：沿用 `get_user_plan`；非 `free` 套餐不写表、不计数。到期的 Pro 回到免费后受规则约束。
- **保留期**：只有当天预约需要退还，其余为余量；每个进程每天最多清理一次 7 天前的行，失败只记 WARNING，不影响本次扣减。
- **错误与前端**：HTTP 402 `ERR_QUOTA_FREE_NETWORK_DAILY_EXCEEDED`，文案「当前网络今日免费体验额度已用完，请明天再试或升级。」，不出现数字、IP、成本或任何指控。聊天面板显示同一说明和升级入口，收尾逻辑与账号任务名额拒绝相同：新发送的文字和技能退回输入框、附件引用保留、没有重试按钮；重试和停止后重新发送没有可退回的气泡（旧附件只在那次请求里），保留气泡和手动重试。空会话也显示面板，午夜或账号变为不限量时自动清除。发送不被前端锁住：作者可能换了网络，由服务端判定。账号额度卡不显示，也不记 `ai_send_blocked_quota` 事件，因为账号自己的 3 条没有用完。润色入口通过既有 toast 显示。
- 日志：拒绝记 INFO `free_ai_network_limit_reached`（`reason`、`network` 前缀、`day`、`user_id`）。

## Alternatives considered

- **Redis Lua 计数器**。最强理由：账号并发名额已是这个模式，不加表，操作快。否决：和账号扣减跨两个存储，崩溃或网络失败会留下单边状态，必须再做对账和 TTL，还要决定 Redis 故障时放行还是拒绝；账号额度本来就在 PostgreSQL，同一事务一次解决。
- **带计数列的网络桶表和成员表**。最强理由：判定时不用统计，可以用 `WHERE used < 9` 直接做原子更新。否决：要多维护两张表和两份会漂移的计数，名额退还还要判断成员计数归零；预约行本来就要有（幂等退还），每网络每天最多约 9 条未释放的行，统计开销可忽略。
- **`reserve` 返回新的预约对象**。最强理由：调用方拿到的类型表达了预约概念。否决：既有调用和大量测试都依赖返回 `period_start`；调用方提供幂等键是常见模式，运行 id 也已存在，改动面小得多。
- **缺失 IP 时拒绝，或全部并入一个共享桶**。最强理由：不会漏限。否决：代理配置一旦出错，所有免费用户会立刻被一起拒绝或共用 9 条；请求方无法主动制造缺失 IP（隧道地址已单独处理），账号上限和成本兜底仍然有效。
- **IPv6 按完整地址算**。最强理由：严格对应「同一 IP」的字面含义。否决：同一用户在 /64 内更换地址即可绕过，规则形同虚设。
- **前端像账号用完一样锁住发送到午夜**。最强理由：和账号额度体验一致，少一次请求。否决：换网络后规则可能不再适用，锁住会误伤；被拒的请求没有成本。

## Consequences

- 收益：单一网络上免费账号每天的 AI 消息有硬上限，账号和网络计数不会出现单边状态，退还幂等；Redis 故障不影响这条规则。
- 代价：学校、公司、CGNAT 等共享出口的用户可能在账号未用完时被拒，这是已确认的产品取舍。换网络可以绕过，规则不是身份校验。每条免费消息多一次锁、一次统计和一次插入；退还多一次更新。
- **上线前置条件**：
  - 先在目标环境执行迁移 `20261105_120000` 再发布服务端，否则免费用户预扣报错、AI 不可用。
  - 托管环境必须设置 `TRUSTED_PROXY_HOPS=2`，并让生产回退改写排除计费入口，见 [Railway 实测记录](../architecture/2026-11-06-railway-client-ip-two-hops.md)。默认值 1 在 Railway 上取到的是边缘地址，会让全站免费账号共用额度。
  - 上线后用已知出口地址比对 `client_host`，确认解析到真实客户端。
  - `JWT_SECRET_KEY` 轮换会让当天已有的网络计数失效，只影响当天，方向是多放行。
- 账号行锁和网络锁都只在预扣事务内持有，不跨模型调用。
- 已知缺口：收尾说明里的「回复继续」只看账号额度，网络已满时作者回复后会收到这条提示，不扣额。`/suggest`、素材入口等不占 AI 消息的成本不在此规则内。
