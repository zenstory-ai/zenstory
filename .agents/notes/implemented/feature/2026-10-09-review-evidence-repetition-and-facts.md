# Agent Note: 送审时附程序检测证据：逐字复读与数字事实对照

Status: implemented

## Problem

- 新用户审计里，连载第三章和前两章有整句逐字重复，同一章里相邻段落也有复读；审稿人（quality_reviewer）给了通过。模型审稿靠通读，十几个字的逐字重复很难被发现，跨章重复则要求它先读前两章并逐句比对。
- 同一份审计里还有数字事实前后矛盾：第三章写「孩子五岁」，角色卡和前一章写「四岁」。审稿人没有对照材料，也就没有提出。
- 这两类问题都能用确定性的字符串计算找出来，不需要再调用模型。

## Decision

- **新增 `agent/graph/review_evidence.py`**，纯函数，不碰数据库，不调用模型。
  - `find_repetition_evidence(target_title, target_text, neighbors)`：
    - 规范化：去掉空白和标点（Unicode 类别 P*、Z*、Sk/Sm/So、Cc/Cf），记下每个字在原文的位置和所在段落（非空行计段，从 1 开始）。
    - 跨章：以 15 字为窗口滑动，target 与每个前章逐字相同的窗口前后相连或重叠时合并成一段。同一 target 区间只报一次。
    - 同一文件：规范化后完全相同、长度 ≥ 10 字的两段（不要求相邻，每段只和它第一次出现的位置配对）；相邻两段之间逐字重复 ≥ 15 字（完全相同的相邻段已在前一项报过，不重复报）。
    - 每条格式：`《第三章》第 N 段与《第二章》第 M 段逐字重复：「前 30 字…」（共 L 字）`。摘录取原文（去掉空白），超过 30 字截断加「…」；L 是规范化后的字数。
    - 合计最多 8 条，按 L 从长到短排序。
  - `find_numeric_fact_pairs(target, references)`：
    - 正则抽取「主语 2–4 个汉字（不含数字字）+ 可选虚词（今年、已经、才、刚满、当时……）+ 数字（阿拉伯或中文数字）+ 岁 / 年前 / 年后 / 个月」。主语取「的」之后的部分再取最后两个字作为键（「他说孩子」「孩子」都归到「孩子」，「林念念」归到「念念」）。「三四岁」这类连写约数、「十几岁」「二十多岁」不抽取。
    - 主语落在「今年」「现在」「年龄」这类说不清是谁的词上时，正文里丢弃；角色卡里归到这张卡的角色名。角色卡另外识别「年龄：四岁」「年龄 4」。
    - 同一主语键、同一单位、数值不同就输出一条：`《第三章》「念念今年五岁」↔《角色：念念》「四岁」`；同一文件不同段落之间的写作 `《第三章》「孩子五岁」↔《第三章》第 2 段「孩子四岁」`。
    - 最多 6 条。
- **交接点**（`agent/graph/writing_graph.py`）：writer 交给 quality_reviewer 时（自动质检门、计划交接、writer 显式送审都走同一个拼装 `[待审查内容]` 的分支），在拼好的 handoff context 末尾追加
  ```
  [自动检测：需核对]
  - …
  ```
  - 标题 `REVIEW_AUTO_CHECK_HEADER = "[自动检测：需核对]"` 是和审稿提示词（WP2）约定的固定写法。
  - 检测对象：`review_guard.written_file_ids()` 中 file_type 为 draft 或 script 的文件，按写入顺序最多 2 个。参照：同一父目录、同类型、按文件清单同一排序键（`build_sequence_sort_key(order, title)` → created_at → id）排在它前面的 2 个文件；项目里最多 10 张角色卡（`角色：{title}`），按 order、created_at。
  - `_collect_review_auto_checks` 用 `ToolContext.short_lived_session()` 读正文并计算，整体放进 `asyncio.to_thread`，`asyncio.wait_for` 预算 0.5 秒（`REVIEW_AUTO_CHECK_TIMEOUT_SECONDS`）。超时或任何异常只记 WARNING，返回 None，照常送审。
  - 检测跑成功时交接包 evidence 追加一行 `auto_checks=repeat:N,facts:M`（N、M 可为 0）。它匹配内部标记规则 `^[a-z_]+=\S*$`，不渲染给审稿人，只留在 HANDOFF 事件和日志里。
  - 没有结果时不追加标题段。
  - `workflow_plan == "review_only"`（用户要求审查）时不做；用户手动审查从 quality_reviewer 起步，不经过这个分支。已是最后一轮协作（审稿人不会运行）时也不做。
  - `[待审查内容]` 本身也优先取库里的正文：`_collect_review_payload_text` 按写入顺序读 `review_guard.written_file_ids()` 中 draft / script 文件当前的内容，同样走短 session + 工作线程 + 0.5 秒预算（`_review_payload_text`），所有 writer → 审稿人交接都读，不受 review_only 和最后一轮的限制。流式落库和 edit_file 已把半角引号规范成稿件风格，模型原始输出里的半角引号不能再送审，否则审稿人会按「半角引号是客观缺陷」打回，多一轮付费返工。没写文件、读不到、超时或异常时退回原来的做法：模型输出里的 `<file>` 块，没有就用全文。
- 证据只交给审稿人核对，不自动判定、不自动返工。是否算问题、怎么改由审稿人按提示词决定。

## Alternatives considered

- **只在提示词里要求审稿人逐字比对前两章、核对角色卡。** 最强理由：不加代码，审稿人能结合语境判断。没采用：审计里的复读正是在这样的提示下漏掉的；让模型逐字比对既贵又不可靠，读前两章全文还会多花一轮工具调用和大量输入 token。程序先找出候选，模型只需判断。
- **检测命中直接判定不通过、自动交回 writer 返工。** 最强理由：复读是客观缺陷，不该靠审稿人自觉。没采用：数字差异可能是合理的时间跳跃或回忆，跨章重复也可能是有意的呼应、口头禅、系统提示音；硬判会制造误返工，而返工轮数有 `MAX_REVIEW_ROUNDS` 上限。把阻断规则放在审稿提示词里（WP2），程序只提供证据。
- **用编辑距离 / 相似度（如 difflib）找近似重复。** 最强理由：能发现改了一两个字的洗稿式复读。没采用：近似匹配误报多、阈值难定，长章节两两比较的耗时也难放进 0.5 秒预算；逐字 15 字窗口确定、可解释，摘录可以直接给作者看。
- **用模型抽取事实再对照。** 最强理由：能处理「孩子」和「念念」是同一个人这类指代。没采用：每次送审多一次付费调用和延迟，结果不确定；正则只覆盖年龄和时间这一类最常见、最好核对的数字，漏报可以接受。
- **在审稿人自己的工具里做（例如新增一个 check_repetition 工具）。** 最强理由：审稿人需要时才算，不需要时不花时间。没采用：审稿人往往不会主动调用；交接点已经知道本轮写了哪些文件，算一次直接附上更省一轮工具调用。

## Consequences

- 收益：审稿人拿到带段落号的逐字复读和数字矛盾清单，能直接定位并要求修改；检测确定、无模型成本；读取失败或超时不影响送审。
- 代价：每次 writer → 审稿人交接多一次读库（最多 2 个目标文件 + 各 2 个前章 + 10 张角色卡）和字符串计算，最坏 0.5 秒延迟；超时后工作线程仍会跑完再归还连接。
- 代价：主语只按最后两个字匹配，「孩子」和角色卡「念念」这类指代对不上（漏报）；不同角色名后两字相同（「王小明」「李小明」）会误配。时间跳跃、回忆导致的合理数字变化也会被列出，要靠审稿人判断。
- 代价：规范化后的文本跨段连续，跨段落边界的 15 字窗口也可能命中；段落号按非空行数，和编辑器的段落显示可能差一（标题行也算一段）。
- 代价：只检测 draft / script，大纲、设定卡里的复读不检测。
