# 首部作品开启前打磨：按类型命名、「开始创作」进入首作、AI 引导排第一

Status: implemented

关联并部分反转：
- `feature/2026-10-14-first-work-static-guidance.md`：「默认项目永不消费其他入口的遗留想法自动发送键」和「与 AI 创作 / 自己写」两个并列次按钮。
- `feature/2026-10-14-first-work-server-initialization.md`：首作固定命名「我的首部作品 / My First Work」。
- `proposed/feature/2026-10-19-onboarding-to-first-message.md` 第二批差异里的「首页想法写进首部作品：不做」。

其余决定不变：资格只在真正新建账号时按稳定 user id 采样写入；初始化 0 模型调用、不动额度；首次主动 AI 之前不请求建议；删除后不重建；`FIRST_WORK_ONBOARDING_ROLLOUT_PERCENT` 仍是唯一开关，代码默认 0。

## Problem

仓库所有者要求把首部作品打磨后再开启。按代码把「开启后新用户从注册到第一条消息」走了一遍：注册写入资格 → 验证邮箱 → 画像页完成或跳过 → 工作台首页自动建作品 → 打开作品 → 发出第一条消息。这条路径有几处会让开启后的体验比现在差：

- **两部作品**：首页同时有首作卡片（次按钮「开始写作」）和想法框（主按钮「开始创作」）。新作者多半会照常在想法框里写一句点子再点「开始创作」，结果新建了第二部作品，自动建的首作空着留在作品列表里。不写点子直接点「开始创作」也一样。
- **名称不说明类型**：首作固定叫「我的首部作品」，而首页新建的作品按类型叫「我的小说 / 我的短篇 / 我的短剧」。首作在列表里看不出类型，之后再新建同类作品也不会顺延编号。
- **引导方向和后来的决定相反**：首作的编辑器引导和首页卡片文案都以「写下第一段 / 粘贴已有稿件」为主，「与 AI 创作」是并列的次按钮。之后 `feature/2026-10-19-chat-starter-cards.md` 把普通空作品的编辑器空态改成以「让 AI 帮你写开头」为唯一主按钮，`feature/2026-10-31-first-turn-complete-unit.md` 又把首轮默认交付改成一个完整单元。首作成了唯一一个先引导手写的入口。

逐项核对后没有问题、保持不变的：
- 起手卡在首作里照常显示（首作打开时聊天历史为空），不请求建议；编辑器的 AI 按钮在桌面聚焦输入框并让示例卡亮起，在手机上只切到 AI 面板、不弹键盘。「只聚焦、不预填」保留：起手卡已经提供一键发送的完整示例，再预填会和它重复。
- 额度用完时起手卡让位给额度卡，首作初始化不受额度影响；首轮完整单元、首轮不送审、继续卡都按作品类型和服务端「从没有过 AI 回复」的判断生效，首作和普通新作品走同一条路径。
- 作者在初始化前自己新建作品会消费资格（`skipped_existing`）；删除首作后入口消失、不重建；老账号没有资格行，开关怎么调都不受影响。
- `workspace_onboarding` 表和迁移 `20261014_100000_add_workspace_onboarding` 已在仓库中（接 `20261014_090000`）。部署前确认目标库已执行该迁移，本次不新增表或列。

## Decision

**服务端：首作按类型命名**
- `initialize_first_work` 用 `get_default_project_name(project_type, lang)` 命名，和首页新建同类型作品的默认名一致（「我的小说 / 我的短篇 / 我的短剧」，英文「My Novel / My Short Story / My Drama」）。正文文件、目录模板和 `creation_source=first_work` 标记不变。
- 首作状态（GET/POST `/api/v1/workspace/first-work`）新增可选字段 `project_type`：首作可用时为它的类型，否则为 `null`。只是响应多一个字段，不加表或列；旧前端忽略它。

**类型来源**
- 首页初始化首作时，只有本设备有类型来源（账号的类型偏好、作者刚点过的标签、已有作品的类型）才传 `preferred_type`；什么都没有时传 `null`，由服务端按画像页答案选类型（短篇作者 → 短篇，编剧 → 短剧，其余长篇）。原来总是传当前标签，而标签在无偏好时默认「长篇小说」，导致在另一台设备上完成画像页的编剧拿到的是长篇。
- `useDashboardProjectType` 在没有偏好、没有作品时，以服务端报告的首作类型作为默认标签，所以首页标签跟着首作类型走。

**首页「开始创作」在首作还没动过时进入首作**
- 新增 `untouchedFirstWork(state)`（`hooks/useFirstWork.ts`）：原文件可用、仍处于静态引导、没有手动写入、没有主动 AI 请求。首作卡片也改用它判断是否显示，条件和原来相同。
- 首页在首作没动过、并且它的类型等于当前选中的类型时，「开始创作」不再新建作品，而是打开首作的正文（`?file=`）。类型优先取首作状态里的 `project_type`，所以初始化刚完成、作品列表还没刷新（或刷新失败）时点「开始创作」也进入首作；服务端还没返回这个字段时（前端先于后端上线的间隙）退回到按作品列表判断：
  - 写了点子：照常写入 `zenstory_inspiration_<首作 id>`，打开后由 ChatPanel 以 `entry: "dashboard_idea"` 发出，和新建作品时完全一样；5 分钟有效期、额度用完时先弹额度提示、存储写不进去时保留想法并提示，都沿用原规则。
  - 没写点子：手机上和新建作品一样，用 `requestChatOnOpen` 打开到 AI 面板（起手卡）；桌面直接打开正文。
- 选了别的类型、首作已经动过、首作被删或不可用、类型未知（旧服务端且作品列表里还没有首作）时，照旧新建作品。
- 首页卡片只在「开始创作」确实会进入首作时，才说「在下面写一句点子，AI 会在这部作品里先帮你写开头」；选了别的类型时改用不提想法框的说明（「打开它，让 AI 先帮你写开头，或者自己写、粘贴已有稿件。」），避免承诺想法会写进首作。
- **反转「首作不消费首页想法」**：ChatPanel 的自动发送不再排除首作。原决定防的是「其他入口遗留的想法」误发到默认作品；而 `zenstory_inspiration_<id>` 只由首页「开始创作」按作品 id 写入，首作能收到的唯一来源就是作者刚在首页点的这一下，和普通新作品同性质。过期想法照旧删除、不发送。自动发送因此也不再等首作状态请求成功：原来的等待只为了判断「当前作品是不是首作」以便跳过，跳过取消后它只会在 GET 失败（`retry: false`）时让普通作品的首页想法一直不发。

**编辑器首作引导以 AI 为先**
- 「让 AI 帮你写开头」（`Button` primary）排第一，「自己写」降为次按钮；行为不变（桌面聚焦聊天输入并点亮示例卡，手机只切面板；「自己写」聚焦正文）。
- 文案：编辑器「说一句点子，AI 先帮你写开头；也可以自己写，或粘贴已有稿件。」；首页卡片标题「你的第一部作品已备好」，说明「在下面写一句点子，AI 会在这部作品里先帮你写开头；也可以直接打开，自己写或粘贴已有稿件。」，按钮「打开作品」。中英文同步。文案只描述发送后会发生什么，不承诺已经生成。

**开关取值的行为（已有实现，本次补核对）**
- 0 → N：只有之后新注册（密码或 OAuth 真正新建）的账号，按 `sha256("first-work-v1:" + user_id)` 的稳定分桶 `< N` 写入资格；已有账号不回填。
- N → 0：已初始化的首作保留，继续享有「首次主动 AI 前不请求建议」的保护；尚未初始化的资格显示为 `disabled`，不建作品；再调回 N 时继续初始化。
- 前端所有新行为都以「存在没动过的首作」为前提，而首作只会出现在已入资格并初始化的账号上，所以开关为 0 时新注册账号和老账号的行为与现在完全相同。

## Alternatives considered

- **首作存在时隐藏首页想法框，只留「打开作品」**
  - 最强论据：只有一个入口，不会再建第二部作品。
  - 不选的原因：想法框是首页的主要起点，带着点子来的作者在这里一步就能拿到正文；藏起来等于让首作新用户多点一步、换一个地方再写一遍点子。
- **维持「首作不接收首页想法」，只把空想法的「开始创作」导向首作**
  - 最强论据：不反转既有决定，改动更小。
  - 不选的原因：写了点子的新作者正是最可能继续写的人，他们会留下一个永远空着的首作，作品列表从第一天起就有一个没用的条目；而原决定要防的「遗留想法」在当前代码里没有来源。
- **首作完成初始化后直接从首页跳进作品**
  - 最强论据：省掉一次点击，进门就是编辑器和起手卡。
  - 不选的原因：首页会在作者还没看清时被替换，带着点子来的作者也会失去想法框；路由跳转还会和首页其他继续流程（如付费回跳）抢路由。
- **保留固定名「我的首部作品」**
  - 最强论据：名字本身就是一句欢迎，作者一眼能认出这是给自己准备的。
  - 不选的原因：作品列表里的其他作品都按类型命名，固定名看不出类型；欢迎的作用已经由首页卡片标题承担。

## Consequences

**收益**
- 开启后，新作者无论先点首作卡片还是首页「开始创作」，都进入同一部作品，不会出现一部空的自动作品加一部真实作品。
- 首作和普通新作品的首轮路径一致：首页点子一键发出、起手卡一键发出，或者进入后按编辑器的主按钮去聊天。
- 开关为 0 时没有任何可见变化。

**代价**
- 首页「开始创作」的结果多了一个分支（首作没动过且类型一致时不新建），读代码时要多看一个条件。
- 写了点子的首作用户，第一条消息落在首作里，「首作」不再只表示「作者手动开始的地方」；后台的自动初始化数量照旧不算激活，首轮激活仍以真实发送和成功回复为准。
- 首作名称改成类型默认名后，作品列表里不再能凭名字区分自动建的作品，需要看 `workspace_onboarding.project_id`。

**推荐开启方式**
- 先在测试环境对全部新账号开启，用合成账号走一遍：注册 → 验证 → 画像完成与跳过各一次 → 首页自动建作品 → 想法框写点子进入首作并发出、空想法进入首作、切到别的类型新建、删除首作后不重建；全程确认初始化不产生模型调用、不动额度，首条消息带 `dashboard_idea` / `starter_example` 入口。
- 正式环境先只对部分新账号开启。分桶在注册时按稳定 id 决定，入资格的账号和用同一函数算出、未入资格的账号自然形成对照组；观察期内不要改比例，否则两组的注册时间段会不一致。样本足以看出差异后，再决定全量开启还是关闭。

**上线后观测（按注册批次、分入资格与对照两组）**
- 主指标：注册后 24 小时内发出第一条 AI 消息并成功结束的比例。建项目率会因为自动建作品机械上升，不能当作成功依据。
- 辅助：首条后 24 小时内发第二条的比例；北京时间次日回访；首轮失败、退还和耗时分布。
- 首作专属：自动建好但从未打开的比例；打开后仍未发消息的比例；首条入口分布（首页点子、起手卡示例、手打）；同一账号首日出现两部以上作品的比例（应明显下降）。
- 护栏：初始化请求不应产生任何模型用量或额度变化；首作在首次主动 AI 前的建议请求应为 0。

**测试**
- 服务端 `tests/test_services/test_first_work_initialization.py`：中英文三种类型按默认名命名；原有资格、采样、关门、删除、额度与并发用例照常通过。
- 服务端同一文件：首作状态返回 `project_type`；首作删除后为 `null`。
- 前端：
  - `DashboardHome.test.tsx`：空想法打开首作、不新建；写了点子时把点子交给首作；手机空想法打开到 AI 面板、写了点子时不请求 AI 面板；作品列表未刷新时按状态里的类型进入首作，服务端不给类型时按列表；想法存不进去时不跳转、保留想法并提示；额度用完时先弹额度提示；卡片说明只在类型一致时承诺想法写进首作；无本地偏好时初始化不传类型、标签跟随首作类型；选了别的类型、首作已手写或已请求 AI、首作不可用、没有首作时照旧新建。
