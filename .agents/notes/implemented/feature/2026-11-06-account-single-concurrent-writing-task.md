# Agent Note: 每个账号同时只运行一个 AI 写作任务

Status: implemented

本记录收紧[账号并发限制优先保障写作可用性](2026-11-05-account-concurrency-availability-first.md)的健康状态上限；原记录中的故障放行、任务范围和生命周期决策保持不变。

## Problem

每账号两个并发写作任务仍允许单个账号把模型调用吞吐翻倍。近期约 35 小时的匿名聚合样本中，31 个实际使用写作任务的账号仅 2 个出现任务重叠，其中一个账号贡献了约 99% 的重叠时长。对绝大多数用户，第二个并发名额没有形成正常使用价值，却保留了明显的成本放大通道。

## Decision

- 所有套餐的每个账号最多同时运行一个 `/agent/stream` 写作任务，跨项目、会话、设备和进程共享。
- 已运行任务占用唯一名额时，新写作请求继续在额度预扣和模型调用前返回 409 `ERR_ACCOUNT_RUNS_BUSY`；不排队、不自动重试。
- 已运行任务不中止。任务正常完成、失败、取消或收尾后按原生命周期释放名额，随后才能开始下一项写作任务。
- 保留原有可用性优先策略：Redis 未配置、连接失败、超时或状态丢失时继续放行；20 秒心跳、90 秒失效回收、墙钟上限、幂等释放和获取结果未知时复用同一 slot id 均不变。
- 限制范围不扩张：路由、内部模型调用、审稿、工具和 `/steer` 不另占名额；`/suggest`、编辑器润色和素材任务仍不计入。
- API 错误码和前端恢复行为不变。中英文提示改为单数表述，不暴露内部成本规则。

## Alternatives considered

- **继续保留两个并发名额。** 最强理由是用户可以同时推进两个项目，减少长任务等待。拒绝：匿名聚合数据显示这种正常重叠极少，第二名额主要放大了异常高频账号的模型吞吐。
- **只限制异常账号。** 最强理由是普通用户完全不受影响。拒绝：需要新增账号特例、运营状态和绕过处理，规则难以解释和维护，也容易把成本控制变成滞后的人工处置。
- **保留两个任务，只限制任务内部模型调用。** 最强理由是可以保留多项目并行体验。拒绝：任务内部阶段和工具调用具有依赖关系，统一串行会扩大延迟并改变写作流程；账号任务入口上限是更小、更可验证的改动。

## Consequences

健康 Redis 下，同一账号的第二个并发写作请求不会扣额或触发模型调用；跨项目、标签页和设备同样适用。按近期样本，绝大多数实际写作账号不会感知变化，确有多项目并行习惯的用户需要等待或停止当前任务。

可用性优先的既有代价仍存在：Redis 故障、状态丢失、局部断联或滚动发布期间可能短暂超过一个任务；恢复后运行中的任务通过心跳重新计数，但不会为恢复上限而中止。已经在旧上限下同时运行的任务也不会被强制终止，新请求会等到计数低于新上限后再放行。
