# Feature Note: Agent 原地改名工具 rename_file

Status: implemented

## Problem

#273：Agent 工具集没有只改文件标题的入口，edit_file 只改正文。作者只要求改名时，模型会读全文、create_file 新建同名文件、把整篇正文重新流式输出一遍，再让作者手动删旧文件。用生产 DeepSeek 密钥对一份 8 章、约 3,900 字的合成合集各跑两次"把《合集》改名为《第一卷 雨夜》"：旧工具集两次都新建了副本、重新输出约 3,900 个输出 token，留下两份文件，**且副本与原文不完全一致**（3,911 字符 vs 3,910）；成本约 0.055 元/次（高峰价），并随正文长度线性增长。

## Decision

- 新增窄工具 `rename_file(id, title)`：复用 `FileCRUD.update_file` 只传 title，沿用同一把文件写锁、项目访问校验、标题校验和章节序号排序；不改正文、不建版本、不新建/删除文件，文件 id 和引用不变。
- 同一文件夹已有同名（未删除）文件时拒绝；标题未变时返回 `mutation_applied=false` 且不写库；跨项目、已删除、缺 id/空标题均报错。结果只返回 id、新旧标题、类型和父目录，不返回正文。
- 归为写工具（`FILE_WRITE_TOOL_NAMES`）：只读请求、先问清楚的轮次照旧拒绝；审稿人没有它。计费、无进展守卫、面包屑、交接产物引用都按"实际改名"计入；不触发正文写入的自动送审。
- 共享执行协议加一句：只改文件名时用 rename_file，不新建、不重写或复制正文、不删除旧文件。
- 前端：工具卡显示"已改名：《旧》→《新》"；成功后刷新文件树，打开着的正是这份文件时重读一次。编辑器已有逻辑：作者没改过的标题跟随服务端，未保存的正文以本地为准保留在新版本令牌上，不触发冲突。

## Alternatives considered

- **给 edit_file 加 title 参数。** 最强理由是不增加工具数量。未采用：edit_file 是正文差异编辑，混入元数据会让作者正文保护、陈旧检查和送审计数的语义变复杂。
- **把通用 update_file（可整篇覆盖）暴露给模型。** 未采用：等于开放整篇覆盖，绕过 edit_file 的逐处校验和作者正文保护。
- **只靠提示词让模型说"请在文件菜单改名"。** 未采用：作者明确要求时仍要多走一步，且模型实际倾向于自己搬运正文。

## Consequences

- 同一合成任务改名后：1 次 rename_file，约 148 个输出 token，约 0.018 元/次（高峰价），正文逐字不变、文件只有一份；节省量随文件长度增长。
- 改名会推进 `updated_at`；编辑器按既有逻辑在新令牌上保留作者未保存的正文。
- 新工具增加约百余 token 的工具说明（每次调用的缓存前缀，命中价）。
