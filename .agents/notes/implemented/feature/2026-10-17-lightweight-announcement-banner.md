# 轻量站内公告横幅

Status: implemented — 本地开发与验证完成；未部署，未迁移共享数据库

## Problem

用户在公告中心的第二轮设计中给出了「左侧标记＋标题／短说明＋可选按钮＋关闭」的横幅参考，明确提出可以更轻量。因此不继续打磨列表、未读和抽屉，而把首版收敛为一条可运营的站内公告条。

本稿替代[最初方案](../../proposed/feature/2026-10-17-in-app-announcements.md)和[抽屉交互修订](../../proposed/feature/2026-10-17-announcement-interaction-refinement.md)的首版范围；此前方案保留为设计记录，不能作为当前开发要求。参考图仅借用结构，不复制其品牌、赠送金额或金色活动皮肤，也不据此新增支付／活动业务。

## Decision

- **用户端只有一条横幅。** 放已登录工作台首页内容顶部；不动组织站，不进入项目写作区、不增加导航入口。保留标题、短说明、可选按钮和关闭，去掉公告中心、未读、列表、正文页、抽屉及阅读确认。
- **最多展示一条。** 常规内容沿用现有主题与强调色，弱底色、细边框，不抢创作主按钮。手机说明自然换行，按钮与关闭保留可用触控区域；不轮播、不强弹。
- **按钮只是链接。** 文案与链接同时填写才显示，不自动触发生成、升级或支付；链接需安全协议、明确目的，新标签打开已有说明／文档等页面，不额外建设公告详情。
- **关闭只负责收起。** 按当前账号＋公告版本在浏览器本地记忆，不建用户阅读／关闭状态表，不承诺跨设备同步；发布新版本后可再次展示。存储不可用时仅本次收起，不虚称永久记住。
- **后台是一块简单配置。** 当前公告的标题、说明、可选按钮文案／链接、展示开关；「保存并展示」和「停止展示」即可。不做多稿流程、语言编辑器、分群、定时、分类、优先级、历史阅读统计或更正向导。UI 本身继续中英翻译，公告内容先按运营填写原样显示，不建设独立双语内容流程。
- **最小持久化。** 一条独立公告配置，带公告版本、字段、enabled、更新时间与操作者；发布内容更改产生新版本，停用不产生新内容。普通端只读当前启用配置，后台沿用超级管理员鉴权与现有审计；不用 Prompt 配置冒充公告，不建通用通知平台。无用户 receipt 表，无逐账号群发。
- **失败不影响写作。** 获取不到就不显示横幅，不挡登录／创作、不自动刷新或调用模型。本轮不增加专门埋点或运营报表；不是把入口浏览误当阅读／转化。

实现：独立 `announcement_config` 单例表，迁移 `20261017_100000`；`GET /api/announcements/current` 供已登录用户读取，`GET/PUT /api/admin/announcements/current` 使用超级管理员鉴权。无启用配置返回 `200 null`，管理员初始空配置读取不落库。后台位于 `/admin/announcements`，首页组件为 `AnnouncementBanner`。

内容版本 `version` 仅在文案／动作变化时推进；启停不改变用户已关闭的内容版本。每次写入另用管理员所见的 `expected_updated_at` 加 `expected_version` 做乐观并发校验；陈旧启停／保存返回 409。保存与审计同事务。冲突保留前端草稿，只在管理员显式点击「加载最新配置」后替换。停用不发布表单里未保存的文案。

链接两端校验 HTTPS 或安全根相对路径，拒绝协议相对、凭据、反斜线、空白及控制字符；新标签使用 `noopener noreferrer`。字段长度为标题 80、说明 240、按钮 24、链接 2048；按钮文案与链接成对填写。

验证覆盖 API 权限／空状态／发布停用／并发冲突／URL／审计，前端关闭持久化、账号隔离、新版本、存储失败、管理员保存停用与冲突恢复；浏览器使用合成账号和 mock API 验证首页与后台接线。原型保留在 `.omx/design/announcements/v3-lightweight/`，最终实现前后图另存 `.omx/design/development-comparison/`。未部署、未修改共享数据库，不承诺跨设备关闭同步或实时推送。

## Alternatives considered

- **保留中心＋侧抽屉。** 优点是历史可查、长正文完整、账号状态可同步；但用户的最新目标是轻量横幅，目前不需要承担信息收件箱责任，因此去掉。
- **沿用双表、未读、发布不可变与更正引导。** 优点是状态完整、运营可追溯；但会让一条公告变成内容投递系统。首版只保留管理权限与现有审计，内容以配置版本更新。
- **把公告写死在前端。** 最省开发，但改一段运营文案就必须发版，不符合「增加公告能力」的持续使用目标；保留最小后台配置。
- **服务端保存每个账号的关闭状态。** 优点是跨设备一致；当前没有这一必要条件。先本地记忆并明确边界，等实际需要再扩展。

## Consequences

首版从「公告中心」收敛成「可运营横幅」，用户只做查看链接或关闭，后台只维护当前一条，开发与理解成本明显降低。代价是没有历史检索、跨设备状态、长正文承载或即时触达承诺；这些是有意不做，不是隐含的待补功能。项目写作、保存、权限、额度与发布安全约束不变。

最终本地证据：前端相关 12 文件／174 tests、后端公告与审计 48 tests、Chromium mock 流程 5 tests 通过；TypeScript／构建、ESLint（0 error，3 条未修改文件的既有 warning）、CSS token、i18n key 与 Ruff 通过。源码基线及最终改动文件 SHA-256 记录于 `.omx/verification/subscription-announcements/receipt.json`；未提交、未推送或部署，真实线上支付与共享数据库迁移不在本轮验证范围。
