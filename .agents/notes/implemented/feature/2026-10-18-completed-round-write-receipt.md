# Feature Note: 正常收尾也给出写入回执

Status: implemented

关联：[文件续写与如实完成](../bug-fix/2026-10-11-file-stream-continuation-and-truthful-completion.md)（"已保存/已修改"只靠提示约束，本文不推翻，只补可核对的事实）。

## Problem

#267：作者要求修改时，模型可能没有写成任何东西，却在自由回复里说"已更新全部内容"。服务端已经有逐帧的真实提交事实（`RoundWrittenFiles`：create_file 带正文、流式正文的保存回执、真正改了字的 edit_file），但只在停止、断线、出错和"有新建空文件未写"的收尾时展示给作者；普通正常收尾没有任何回执，作者无法区分模型说的和实际发生的。

## Decision

- 正常 `done` 帧也带写入回执，并像 incomplete 一样落库为 `stop_outcome.reason = "completed"`（不覆盖原 `stop_reason`，"继续"入口不受影响）：
  - 有确认写入：`written_files`。edit_file 只生效了一部分（`partial_success`）时该文件带 `partial: true`，前端显示"（部分修改未生效）"，不当成整组成功。
  - 路由判定作者本轮要写正文（`write_content=true` 且非只读）、却没有任何写入成功（计费口径的 `write_succeeded`，含列不出文件的并行写章、删除）时：`no_file_changes: true`，前端显示"本轮没有改动文件"。
  - 其余情况（只读、只要大纲/设定、问答、旧格式未给出 write_content）不加任何东西。
- 回执只来自工具结果和保存回执：无写工具、只读取、`no_change`、全部失败（整批回滚）、只建空文件都不会产生"已保存"。字数沿用已有口径（保存回执的真实字数；edit 不报字数），不读并发产生的新版本。
- 前端复用 `RoundEndNote` 与 `formatRoundDelivery`；completed 不显示停止图标，也不提今日次数。
- 自由回复照常流出，不冻结正文、不追加模型重跑、不做"已修改"文字检测。本批只提高可观察性，不宣称消除了虚假完成。

## Alternatives considered

- **检测回复里的"已修改/已保存"并改写或拦截。** 最强理由是直接对准症状。未采用：项目已决定不靠措辞判断授权/完成，正则跨语言脆弱，误伤正常叙述。
- **回复流完后，回执不符时让模型重写总结。** 最强理由是作者只看一份正确回复。未采用：多一次付费调用，延迟变长，且重写的总结同样不可证明。
- **只在 `no_file_changes` 时提示，不展示成功回执。** 最强理由是界面更安静。未采用：部分成功、写了哪个文件同样需要核对；回执一行灰字，干扰有限。
- **按 edit 数量报告"修了几处问题"。** 未采用：edit 数量不等于剧情问题修复数量（#180 另行跟踪），只报告提交事实。

## Consequences

- 作者在每轮正常收尾都能看到实际写入了哪些文件、哪个只部分生效，或明确的"本轮没有改动文件"，可据此核对回复。
- 依赖路由的 `write_content`：确定性延续/旧格式没有给出该字段时不会显示"没有改动"，这是有意的保守取舍。
- 旧前端忽略新字段；旧消息没有 `completed` 回执，照旧显示。
