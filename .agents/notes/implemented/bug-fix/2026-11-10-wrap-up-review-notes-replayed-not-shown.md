# Bug-fix Note: 收尾时没来得及改的审稿要求只回放给模型，作者看简短说明

Status: implemented

关联：[墙钟收尾的暂停卡与回执](2026-10-31-wall-clock-pause-card-and-receipt.md)（第 3 条决定“审稿要点写给作者、随回复落库，下一轮「继续」的 writer 在历史里看得到”）。本文修订第 3 条的展示方式；完整要求如何保存、下一轮能否接着改，仍由原决定保证，只是改用别的载体。另见 [交接原因写给作者](2026-10-09-handoff-reasons-for-authors.md)。

## Problem

审稿人要求返修、返修的 agent 因收尾不再开跑时，图层把交接包里的完整 context 和 todo 作为回复正文写给作者。这段正文同时承担两件事：给作者看，以及作为下一轮恢复返修要求的唯一载体（工具结果不跨轮回放）。后果是作者看到一份写给模型的长工单；但只把它隐藏或截短，下一轮“继续”时 writer 就拿不到完整要求。另外，可见文本经过作者口径清理（去掉 id、字段名），下一轮拿到的本来也不是原文。

## Decision

- **载体**：审稿人的 `handoff_to_agent` 调用。它的参数和真实工具结果（`status=handoff`、reason、context、todo）在审稿 run 期间就以 `tool_calls` 落库，并按先后记入 `display_events`。正常收尾、取消补存、硬超时补存都会带上它，比任何收尾文字都更早进入保存路径。因此缩短可见文字不会新增丢失窗口，也不需要新的事件、字段或持久化机制。
- **回放**：`SessionLoader._pending_rework_history_content` 只看结构化事实：
  - 这一轮的 `stop_reason` 是时限截停或停止/断线（`run_deadline_exceeded`、`cancelled`、`user_stopped`、`client_disconnected`）；
  - 按 `display_events` 的先后，交接调用发生在 quality_reviewer 运行期间、结果为 `handoff`、目标 agent 有写文件工具（与 `_agent_can_write_files` 同一口径），且之后没有 agent 再开始运行。

  满足时，在这条助手消息的模型回放末尾追加一个固定标题的块，`[上一轮未执行的审稿返修要求]`（英文为 `[Unapplied review revisions from the previous round]`），内容是交接原文的原因、说明和待改项。块里注明“这不是新的授权”，本轮的范围与权限仍以作者这条消息和本轮路由为准。标题加入 `router._SYNTHESIZED_SECTION_HEADERS`，路由看到的上一轮结尾不含这一块。
- **可见文字**：图层收尾分支（`writing_graph` 中 `wrap_up_stops_next_agent` 且当前是审稿人）只写四部分：固定说明、作者口径的交接原因、待改项条数，以及交接 context 里按「[要告诉作者]」标记截出的那段。不按长度截取 context，不新增模型调用，不改送审门槛。
- **不变**：达到审查上限（review_limit）路径不变，完整意见仍写在可见回复里，那是作者拍板的依据，那一轮以 `end_turn` 结束，不追加回放块。暂停卡、`stop_reason`、计费、前端都不改。

## Alternatives considered

- **在时限暂停卡上加 `pendingRework` 字段。** 最强理由是暂停卡本身就标明“返修没跑”，判定最直接。未采用：暂停卡在下一次循环顶部、读完今日额度（一次 `await`）之后才发出，而缩短后的说明在它之前发出；硬超时或停止落在两者之间时，补存的消息里只有简短说明、没有卡，会新增丢失窗口。把卡提前到说明之前又会改变时间线上卡片的位置。
- **保留完整工单作为可见文字。** 最强理由是零风险、作者也能核对。未采用：这正是要修的问题，内部工单不该作为写给作者的话。
- **新开一次模型调用写作者版摘要。** 最强理由是摘要更自然。未采用：多一次付费调用和延迟，而且摘要同样不能证明与原要求一致。

## Consequences

- 作者在收尾时看到一句说明、原因、条数和写给作者的话；刷新后“继续”的 writer 拿到交接原文，包括 todo 和文件定位信息，比之前经过作者口径清理的版本更完整。
- 收尾前后被硬超时或作者停止打断时，完整要求同样能恢复。审稿人已经交接、但图还没来得及处理就被截停的情况，现在也能恢复（此前会丢）。
- 本文之前落库的这类回合，可见回复里已有完整意见，下一轮会再多出一份回放块，内容重复但不冲突，这是有意的取舍，不做文本比对去重。
- 回放块内容来自不可变的历史数据，跨轮逐字稳定，不影响前缀缓存；token 与此前把完整意见写进正文时大致相当。
- 续接时是否再自动送审、是否重新附上返修对象正文，仍按原有规则，留作后续单独处理。
