# Agent Note: 混合读写请求逐项保留限制

## Problem

生产作者同一条消息只要求推演第一项、授权修改其余项，路由将整轮标为可写，并将范围压成一句短摘要。Router 原有 scope_constraints 只由服务端从短 scope 合成，模型返回的逐项限制被忽略；续接只能保留这个已丢信息的范围。实际发生未经确认落档。

## Decision

复用既有 scope_constraints 列表作为 router 可选结构化输出，验证条数/类型/长度，禁止截断或丢掉不合法限制后继续执行。首轮把短范围与逐项约束合并；续接保留旧约束并追加本轮限制；新任务和被明确接受的只读方案使用当前任务的新约束。现有持久化与下一轮路由输入已支持该字段，不新增前端 wire、数据库字段或模型调用；只扩展已有路由模型的可选输出。总预算沿用8项（短 scope 计入），提示模型最多输出7个逐项限制。运行指令明确整轮可写不代表每项都可写，不能借允许修改的任务把只讨论/待确认项落入其他文件。

## Alternatives considered

- 全部混合请求设为只读：程序保护最强，但连已获授权的修改也无法完成，并额外消耗作者消息，不采用。
- 新增逐项 ACL / 操作确认界面 / 二次语义分类：更强操作绑定，但属于独立交互和权限系统，超出本次最小修复，不采用。
- 只加提示词：改动最小，但逐项限制仍会在 parser / resolution 被丢弃，不能覆盖已发现的信息损失，故必须同时修复结构化通路。
- 按“推演/落档”等关键词判断：能命中已知样例，但不证明自然语言授权，违反语义边界，不采用。

## Consequences

改善逐项限制的信息完整性及续接保持，不把所有可写任务禁用。内容级限制的理解和遵守仍依赖现有 router/写作模型，字符串不是可程序证明的文件 ACL；不得宣称所有越权写入已由硬权限保证杜绝。本批不接生产、不变更模型/计费/存储/并发约束。
