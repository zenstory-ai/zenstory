# Bug-fix Note: 路由模型用文字回复时按"模型未接受"收尾

Status: implemented

关联：[路由技术故障保留原任务与手动重试](2026-10-18-router-invalid-decision-safe-stop.md)。本文补充其中"真实格式根因待观测"的部分，不推翻它的安全边界。

## Problem

#265 记录生产三次路由 `agent_type`、`workflow_type` 同时 `literal_error`，原值未保留。本批用生产 DeepSeek 密钥做真实调用定位：

- 短消息、长篇粘贴、注入式指令等合成输入，新旧两版路由提示各 108 次、长输入 39 次，均无失败；旧提示的管道示例也没有被原样抄回。
- 账本里这三次路由调用的输出只有 195/482/329 token（上限 2048），不是截断。
- 在内存中重放三次事故轮的路由输入（不落盘、只打印枚举值和分类）：模型多数情况下拒绝处理并用两三句中文解释，而不是输出 JSON。旧解析器的"两行兼容"把两行拒绝文字当成 agent 和 workflow，正好得到"两个字段同时非法枚举"。#266 之后这类回复被报成"这次没能处理你的要求……可以稍后重试"，但原样重试得到的是同样的拒绝。
- 另外，近三天 686 次路由调用中有 4 次输出恰好等于 2048 的上限。#266 之后，截断会直接成为路由失败。

## Decision

- 两行兼容只接受两个由小写字母和下划线组成的词（大小写不敏感），如 `writer` / `quick`；未知但像枚举的词仍是 `invalid_enum`。
- 回复里没有任何 `{`、也不是上述两词格式时，记为新分类 `declined`（`parse_path=prose`）。它对应新错误码 `ERR_AGENT_REQUEST_DECLINED`，`retryable=false`、`refundable=true`。文案说明模型没有接受这条要求、作品未改动、原样重试一般不会改变结果，可以调整要求后再发。出口仍在任何 agent/工具之前，单一 ERROR 终态，路由用量照常记账。
- 不把拒绝文字展示给作者，不改成 writer 或只读回答，也不自动重试；含 `{` 但无法解析的回复仍是 `schema`，按原来的可重试技术失败处理。
- 路由 `max_tokens` 从 2048 提到 4096，给推理留余量；只有实际生成的 token 计费。
- 前端无需代码改动：错误码走现有 i18n，`retryable=false` 时现有错误卡不显示重试。

## Alternatives considered

- **把路由模型的拒绝原文直接作为回复展示。** 最强理由是信息最具体、语言自然。未采用：路由提示不是面向作者的角色，文字可能夹带路由内部说明；非拒绝的文字回复（直接回答问题）也会被当成正式回复，且计费口径不清。固定文案更可控。
- **仍归为可重试的路由技术失败。** 最强理由是不必判断回复是不是拒绝。未采用：重放显示原样重试几乎总是同样结果，提示"稍后重试"会让作者反复白费时间。
- **按拒绝关键词识别。** 最强理由是更精确。未采用：自然语言正则脆弱、跨语言，项目已明确不靠措辞判断；"没有对象的文字回复"这一结构特征足够区分。
- **关闭路由推理以免截断。** 最强理由是更快更省。未采用：会改变路由质量，需要另做评估；提高上限只影响原本会被截断的少数调用。

## Consequences

- 内容被模型拒绝时，作者看到准确、不鼓励原样重试的说明，额度照退；不会被误导为平台故障。
- 极少数"模型直接用文字回答而不是拒绝"的情况也会显示同一文案；真实调用中未观察到（短消息 108/108 均输出 JSON）。
- 截断导致的路由失败预计减少；如仍出现，日志保留 `truncated` 分类。
