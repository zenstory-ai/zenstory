# Agent quiet delivery UI

## Problem

Agent 的实时 `done` 回执过去只凭 `written_files` 是否非空判断保存结果，也只靠未写文件卡判断一轮是否未完成。这会让“已确认保存但无法列出文件名”的写入在实时界面被误报，刷新后又从持久化 `stop_outcome` 得到不同结论；只有 `delivery_incomplete`、没有旧卡片的轮次还可能恢复旧建议或自动请求下一步建议。空文件纠正同时显示收尾说明、撤销文件名和内部迭代信息，作者看到的是重复的故障感，而不是可执行的交付事实。

## Decision

前端优先消费 `done.saved_output`，仅在旧服务端没有该字段时回退到已命名写入文件列表；`delivery_incomplete: true` 映射到既有 `deliveryOutcome.reason = incomplete`，不新增终态类型。实时与历史建议入口共同把 `error` 和 `incomplete` 视为不可自动推进，并继续用现有请求序号丢弃晚到结果。

`RoundEndNote` 继续作为结构化收尾的唯一说明。已确认未完成且没有待确认保存文件时，只按服务端事实区分“已保存本轮完成的修改”“明确没有新写入”和“不声明保存结果”；`saved_output=false` 本身不解释成没有改动或保存失败。仍存在、但保存无法确认的文件继续沿用原有可操作提示。与同一收尾重复的 `empty_file_correction` 卡和已撤销占位标题不再显示，继续动作放在收尾说明旁；其他层的未完成卡保持原有动作。

时间线仍保存原始路由、轮次、预算和清理字段供恢复与诊断，但作者界面只显示实际任务角色、文件操作和交付结果，不显示路由拓扑、步骤编号、剩余轮次或临近预算警告。

## Alternatives considered

- **继续由文件名列表推断保存。** 优点是无需协议补口；但并行写入、删除等成功操作可能无法列名，会让实时和刷新互相矛盾，因此拒绝。
- **把所有未完成卡统一隐藏。** 优点是界面最安静；但会同时删除其他层必要的继续、拆分和人工处理动作，也可能掩盖真实未保存或冲突，因此只去掉已由收尾说明覆盖的空文件纠正卡。
- **新增统一终态面板或前端状态机。** 优点是可以集中重算所有事件；但会扩大状态分叉和兼容面，现有 `RoundEndNote`、`deliveryOutcome` 与建议序号已经足够，因此不新增体系。
- **按模型正文判断是否已解释或已保存。** 优点是表面上文案更灵活；但模型措辞不是交付证据，空正文与非空正文都必须遵循同一结构化事实，因此拒绝。

## Consequences

实时与刷新会使用同一未完成和保存事实；无旧卡片的未完成回执也不会自动请求建议，旧缓存与晚到建议不会回写。已安全撤销的临时占位和内部预算不会出现在作者界面，同时原始历史没有被删除。旧服务端和旧消息仍可用既有文件清单与状态卡显示。真实的保存失败、未知保存、版本冲突和仍存在的未写文件继续保留原有可操作提示。
