# Agent Note: 审稿人把客观缺陷当阻断问题同轮返工，回复按「给作者的回复」写，首条想法加隐藏提示

Status: implemented

## Problem

2026-10-08 的三份新用户审计（短篇、连载、短剧）里，下面几类问题都和提示词有关：

- **审稿发现了 AI 自己造成的硬伤，却不修。** 扩写出的相邻重复段落、和第二章几乎逐字相同的救人桥段、整章对白没有引号、和「从此再没去过南城」矛盾的新设定，审稿人都指出来了，结论却是「无阻断问题，不启动返工交接…若你同意，我可一次性交 writer」。作者要再花一条 AI 消息才能改掉。QUALITY_REVIEWER_PROMPT 写的是「自动审查只为阻断问题返工，错别字/标点列入报告」（`2026-10-08-agent-context-full-text-and-working-set.md`、`2026-10-08-agent-routing-continuity.md`），没说清哪些算阻断，模型把这些都当成了可选意见。
- **字数口径。** 审稿人和 writer 用 `content_length`（含标点和空白）或自己估算，报「约 3586 字」「✅ 达标（≥2500）」，编辑器显示 2234。P1a 给工具结果加了和编辑器同口径的 `word_count`（`bug-fix/2026-10-09-agent-word-count-matches-editor.md`），提示词要求只报它。
- **引号体例。** 第 1–2 章半角 `"`，第 3–5 章全角“”，第二章整章没有引号。
- **回复像内部质检单。** 回复里有文件 id、`content_length`、「交 writer」「返工判定」「送审」「[任务完成]」；短剧那轮以英文过程句「Let me write the final summary in markdown chat mode.」开头；项目备注里写着「(id=9ddca7c1-…)」。
- **首条想法被套模板。** 工作台把想法套进「我想写一部短篇小说。我的想法是：…请先帮我理一理…」再发出去，还显示成作者原话；「帮我写一篇 8000 到 10000 字…」这种明确要正文的请求，AI 也只给了框架。前端改为发原话（P5），服务端需要一个只给模型看的提示。

## Decision

ROUTER_PROMPT 不动（2026-10-08 的 12/12 路由探测依赖它）。

**QUALITY_REVIEWER_PROMPT**（`agent/prompts/subagents.py`）

- 审查方法第 6 条：报字数只引用工具结果里的 `word_count`（edit_file 是 `new_word_count`），不估算，不写「约」，不用 `content_length`。
- 新增 `## 客观缺陷（按阻断问题处理）`：没达到用户原话里明确的篇幅或格式要求；小说整章对白没有引号、中文对白用了半角 `"`，或引号体例混用；和同一文件或前两章逐字重复 15 字以上；相邻段落重复；正文里留着元叙述或标注（「（本集完·钩子落）」「【本集完】」）；本轮新写的内容和同一文件、前两章或角色卡里已确认的事实矛盾（年龄、时间线、地点），改新写的内容，不动已确认的事实。审稿人看到的 `[待审查内容]` 是落库后的正文（引号已由 P1b 规范），不是模型原始输出，所以 P1b 已修好的半角引号不会触发返工（`feature/2026-10-09-review-evidence-repetition-and-facts.md` 的交接点）。
- 交接里的「[自动检测：需核对]」（P1a `review_evidence`，`feature/2026-10-09-review-evidence-repetition-and-facts.md`）是程序比对出的候选问题：逐条核对原文，属实的按客观缺陷返工，误报直接忽略，不写进给作者的回复。
- 自动审查发现客观缺陷时，在本次请求内一次性交给 writer 返工，context 逐条列位置、原文和改法，不返工的可选建议也写进 context；返工时审稿人回复正文不写任何文字，直接调用 handoff_to_agent。仍然每次请求最多一次返工交接（`MAX_REVIEW_ROUNDS` 和 `2026-10-08-agent-review-gating-and-handoff-details.md` 的「返工稿不再送审」都不变）。
- 篇幅不足时 context 写当前 `word_count`、目标和差额，要求补新的事件、选择或后果，不复述。
- 只报告、不返工：个别错别字/标点、风格偏好（写成可选建议）、需要改动作者已确认故事事实的地方（说明影响，交给作者决定）。
- 收到「[质量检查任务]」（writer 写完后的检查，作者本轮没要求审稿）且不需要返工时，不写审查报告、逐项结论或「审完了」：第一行说本轮写好了什么（文件名、`word_count`），再给最多 3 条可选建议。作者明确要求审稿时才写完整报告。

**WRITER_PROMPT**

- 新增 `## 格式与篇幅`：小说中文对白统一用全角“”，每句都带引号，不用半角 `"`，项目已用「」的跟随项目；剧本台词按「角色：台词」写，不加引号；段首缩进和已有章节一致；正文和剧本里不写「【本集完】」「（本章完）」这类标注；有篇幅目标时按编辑器口径（只数汉字，标点和空白不算）写够再收尾，写完用 `query_files(id=…)` 读一次、按 `word_count` 核对，不够就用 edit_file 续写新的情节；报字数只用 `word_count` / `new_word_count`；第一次给作品定名时用 `update_project(title=…)`。只改局部时，没改到的段落里还有半角引号或没带引号的对白不顺手改，回复里用一句话告诉作者并给「把全章引号统一成“”」的选项，不说全章已统一（P1b 的 edit_file 只规范化本次写入的文字，局部修改又不到自动送审的长度，没人会再看这些段落；集成探测里 writer 改完结尾，全章仍有 5 行半角引号，回复却写「全角引号与第一章统一」）。
- 送审前只写一句给作者看的进度（如「第三章扩写好了，我再通读核对一遍」），不写总结、选项或「送审」，然后调用 handoff_to_agent。保留这一句是因为 P1a 的送审检测和 `[待审查内容]` 只在 writer 本轮有文字时才运行（见 Consequences）。
- 返工回来直接修改、不写过程说明；最终回复把修好的问题当成自己顺手修的写，不提审稿、修改意见或报告，交接里的可选建议最多挑 3 条写成作者能直接回复的选项。

**PLANNER_PROMPT**：第一次给作品定名时（大纲里写出了书名或剧名）用 `update_project(title=…)`。作者起过名的由服务端忽略（P1b）。

**共用部分**（`agent/prompts/base.py`）

- 新增 `AUTHOR_REPLY_PROTOCOL`（`## 给作者的回复`），紧跟 `OUTPUT_PROTOCOL` 进入每个项目类型的系统提示：回复里每段文字作者都看得到（几个角色的文字连在一起显示）；过程说明整轮最多一句，交给其他角色前不写说明，不解释系统、上下文、读写记录；最后总结的第一行直接用作者使用的语言说结果，不用和作者不同的语言开头（作者写中文时不用英文开头），不写「Let me…」「Now…」这类过程句（所有作者共用这份中文提示词，英文界面的作者也读到这条，所以按「跟随作者的语言」写，不写成「不用英文」）；先用 1–3 行说清写了或改了什么（文件名、`word_count` 字数、顺手修好的问题），工具没给字数就不报；需要作者决定的选项最多 3 个，用作者口吻写；不写文件 id、工具名和字段名、角色名（writer、planner、hook_designer、quality_reviewer），不写「阻断/返工/交接/送审」和评分等级；`[TASK_COMPLETE]` 单独放最后一行。
- update_project 的注意事项：summary 和 notes 用文件标题指代文件，不写文件 id 和字段名；第一次给作品定名时同时传 `title`。
- 「思考过程」一节加「思考过程使用作者的语言」（真实模型统计见 Verification，三例汉字占比都超过 50%，保留）。

**首条想法的隐藏提示**（`agent/service.py`）

- `metadata.entry == "dashboard_idea"`（常量 `DASHBOARD_IDEA_ENTRY`）时，在本轮用户内容的「上下文」段加一行 `dashboard_kickoff_hint(project_type, force_en)`。中文：「这是作者在工作台新建「{类型名}」后发来的第一条消息：作者已经明确要求写正文/大纲/剧本时，直接按要求做；想法已经具体时，给出主要人物、背景、核心冲突和大致走向；还很模糊时，先问两三个关键问题。」英文按 `force_en` 选。类型名用术语表的「长篇小说 / 短篇小说 / 短剧剧本」（英文 Novel / Short Story / Short Drama Script），查不到类型时写「作品」。
- 作品类型用 `_lookup_project_type` 查：PostgreSQL 分支在工作线程里开短 session（`_load_project_type_sync`），SQLite 分支用请求级 session；失败只记 warning。
- 落库的 `ChatMessage.content` 和路由器收到的 `router_message` 仍是原话。它取代 `process/2026-10-08-dashboard-home-copy.md` 里首条消息套模板的做法，前端部分由 P5 的新笔记记录。

## Alternatives considered

- **审稿人只报告，由界面给一个「按审稿意见修改」按钮。** 最强理由：作者对每次改动都有知情和选择权，模型成本也更低。没采用：这些缺陷（缺引号、复读、相邻重复、标注残留、篇幅不够、和角色卡矛盾）没有「作者偏好」的空间，审计里三位作者都认为该直接修；按钮仍要多扣一条 AI 消息。自动返工只增加本请求内的模型成本，由现有成本兜底覆盖，不额外扣消息。
- **用确定性代码规范化引号、删重复段。** 最强理由：不依赖模型遵从，结果稳定。引号这部分 P1b 已对 draft/script 写入做了确定性规范化（`feature/2026-10-09-agent-writes-normalize-cjk-quotes.md`）；删重复段要判断删哪段，仍交给 writer，P1a 只做检测。
- **送审前 writer 一个字都不写。** 这是本轮第二版提示词的写法，最强理由：作者看不到「正在送审」这类流程话。真实模型探测发现它让 P1a 的送审检测被跳过（`writing_graph` 只在 writer 本轮有文字时组装 `[待审查内容]` 和 `[自动检测：需核对]`），第 5 例的 18 字复读因此没有程序证据。改为只写一句给作者看的进度。
- **把隐藏提示拼进用户消息正文（前端模板）。** 10-08 的做法。最强理由：不用改服务端。被否：提示显示成作者原话、落进历史，模型把它当作者的明确要求（「请先帮我理一理」压过了「帮我写一篇」）。
- **把首条提示放进系统提示。** 最强理由：模型更重视系统提示。没采用：系统提示每轮都变会让前缀缓存失效，这条提示只对首条消息有意义。

## Consequences

- 收益：真实模型探测里，复读、相邻重复段、时间线和轮椅去向矛盾、疤痕位置前后不一都在同一请求内修好；回复第一行就是结果，没有 id、角色名和流程词；报的字数等于编辑器字数；首条「帮我写一篇…」直接出稿（8063 字），模糊想法先问三个问题；从默认名项目出发的大纲会把项目名改成剧名。
- 代价：自动返工让一次请求多一轮 agent 运行（探测里 writer → 审稿 → writer 的请求为 9–15 次模型调用，8000 字短篇约 5–6 分钟）；返工稿不再送审，返工引入的新问题本轮发现不了。
- 代价：有篇幅目标时 writer 写完要多读一次文件核对字数。
- 代价：P1a 的送审检测依赖 writer 本轮有文字（`writing_graph` 的 `agent_content.strip()` 条件），提示词要求的那一句进度是概率性的；writer 不写字时检测被跳过，只剩审稿人自己核对（探测里审稿人仍抓到了 18 字复读）。更稳的做法是让检测不依赖 writer 文字，属于 P1a 的代码。
- 代价：「过程说明整轮最多一句」模型并不总遵守，工具调用之间仍会出现几句中文进度说明；内部词已经不再出现。审稿人有时把可以算客观缺陷的问题（如药名前后不一）写成可选建议。
- 代价：提示词遵从是概率性的，提示词文本没有镜像测试（AGENTS 规定），回归只靠真实模型探测。
