# 作者保护拒绝后终止本次请求

Status: implemented

相关：[作者正文的破坏性操作保护](2026-10-09-agent-respects-author-manual-edits.md)、[聊天改稿直接展示](../feature/2026-11-18-direct-ai-edits.md)。

## Problem

应用内对话对作者保存过的正文执行 `write_chapter` 或 `delete_file` 时，会以结构化的
`author_edit_protected`（来源无法确认时为 `author_edit_protection_unavailable`）拒绝。
但拒绝结果过去只返回给模型，SDK 仍会发起下一次模型调用；模型可以改用 `edit_file`，
把新正文塞进第一段并删除其余段落，绕过整份覆盖和删除保护。历史版本仍可恢复，
但“本次没有动作者原文”的硬边界已经失效。

## Decision

- `ToolContext` 每个请求创建一份共享的作者保护拒绝状态，只接受上述两个稳定错误类型，
  记录原始工具结果、作者可见短句和目标文件 id；下一请求创建新状态，不继承拒绝。
- 所有应用内 agent 写工具共用的 `_offload_write_tool` 按实际进入顺序串行；类型化拒绝
  在工具 payload 生成时原子记入共享状态。首个已完成的作者保护拒绝成为共享事实后，
  同批后续写工具不再执行，原样返回该拒绝；读工具仍可并行。
- `runner._stop_run_after_tools` 通过 SDK 的同步 `tool_use_behavior` 返回既有 `user_message`，
  阻止下一次模型调用。外层单循环在 run 边界读取同一请求级事实并结束整次请求，
  不再因正文自查、插话或其它续跑分支换工具重试。工具结果卡和正常终止帧照旧保留，
  计费仍只看此前真实写入和作者可见产出。
- `whole_body_replace`、`chapter_written_this_turn` 等普通可恢复错误不进入该状态；
  作者一开始直接用 `edit_file` 做合法局部修改的合同不变。

## Alternatives considered

- **只在 SSE `StreamAdapter` 看到拒绝后停止。** 最强理由是可以复用整章替换提交失败的
  现有停止路径。未采用：SDK 工具输出进入消费队列后才被 adapter 看见，下一次模型调用
  可能已经发起并真实执行工具，无法守住写入边界。
- **把一次请求里覆盖全部旧段落的多个 `edit_file` 一律判为整章替换。** 最强理由是能直接
  挡住已知三段绕过。未采用：现有合同明确允许对全部段落分别定位润色；在没有独立批准的
  精确“实际命中范围”规则前扩大 `whole_body_replace` 会误伤合法改稿。本修复只收紧已发生
  类型化作者保护拒绝之后的请求生命周期。
- **只冻结被拒文件，允许请求继续改其它文件或项目状态。** 最强理由是能保留同一请求中
  其它独立工作。未采用：模型已违反硬边界后继续运行，仍可能写其它内容并给出“已完成”总结；
  终止本请求的事实更稳定，作者下一条消息仍可正常局部编辑。

## Consequences

- 收益：一旦破坏性作者保护命中，模型不能在同一请求里换工具绕过，也不能由外层循环另开
  run；既有拒绝文案、工具卡、版本历史和计费证据保持真实。
- 代价：同一请求内经中央 offload 入口执行的写工具不再并行，批量写多个不同文件会按进入顺序执行；读工具不受影响。
  该串行只保证首个**已经完成**的类型化拒绝之后的写调用不执行，不能倒退撤销在拒绝事实建立前
  已先进入执行的调用。SDK 当前按工具列表建立兄弟任务，回归锁定“拒绝调用排在前面”的同批场景；
  不把任务调度顺序当作更强的全局事务保证。
