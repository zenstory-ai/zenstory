# Bug Fix Note: 快速模式总结不自我降级；写正文阶段、内部拒绝与断线回执的呈现

Status: implemented

关联：[快速模式保留 writer 总结](2026-10-21-fast-mode-summary-and-file-body-turn.md)（本 note 保留其第 1 条「作者要求审稿时说明这一轮没审」，只去掉其中换模式的建议并改为中性措辞）、[快速模式默认保留路由](../feature/2026-10-20-fast-mode-default-keeps-router.md)、[写作提示与快速模式自查](2026-10-31-prose-craft-and-continuity-self-check.md)、[正文待写拒绝回到纠偏](2026-10-25-pending-body-refusal-returns-to-correction.md)、[空文件纠偏恢复捕获](2026-10-24-empty-file-correction-resumes-capture.md)、[时限暂停卡与回执](2026-10-31-wall-clock-pause-card-and-receipt.md)、[额度用完的一轮](2026-10-24-used-up-day-and-undo-conflict-hints.md)、[停止输出定义与终态](../architecture/2026-10-09-stop-output-definition-and-round-outcome.md)。

## Problem

1. **快速模式的总结常以自我降级收尾。** `FAST_MODE_DIRECTIVE` 让 writer「作者要求审稿时，在总结最后说明这一轮没有审稿，可以发消息要求审稿或切换到高质量模式」。条件写在提示里，模型经常在作者没要求审稿时也照说，首轮回复于是以「快速模式、没审稿、可切高质量」结尾，读起来像交付打了折扣。同批新增的写后自查又要求「用一句话说核对了什么、改了哪处或没发现矛盾」，没发现问题时也多出一句流程说明。
2. **内部顺序拒绝显示成失败卡片。** 建文件后的下一次回复没先写正文就调用工具时，`tools_adapter` 以 `file_body_pending`（或 `pending_empty_file_unwritten`）挡回。这是引导模型先写正文的内部协议，作者的作品没有任何问题，但前端按普通工具失败画出「××失败」卡片。
3. **写正文阶段没有进度。** 空文件纠偏重跑期间，聊天区只有「AI 正在处理 · N 秒」，看不出 AI 正在往哪个文件写正文、写了多少。
4. **断线但已保存文件的一轮只剩一行灰字。** 作者离开或断网后回到会话，那一轮的气泡可能几乎是空的，只有「已中断 · 已保存《…》N 字」，没有直接打开文件的入口。
5. **额度用完时仍提示「可以继续」。** 暂停卡和中断卡已按今日额度隐藏「继续完成」按钮（10-24），但未完成一轮的灰色说明仍写「可以继续」。

## Decision

1. **快速模式提示**：`FAST_MODE_DIRECTIVE` 删去「可以发消息要求审稿或切换到高质量模式」，改为总结里不提生成模式、不推荐作者换模式；作者没要求审稿时不说这一轮没有审稿或送审。作者在这条消息里要求了审稿时保留告知，改成一句中性的话：这轮没有安排审稿，需要的话再发一句「审一下」，不评价这次交付的质量。自查保留，只在发现并改正了矛盾时用一句话说改了哪处，没发现就不提。`FAST_MODE_REVIEW_REFUSAL`（writer 在快速模式里仍交给审稿人时的工具拒绝说明）同步：交接前的自查只在改正了矛盾时提，不说已经审稿，也不提生成模式；作者要求了审稿时同样补那一句中性告知。只要求审稿的消息由路由照常安排审稿人（`review_only`）；「写完再审」在快速模式里不自动送审，这一点是 10-20 note 已记录的既有代价。作者是否要求了审稿由模型按提示判断，只改提示规则，不加检测或拦截代码。
2. **内部拒绝不画卡片**：前端 `isInternalOrderingRefusal`（`lib/agentRoundProgress.ts`）按结构化 `error_type`（`file_body_pending`、`pending_empty_file_unwritten`，顶层或 `data` 内）识别；`MessageList.visibleToolCalls` 把这类失败的工具调用和流程控制工具一样过滤掉，实时与刷新后一致。服务端协议、熔断记账不变。
3. **写正文阶段提示**：`createBodyWriteProgress` 只读这一轮已有的事件：`create_file` 成功且 `awaiting_body: true` 时记下文件和标题；`file_content` 片段按编辑器的 `countWords` 计字；收到带正文的 `file_content_end` 后清除；模型删掉正在等正文的文件（`tools_adapter` 允许用 `delete_file` 取消逾期的空文件）时也清除，`delete_file` 的结果只有 `true`，被删文件的 id 取自同一次调用的参数（`onToolCall`）。没有正文的结束（run 先停了、随后是空文件纠偏）不清除，所以纠偏重跑期间仍显示同一阶段。`StreamActivityLine` 每秒读一次快照，显示「正在写入《标题》正文…」或「正在写入《标题》正文 · 已写 N 字 · N 秒」；`ChatPanel` 不因片段重新渲染。不新增事件、不新增模型调用。
4. **断线回执可打开**：服务端已在 `client_disconnected` 的 `stop_outcome.written_files` 里落库 `{id, title, words}`（只列有确认保存回执的文件），无需改动。前端 `parseRoundStopOutcome` 保留 id（实时 `done` 帧的解析不变）；`reason=client_disconnected` 且 `saved_output` 为真时，`MessageList` 在 `RoundEndNote` 下列出最多三个「打开《标题》」按钮。回执不带文件类型，`ChatPanel.handleOpenFile` 收到空类型时用 `fileApi.get` 读出真实类型和当前标题再选中（选中项的类型会作为下一条消息的当前文件上下文，标题跟随之后的改名）；文件已不存在（404）时提示「这个文件已经不在了」而不选中，其他读取失败照常按正文打开；读取期间切换了项目或选中了别的文件则不打开，不抢回作者的新选择。
5. **额度用完时的未完成说明**：`RoundEndNote` 接收 `nextStepsBlocked`（与暂停卡同一个 `aiSendBlocked`），用不含「可以继续」的同义文案（三句单独的未完成说明 `roundIncomplete*Paused`；列出已保存文件的回执里那一项用 `roundUnfinishedItem`，见[时限暂停卡与回执](2026-10-31-wall-clock-pause-card-and-receipt.md)第 5 条）；恢复时间与升级入口仍由 `ChatQuotaCard` 给出。暂停卡（含 `limit=wall_clock`）与 `iteration_exhausted` 卡在额度用完时不显示「继续完成」的既有行为不变，实时流与刷新后回放共用同一个判定。

## Alternatives considered

- **完全去掉「没审稿」的告知，任何轮次都不提。** 最强理由：模型不会再在没要求审稿的轮次误说，首轮回复一律以交付收尾。没采用：作者明确要求「写完帮我审一下」时，快速模式既不送审又不说明，作者会以为已经审过；保留条件告知、去掉换模式建议、改成中性措辞，误说时的损害也小得多。服务端没有「作者要求审稿」的结构化字段，按关键词判断属于被禁止的意图猜测，所以条件仍交给模型。
- **快速模式里作者要求审稿时由服务端自动送审。** 最强理由：作者要求的事被做到。没采用：需要从自然语言判断「要求审稿」，且改变快速模式的成本与等待；路由对只要求审稿的消息已经安排审稿人。
- **把 `file_body_pending` 归入 `INTENTIONAL_SKIP_KINDS`，显示成「有意跳过」卡片。** 最强理由：改动最小，信息不丢。没采用：这是对模型的内部引导，作者既没要求、也无需处理，任何卡片都会让一轮正常写作看起来出过岔子。
- **服务端为纠偏重跑新增一个「正在写入正文」事件。** 最强理由：阶段提示能在模型开始写之前就出现。没采用：`create_file` 的 `awaiting_body` 已经标明在等正文，前端从既有事件就能得到同样的阶段和字数，不必改 SSE 合同。
- **服务端在 `written_files` 里补上文件类型。** 最强理由：打开文件不必再读一次。没采用：回执结构在多处按精确结构比对，补字段牵动面大；打开时读一次文件的代价只在作者点击时发生。
- **断线回执对所有中断原因（作者停止、出错）都给打开按钮。** 最强理由：同样省一步。没采用：本批只处理断线后回到会话、气泡可能为空的情形；作者主动停止时人还在页面上，编辑器已跟随写入。

## Consequences

- 收益：快速模式的首轮回复以交付内容收尾，不再出现换模式的建议；内部顺序拒绝不再以失败示人；写正文和纠偏重跑时能看到正在写哪个文件和已写字数；断线回到会话能一键打开已保存的文件；额度用完时各处都不再叫作者「继续」。
- 代价：快速模式里作者要求「写完再审」时仍不自动送审，作者需要再发一条消息要求审稿（与 10-20 note 记录的代价相同）；「作者是否要求了审稿」由模型判断，偶尔可能在没要求时也补那一句中性告知。阶段提示的字数是流式正文的实时估计，与落库后的字数可能略有出入；同一批里并行删除多个文件且只有部分成功时，阶段提示可能提前清除。打开断线回执里的文件多一次文件读取请求。
- 已知缺口：打开按钮只来自会话消息加载时读到的 `stop_outcome`。页面一直开着时网络中断（例如手机切到后台又切回、标签页没有刷新），实时流收不到断线那一轮的 `done` 帧，只显示流错误卡片，要重新打开会话或刷新页面后才出现回执和打开按钮。服务端在断线被察觉、这一轮收尾后才写 `stop_outcome`，流错误当下立刻重读往往还读不到，可靠的做法需要延迟或按页面可见性重读，留待后续单独处理。
- 回归：后端 `test_prose_craft_prompts.py`（快速模式两段说明不推荐换模式、作者要求审稿时保留中性告知）；前端 `agentRoundProgress.test.ts`（写正文进度、删除等正文的文件后清除、内部拒绝识别）、`StreamActivityLine.test.tsx`、`MessageList.test.tsx`（内部拒绝不画卡片、断线回执按钮）、`RoundEnd.test.tsx`（回执保留 id、额度用完的未完成说明）、`ChatPanel.mount.test.tsx`（等待行接线、空类型按文件真实类型与当前标题打开、已删除文件给提示、读取期间换了选中项不抢回）。
