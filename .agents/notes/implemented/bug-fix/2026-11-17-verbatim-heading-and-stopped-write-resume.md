# 原文标题范围与停止后的正文交付

## Problem

PR #379 后的 staging 真实浏览器复测发现两项残留：

- 逐字录入大纲时，模型把原文首行只用作文件名，传入 `source_text` 的连续范围少了标题及换行。服务端确实逐字保存了这个较窄范围，但助手仍总括称全部逐字存档。
- 整章替换中途停止后，作者在下一轮明确要求继续。模型先把一版未保存正文输出到聊天，随后发现文件仍是旧稿，经一次锚点失败后重新定位替换并完成。最终数据正确，但多出聊天正文及模型回合。

## Decision

- 明确逐字录入的范围包含原文标题和小标题；文件名不替代正文中的原文行。作者明确只要正文时遵从其范围，不以字符串规则替作者判断范围，也不擅自拼接标题。
- 历史中的成功 `write_chapter` / `create_file` 结果明确标记 `write_target_active=false`，与 `body_saved` 分开表达：过去是否保存不代表本轮已经建立捕获目标。未保存的整章替换结果说明本轮仍需按作者要求重新定位，不能把聊天中新写但未保存的文字当编辑锚点。输入协议说明当前作者改为只读或其他任务时不恢复旧写入，不自动继承权限或过期版本。
- 核对 C1 实际落库的 `display_events` 后确认：只含思考、工具调用和两个换行，半篇正文仅通过 `file_content` 发给编辑器，没有回放到模型。保留原有正文/聊天事件隔离，不做缺乏证据的历史文本过滤。
- 以停止、继续、改为只读/另一任务、原稿版本保护等回归验证修复；实际模型行为仍需 staging 复测，脚本模型不能证明所有生成都遵循指引。

## Alternatives considered

- 自动把邻接且等于文件名的行补到 `source_text`：可以修补已知样例，但会猜测作者的保存范围，误伤明确排除标题的请求，拒绝。
- 跨请求自动恢复之前的待写目标：可少一次工具调用，但过期状态不能代表本轮授权，也会绕开新鲜版本与作者手改检查，拒绝。
- 仅减少工具失败阈值或缩短超时：不能修复写入协议上下文，且会使可恢复请求更早失败，拒绝。

## Consequences

沿用现有文件工具和版本/计费/取消保护，不新增依赖，不更改生产或云配置。脚本模型回归证明结构化历史状态、跨请求不自动绑定、原稿/版本保护及本轮重新定位后的落库路径；模型能否遵循新范围和续写指引仍以 staging 真实复测为准，不能用脚本模型的预设工具顺序证明语义正确率。

针对原文复制、历史回放与整章替换的 77 项脚本模型测试通过；新增跨请求测试核对只读轮不写入、重新定位后的正文只进入文件流且旧版本可恢复。
