# Bug-Fix Note: 素材拆书章节标题装饰符号归一化与超长章节兜底切分

Status: implemented

## Problem

线上复盘 2026-11-23 当天入库的 4 本素材小说（novel 98/99/100/101，单本 25.8 万～29.3 万字）时发现严重拆章失效：

1. 这 4 本 TXT 导出的 59～86 个真实章节标题均带有装饰前缀 `§§§`（如 `§§§第一章 标题`），而 `apps/server/services/material/novel_text.py`（及前端同口径镜像 `apps/web/src/lib/novelChapterSplit.ts`）仅做首尾空白剥离，导致所有真实章标题全部漏识别。
2. 全书仅偶发命中 1 条杂散行，约 29 万字的正文被合并成单个超大章节；下游阶段 1 将约 17.5 万 token 的整章正文重复送入模型 3 次，使前缀缓存命中率跌至 0.22%～0.68%，并严重劣化摘要与人物提取质量。

## Decision

在 `apps/server/services/material/novel_text.py`（并由 `apps/web/src/lib/novelChapterSplit.ts` 保持前端同口径镜像）落地两层互补修复：

1. **标题行装饰前缀与外层包裹归一化**（`_normalize_heading_line` + `_heading_candidate`）：
   - 在匹配 `_VOLUME_ONLY_RE`、`_CHINESE_CHAPTER_RE`、`_ENGLISH_CHAPTER_RE`、`_NUMBERED_RE`、`_SPECIAL_RE` 之前，对已 `strip()` 的行先检查原始长度上限 `MAX_RAW_HEADING_LENGTH = 60` 与句末标点 `_SENTENCE_ENDINGS`，再迭代剥离常见中文 TXT/电子书/Markdown 装饰标记：
     - 成对外层包裹：`(**...**)`、`(__...__)`、`【...】`、`《...》`、`「...」`、`『...』`、`[...]`（仅在内部不含闭合符时剥离，避免破坏 `【第一章】【标题】`）。
     - 行首装饰前缀：`§+`、`#+`（含 Markdown `#{1,6}`）、常见装饰符号串 `[*☆★◆◇●○■□▲△▼▽▶▸※•·\-—_=~>]+`（可后接 `、`/`.`/`．` 与空白）。
     - 行尾装饰标记：连续 2 个及以上装饰符号、空白后装饰符号，或常见单字符装饰尾标（保留附着于词尾的 `喵~`、`C#`）。
     - 可选 `正文` 卷标前缀（`^正文[\s:：、.．·\-—]+`）。
   - 同时将 `_CHINESE_CHAPTER_RE` 的章号括号扩展为成对校验的 `【】`/`《》`/`「」`/`『』`/`[]`（支持 `【第五章】标题`、`《第一章》标题` 等前缀包裹，拒绝不配对或未闭合括号）。
   - 归一化后再校验 `len(normalized) <= MAX_HEADING_LENGTH (40)` 与非句末标点。严格不剥离 `U+FEFF`（保持 Python/JS 空白一致性测试）以及对话引号 `“”‘’"'`（防止 `“第一章很好看”` 误判为标题）。

2. **付费分章的超长章节兜底切分**（`MAX_CHAPTER_CHARACTERS = 20_000`、`TARGET_SUBCHAPTER_CHARACTERS = 6_000`）：
   - 仅在 `split_novel_text` 的正常分章与短章合并之后触发；若全文无任何标题，仍返回 `[]`（保持 `ERR_MATERIAL_NO_CHAPTERS` 语义）。
   - 若某章正文超过 20,000 字，按均衡段数目标（每段约 6,000 字、严格不超过 20,000 字）切分：优先按段落/换行边界（`\n`）切分；若单行本身超过 20,000 字，回退到句末标点（`。！？!?；;`），最后回退到硬字符切分。
   - 子章节命名为 `f"{base_title}（{part_idx}/{total_parts}）"`，并确保触发兜底切分后整本书的 `chapter_number` 严格单调递增，满足数据库按 `chapter_number` 排序的稳定性。
   - **免费试拆不变量不变**：`truncate_novel_text` 继续只基于 `_split_lines` 的原始章边界截断，绝不对超长单章做内部切分，确保「前 3 完整章且不超过 15,000 字，超限直接拒收而不截断」的规则零变化；且通过试拆校验的文件总长 `<= 15,000 < 20,000`，后续 `split_novel_text(kept.text)` 不会触发兜底切分，前后端与 worker 完全一致。

## Alternatives considered

- **只补 `§§§` 单个前缀而不做通用装饰归一化**：最强理由是改动面最小、误判面几乎为零。未采用：真实网文 TXT 导出器除 `§§§` 外普遍存在 `###`、`☆、`、`◆`、`**...**`、`正文 `、`《第一章》标题` 等常见格式，仅补单一字符会反复在线上踩坑；通过明确排除对话引号、`U+FEFF`、句末标点与长度上限，已能把误判控制在极低水平。
- **在 `truncate_novel_text` 中同样启用超长章兜底切分**：最强理由是让 `split_novel_text` 与 `truncate_novel_text` 永远共享完全相同的章节数。未采用：免费试拆契约明确要求「前 3 个完整章节、超限拒收不截断」，若对超长单章做内部切分，会把原本超限的 2.5 万字单章偷偷切成多个 6,000 字子章从而绕过拒收语义，破坏 `test_materials_trial.py` 与产品不变量。
- **按固定 6,000 字贪心硬切而非动态均衡打包**：最强理由是实现更短。未采用：例如 20,500 字会被切成 `6000/6000/6000/2500` 或在长段后产生极短尾段，既浪费一次 LLM 调用也破坏摘要上下文完整性；按剩余预算动态均衡并在段末合并过短尾段能在保证每段 `<= 20,000` 的前提下让各子章字数接近一致。

## Consequences

- **收益**：彻底修复带 `§§§`、`###`、`☆、`、`◆`、`**...**`、`正文 `、`《第一章》` 等装饰标记的网文无法分章的问题；即使遇到极端无标点或缺失部分标题的巨型章节，也有 20,000 字上限兜底，避免单章十几万 token 击穿 LLM 前缀缓存和质量基线。
- **代价**：新增约 200 行归一化与均衡切分逻辑，需由 `apps/web/src/lib/novelChapterSplit.ts` 同步维护标题归一化规则以保持浏览器预检一致性；正常章节长度 `<= 20,000` 时零额外开销、输出不变。
