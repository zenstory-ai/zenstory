# Agent Note: 项目标识不再打断共用提示前缀

Status: implemented

## Problem

`get_base_prompt` 在第一行写入项目 UUID，随后才是角色定义、产品身份、输出格式、作者回复和执行协议。同一写作配置的两个项目虽然共用大段协议，字符前缀却只相同到 `## 当前项目 ID: `（12 字符），项目间无法复用这些协议对应的输入前缀。

延续 [读取路径不改写历史](2026-10-08-agent-read-path-no-history-rewrite.md) 的前缀稳定原则；保留 [产品身份规则](2026-10-11-agent-identity-reply-language-rewrite-in-place.md) 在数据库角色定义之后的优先级。

## Decision

- 仅把现有项目 ID 行移到基础提示末尾。其他段落、协议、数据库配置和真实目录 ID 的顺序与文字不变；仍由已有项目归属校验和工具上下文决定访问范围。
- 回归使用两组独立的项目 UUID 和目录 UUID，验证固定协议处于共同前缀中，项目标识唯一、所有 `parent_id` 正确且不串项目；替换各自动态 ID 后，两份提示完全相同。
- 按 [DeepSeek 当前缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)，请求必须完整匹配已持久化的前缀单元才会命中。单元可在请求边界、多个请求的公共前缀或固定 token 间隔产生；公共前缀首次被发现不等于当次已经命中。不能沿用旧的固定 64-token 单元假设。

## Alternatives considered

- **保留项目 ID 在第一行。** 最强理由是项目上下文醒目、完全不改变提示顺序。未采用：项目 ID 没有必须早于协议的语义要求，放到末尾仍完整提供，同时允许共用协议成为稳定前缀。
- **重排所有目录标识、角色提示及动态上下文。** 最强理由是能形成更长的公共前缀，并减少跨轮动态内容对后续角色提示的影响。未采用：需要改变更多段落的关系与指令优先级；本次先消除第一行 UUID 这一确定断点。

## Consequences

- 离线合成案例的共同前缀从 12 字符延长到 8,000 字符，首个差异延后至工具指南里的目录 UUID。这是可复用文本范围，不是 DeepSeek tokenizer 的 token 数、真实缓存命中或生产节省金额；最终收益仍以真实 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens` 衡量。
- 缓存按服务商规则尽力而为，构建需要时间，闲置会清除；不同目录、动态上下文、模型或权限仍可能打断后续前缀。提示顺序发布变化也会使旧前缀失效一次。
- 不新增缓存层、依赖或模型调用，不改变文件写入、权限、额度及退款逻辑。

## Verification

新增回归先在旧实现失败：公共前缀只有项目 ID 标签，找不到固定协议。修复后提示组装、数据库配置来源、身份优先级、目录解析、权限、语言与技能组装共 37 项测试通过；受影响 Python 文件 Ruff 与 `git diff --check` 通过。不调用付费模型。
