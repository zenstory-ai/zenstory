# Agent Note: LLM 路由带上上一轮助手结尾和落库路由

Status: implemented

## Problem

`router_node` 只把用户本条原话发给路由模型。`2026-10-08-agent-routing-continuity.md` 的确定性沿用规则（`inherit_routing_after_clarification`）覆盖了最常见的短回答，但它有意收得很窄：回复超过 40 字、上一轮不以问号收尾、上一轮只读或不要正文、命中只读/规划意图词时都交回 LLM 路由。这些情况下路由器仍然看不到用户在回应什么：

- 「B，主角叫陈默，金手指是能看见别人的寿命，写到第一章结束」超过 40 字，被单独分类成人设/设定，`write_content=false`，随后以 [最高优先级] 下发「不要写正文」，第 1 章出不来。
- planner 规划完问「主角性格偏隐忍还是张扬？」、上一轮 `write_content=false` 时，「隐忍吧」交回路由，路由器不知道它是在回答 planner，可能分给 writer。
- writer 写完一章、正常结束（不走「继续」直达），用户说「继续」，路由器只看到「继续」两个字。

## Decision

**路由输入**（`agent/graph/router.py::build_router_user_message`）

- 取历史里最后一条 assistant 消息（与沿用规则用同一个 `_last_assistant_message`）。
- 上一轮助手结尾：`_reply_text` 剥掉工具面包屑和合成状态卡段落后，取最后 `ROUTER_PREV_TAIL_MAX_CHARS`=600 字，被截断时前面加「…」；再接上状态卡摘要，封顶 `ROUTER_PREV_CARD_MAX_CHARS`=400 字。
- 状态卡摘要来自历史 dict 的新字段 `status_card_text`（`core/session_loader.py` 在有状态卡时总是填，正文非空时摘要不进回放，只能从这里拿到）；没有这个字段时从正文里截出 `[workflow_stopped]` / `[iteration_exhausted]` 段落。
- 上一轮路由：落库 `routing` 的 `initial_agent` / `last_agent` / `workflow_type` / `write_content` / `read_only` / `scope`，按这个顺序输出成一行 JSON；状态卡上的 `lastAgent` 覆盖 `routing.last_agent`。缺失或类型不对的字段不输出。
- user 消息为 `[上一轮助手结尾]\n…\n[上一轮路由]\n…\n[用户本轮原话]\n…`，两段上下文各自为空时省略该段。没有上一条 assistant 消息、或它既没有正文/状态卡也没有落库路由时，原样发用户原话，与改动前逐字相同。
- 系统提示仍是 `ROUTER_PROMPT` 常量，动态内容只放 user 消息，路由调用的前缀缓存不受影响。模型、温度、`max_tokens` 都不变。

**ROUTER_PROMPT**

- 新增「上一轮上下文」一节：说明三段标题的含义，交付范围仍按 [用户本轮原话] 判断；简短回复在回答或确认上一轮提问（「可以」「B」「隐忍吧」、逐条作答）时沿用上一轮路由的 agent（优先 `last_agent`）、`workflow_type` 和 `scope`，`write_content` / `read_only` 也沿用，除非用户本轮另有明确说法；上一轮 writer 在写正文时「继续 / 接着写 / 下一章」→ writer + quick + `write_content=true`；与上一轮无关的新要求忽略上下文。
- `write_content` 规则改为：只有用户原话明确不要正文（「先别写 / 不要正文 / 只要大纲 / 先不用写」），或本轮只要求大纲/人设/设定/规划/爽点思路这类非正文产出时才为 false；回答问题、补充人设/设定信息不算只要设定；上一轮助手说的话不能成为 false 的理由。
- 「检查并修改 / 有问题就改」→ writer + quick 与「只审不改」→ review_only 两条规则保持原样（上一批已加）。
- [最高优先级] 范围指令机制（`writing_graph` 的 `SCOPE_DIRECTIVE_NO_CONTENT`、`nodes` 的「本轮用户范围约束」）不动。

**顺序**

`writing_graph` 里仍是「继续」直达 → 确定性沿用 → LLM 路由。前两条命中时不调用路由模型；这里只改变第三步的输入。快速模式（路由关闭）不受影响。

**真实模型探测**

分类效果要用真实模型确认。探测脚本不放仓库：它内嵌新版 `ROUTER_PROMPT` 和本节的构造/解析代码（由生成脚本从源码逐字拷出），在生产 API 容器里经 stdin 运行，最多 20 次请求，覆盖「可以」确认下一章、选 B、回答 planner 提问、补充主角信息、检查并修改、只检查不改、先别写正文列大纲、写完一章后「继续」、新开长篇九种情况。

## Alternatives considered

- **只靠确定性沿用规则，放宽 40 字上限和意图词。** 最强理由：完全可测，不多花路由 token，也不受模型波动影响。没采用：放宽后「可以，第二章换成女主视角」「B，另外把大纲也改一下」这类混合回复会被直接沿用，新要求只靠历史原话传达；意图词是子串匹配，放宽只会更容易误判。语义判断交给看得到上下文的模型更稳，规则仍保留为便宜的第一道。
- **把完整历史（或最近几轮）发给路由器。** 最强理由：信息最全，多轮之前的约束也能看到。没采用：路由每轮都跑，输入从几十字涨到上万字，首字延迟和成本明显上升；路由要判断的是「这句话在回应什么」，上一轮结尾和它的路由已经够用。
- **把上一轮上下文写进系统提示。** 最强理由：模型通常更重视系统提示里的约束。没采用：系统提示每轮都变，路由调用的前缀缓存全部失效；而且会让模型把上一轮内容误当成规则。
- **把「只要大纲」以外的规划请求也改成 `write_content=true`，严格只认否定词。** 最强理由：与评审报告字面一致，回答设定信息永远不会被判成不要正文。没采用：「帮我列个大纲」若判成 true，standard 工作流会在大纲后自动交给 writer 写章节，正是 10-03 修过的「只要大纲却写出多章」。这里改为「本轮只要求非正文产出」才为 false，并明确回答问题、补充设定不算。

## Consequences

- 收益：确定性规则没接住的回答（长回答、上一轮只读/不要正文后的作答、问号以外的提问方式、写完后的「继续」）也能按上一轮的 agent 和范围路由；第一轮的路由输入和缓存前缀与改动前完全一致。
- 代价：有上一轮时每次路由多约 1000 字输入（600 字结尾 + 400 字状态卡 + 一行路由），路由调用的 token 和延迟随之略增。
- 代价：路由器可能过度沿用：用户在上一轮之后换了话题但措辞含糊时，可能仍被判给上一轮的 agent。提示词要求新要求忽略上下文，效果以真实模型探测为准，mock 测试只验证管线。
- 代价：600 字结尾按字符截取，可能截在半句话中间；提问通常在结尾，影响有限。

## Verification

`cd apps/server && venv/bin/python -m pytest tests/test_agent/test_router_previous_turn.py -q --no-cov -n 0`（mock DeepSeek 客户端）：第一轮发给路由模型的消息与改动前逐字相同；有上一轮时 user 消息依次是结尾、路由 JSON（固定字段顺序）、用户原话，面包屑和 UI 装饰不进路由；长回复只保留最后 600 字；正文非空的澄清卡问题经 `session_loader` 的 `status_card_text` 进入路由；只有状态卡的旧数据从正文里截出卡片；上一轮既无文本也无路由时退回旧消息；构造器发出的每个段落标题在系统提示里都有解释；提示词含短回复沿用、`write_content=false` 只认明确否定、检查并修改 → writer、只审不改 → review_only。除两条「与改动前一致」的用例外，其余在改动前的代码上全部失败。另跑 `tests/test_agent` 全量与 `tests/test_api/test_agent.py`。真实模型探测脚本的结果不在仓库里，见本批交付说明。
