# 素材目录查询随拆解进度版本更新

## Problem

素材详情通过轮询获取整体状态，但目录数据另用 `loadedFolders` 记录已加载，完成时只强制刷新正在展开的目录。因此处理时打开后收起的目录，拆解完成后再次展开仍会使用旧结果。完成状态到来时若旧目录请求还在进行，刷新又会被 `isFetching` 跳过；旧响应结束后没有补查，目录可能一直为空。

这两种时序已在发布源 `40d22a0a` 用本地合成响应复现，不能据此认定近期某位真实用户实际遇到。整体状态与 [拆解失败及退款规则](2026-10-05-material-job-failure-codes-and-refunds.md)、[阶段可见性](../feature/2026-09-27-material-decompose-stage-defaults.md)保持原有语义；本次只修详情目录读取缓存。

## Decision

- 将既有进度版本（整体状态、更新时间和各目录计数）加入目录的 React Query key，与素材 ID 一起区分缓存。进度变化后，旧请求只能写入旧版本缓存，不能满足或覆盖新版本结果。
- 目录仅在实际展开或搜索需要时启用查询，阶段未启用且确认无数据的目录不查询。收起的目录保持懒加载，下次展开自动读取当前版本；搜索仍只读取可见目录。
- 用 React Query 自身的成功、错误和请求中状态显示目录状态，删除 `loadedFolders`、手工错误集合、版本刷新 effect 和请求回调状态。错误按钮直接重取对应查询；已展示搜索失败后修改关键词仍可重试。
- 用 `keepPreviousData` 在版本变化后的请求期间保留已取得的目录内容，避免后台刷新时清空结果。素材路由仍以素材 ID 重挂组件，保持不同素材的选择、展开状态及结果隔离。

## Alternatives considered

- **保留手工加载集合，版本变化时清空，并为进行中的请求增加待刷新标记。** 最强理由是改动集中，可以沿用原有命令式刷新。没有采用：这会让本地集合与 Query 缓存继续共同决定成功状态，还要补一套跨版本请求协调；将版本放入 Query 身份就能直接解决两种时序。
- **每次展开都忽略缓存并请求。** 最强理由是逻辑直接，能更新收起后的目录。没有采用：无法单独解决已展开目录跨完成状态的进行中请求，也会让同一版本的反复展开重复请求。

## Consequences

- 收益：完成状态不再被旧目录请求吞掉；收起后重新展开可读取最终结果；成功、错误与进行中状态由同一份查询状态提供，不新增请求状态机。
- 成本：进度变化会产生不同的查询缓存项，沿用 React Query 的默认回收机制。正在执行的旧版只读请求可以自然结束，但结果与新版隔离；本次没有新增拆解任务、模型调用或后台写操作。

## Verification

- 两项新回归先在修复前失败：已加载目录收起后跨完成状态、旧目录请求未返回时跨完成状态。修复后同时验证最终结果、旧响应晚到不会覆盖，以及同版本展开复用缓存、收起时不提前读取。
- 既有详情测试继续覆盖已展开空目录完成刷新、目录错误后重试、搜索失败后重试、隐藏阶段、章节详情懒加载及切换素材隔离。
- 本地验证仅使用 mock API，未使用旧管理员素材作为近期用户页面证据，也未发起真实模型或拆解任务。
