# Agent Note: 流式写文件协议按真实回合写成「两次回复」，消除 writer 第 1 步的思考退化触发条件

Status: implemented

关联：[2026-10-10-writer-handoff-reviewer-task-and-length-stop](2026-10-10-writer-handoff-reviewer-task-and-length-stop.md)（上一轮只证实并修了返修步的角色混淆，循环本身未查清）。

证据来源：`audit-runs/20261009-180227-r5-fix-release-supervisor/progress.md` 与同目录 `loop-ab/`（20 次真实模型调用的请求变体、完整思考与汇总 `calls.jsonl`；探针在仓库外）。

## Problem

生产 r4 审计里，首条长任务（「写一个8000字左右的短篇…写完整的，我要直接发平台。」）在 **writer 第 1 步、还没有任何审稿交接**时，思考退化成「Let me write./OK./Writing.」，207k 字符后撞上 64000 输出上限，一个字没交付。角色混淆不能解释这一次。

**已证实**

1. 用同一场景的 writer 第 1 步请求（系统提示、作者原话、11 个工具与生产一致，`max_tokens=64000`）直接重放 deepseek-flash，分四组（progress.md 里按组标注）：A＝与生产逐字相同的提示；B＝协议描述不变、另改 `subagents.py` 一行（见「反证」）；C＝两次回复描述的初版措辞；D＝本次上线措辞。协议描述未改的 A、B 两组合计 8 次里 3 次撞上限且没有任何工具调用（A 1/4：228,771 字符；B 2/4：205,500 / 199,716 字符），思考后段就是生产里的那种短句循环。退化可以在没有交接的第 1 步重现。
2. 8 个样本的思考都在纠结同一件事：要「先调用 create_file，再在**同一次回复**里输出 `<file>` 正文」（例：「That's one reply… Hmm, but I'm generating one response」「write it in the tool call」「Let me output the create_file call and then the content」；生产那次：「call 更新项目信息 and 创建文件 in the same tool block, then stream content」）。3 次撞上限都卡在「开始输出」的转换点。
3. 这个计划在 Chat Completions 里做不到：一次回复里文字在前、`tool_calls` 在后，工具调用就结束这次回复；正常成功路径实际是「第 1 次回复只发 create_file → 工具返回 → 第 2 次回复以 `<file>` 写正文」。而 `base.py` 的协议写的是「调用 create_file 后**立即**在你的回复文本中输出 `<file>`」「工具调用 -> `<file>` -> 正文」，同时又要求「调用 create_file 前禁止说话」——模型按字面理解成同一次回复内的顺序，两条要求无法同时满足。
4. 只把这两处描述改成真实的两次回复顺序（其余提示、工具、参数不变）：C 0/6、D 0/6，全部正常发出 create_file；思考里明确写出「this reply = create_file，next reply = `<file>`」。按协议描述合并比较：旧描述 3/8（A+B）对 两次回复描述 0/12（C+D），Fisher 单侧 p≈0.049；只比 A 与 D（1/4 对 0/6）不显著（p≈0.4）。合并的前提是 B 只多改了一行与协议无关的要求、C 与 D 只差措辞，这一点本身是判断而非实测。
5. 已排除：前端重放（207k 字符 ≈ 约 2 万 token 草稿 + 约 4.2 万 token 短句，与 64000 上限和生产日志「hit the output cap with thinking only」吻合）；工具被禁（第 1 步工具齐全）；审稿交接（第 1 步没有）。

**反证**

- B 组只加「不在思考里起草正文、不估算字数」的要求（协议描述不变）：4 次里 2 次撞上限（这 2 次已计入上面旧描述的 3/8，不是另一份证据）。思考里起草全文是普遍现象（正常样本也这样做，并在下一步把草稿抄进 `<file>`），不是这次退化的触发条件，不采用。

**未证实 / 剩余**

- 退化本身是模型在长推理后的输出行为；本修复去掉的是原场景里已证实的触发条件，**不能宣称循环已根除**。样本 n=12，属于小样本。
- 返修步（大段 edit_file、在思考里反复核算字数，如 r4 定向覆核第 3 步 209k 字符但未循环；r3 那次第 3 步）是否还有别的触发条件，没有验证。

## Decision

只改 `agent/prompts/base.py` 流式写入协议的两处描述，与实验 D 组逐字一致：

- 「步骤」第 1、2 条：这一次回复调用 create_file（不传 content），正文不写在这次回复里、也不写进工具参数，这次回复到工具调用就结束；工具返回创建成功后，**下一次回复**第一行输出 `<file>`。
- 「交互规范 3」：保留「调用 create_file 前禁止说话」，把「立即执行：工具调用 -> `<file>` -> 正文」改为「分两次回复：这次回复调用 create_file 后就结束，不写正文；工具返回后，下一次回复以 `<file>` 开头写正文」。

与多文件链式写法兼容：写完 `</file>` 后，同一次回复里接着调用下一个 create_file 仍然成立（文字在前、工具在后）。

不新增重复阈值、思考长度上限、超时、截断或自动重试；`ERR_AGENT_OUTPUT_TRUNCATED` 仍只是撞上限后的说明与退还路径。

## Alternatives considered

- **调低 writer 的 reasoning_effort 或 max_tokens**：会缩短退化的持续时间，但不消除触发条件，且写作质量代价没有评估（runner 里已注明有意不设）。
- **流式检测重复短句并提前中止**：能让作者少等，但属于保护措施而不是根因修复；用户明确要求先在责任层修，不以阈值宣称修复。
- **让模型在同一次回复里直接写正文（例如允许 create_file 传 content）**：会放弃流式写入体验，也与现有 StreamAdapter 的捕获协议冲突，改动面大。
- **只要求不在思考里起草/估字数**：已用真实模型反证无效（见上）。

## Consequences

- 原场景 writer 第 1 步不再在「怎么同时满足先工具后正文与工具前不说话」上卡住；正常完成的样本耗时与现行提示相近（现行 84–125 秒，修改后 40–153 秒），这次修改不以提速为目的。
- 提示只改 4 行，所有项目类型共享；按 AGENTS.md 不加逐字锁定提示文案的测试，证据是上面的真实模型对照；正文仍在第 2 次回复里流式写入，前端、计费、StreamAdapter 不变。
- 上线后只能用诊断账号做少量真实回合观察，不能证明退化不会因其他原因出现；如果再出现，先看是否仍是「开始输出」转换点、是否在返修步，再决定下一步。
