# Agent Note: SQLite 递归删除重新收敛迟到子节点的写锁

## Problem

应用内对话递归删除作者稿件时，PostgreSQL 会先拿项目独占门再锁定子树；SQLite 只有进程内的 64 个文件条带锁。旧实现先读一次子树 ID，只拿这些 ID 对应的条带，然后在锁内重读子树并直接校验、删除。如果新子文件在预读后、拿锁前插入，重读会看到它，但删除者没有它的写条带。

因此可复现这一时序：保护校验看到迟到子文件仍属于 AI；作者随后通过真实 REST `update_file` 保存正文，因为该条带未持有而成功；原删除请求再把已保存的作者正文标记为已删除。这违反了 [typed authority and delivery evidence](../architecture/2026-10-14-typed-authority-and-delivery-evidence.md) 中「实际写锁内核验作者内容」的约束。

## Decision

- 仅对 `protect_author_content=true` 的 SQLite 递归删除，先从预读子树得到候选 ID，按既有稳定顺序拿去重后的条带锁，然后重读根和子树。
- 覆盖判断比较条带锁实例，而不是比较文件 ID：多个 ID 落在同一条带时已经安全，无需重试。
- 新鲜子树里若出现未覆盖条带，释放已有锁，`rollback` 结束可能的 SQLite 读快照，把新 ID 并入候选集后重试。只有在某次新鲜子树的每个目标条带都已持有时，才在这组锁内执行来源校验、软删除和提交。
- 重试上限为 4 次。成员持续扩张仍不稳定时，使用既有 `AuthorEditProtectionUnavailableError` 失败关闭；在稳定覆盖前不暂存任何删除或元数据变更。
- PostgreSQL、非递归删除、不带对话保护的直接路径不变；因此既有不受保护递归删除的 3 条 `File SELECT` 预算不变。

## Alternatives considered

- **SQLite 受保护删除一次拿全部 64 个条带锁**：最强理由是结构上排除新成员条带遗漏，无需重试。不采用，因为一个项目的删除会阻塞进程内其他项目所有文件写入，扩大了 SQLite 条带锁的冲突面。
- **只在重读后为新 ID 继续加锁**：最强理由是少一次释放和重拿。不采用，因为新条带的全局顺序可能排在已持有条带之前，违反稳定加锁顺序并引入死锁风险。
- **看到新成员立即拒绝**：最强理由是最保守且代码更少。不采用，因为一次可收敛的正常并发插入不应必然使删除失败；有界重试同时保留可用性和失败关闭。

## Consequences

- 收益：作者 REST 保存不能再穿过递归删除已检查但未持有的迟到子文件条带；作者写先获锁则新鲜保护校验拒删，删除先持有锁则作者保存在删除提交后按已删除失败，不再出现「保存成功后被删」。
- 代价：受保护的 SQLite 递归删除在成员变动时多做新鲜根/子树查询，最多尝试 4 次；持续不稳定时宁可不删除。SQLite 条带锁仍是单进程保证，不升格为跨进程互斥。
- 回归用文件型 SQLite 的独立 session 执行真实 REST 保存，并用不同条带的迟到子 ID 固定旧时序；另一用例在每次加锁前增加新条带，验证有界失败时根和所有子文件未删除，标题、排序、元数据和时间戳不变。
