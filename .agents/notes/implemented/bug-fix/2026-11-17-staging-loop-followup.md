# Agent Note: staging 单循环验收后的有限修复

## Problem

PR #377/#378 合入后的三轮 staging 浏览器验收发现：待写文件的孤立 `<` 进入聊天；作者提供的大纲和人物资料被模型重新排版并补入未提供的性别；章节自查中的多次编辑失败最终在约 618 秒收尾；MiniMax 流内错误的备援未执行原因无法从日志确定。顺序撤销、接受审阅、作者草稿保护已经通过，不能破坏这些行为。

## Decision

- 只在结构化待写文件状态丢弃纯未完成协议前缀，保留正常聊天和正文中的尖括号。
- 为现有 `create_file` 增加可选的原文复制参数：模型选择本轮作者原文中的完整片段，服务端校验精确来源后直接保存，沿用已有文件创建、权限与版本路径。生成资料仍可使用原有 `<file>` 路径。原文复制不夹带 AI 建议；建议只在回复中提出，作者要求后再编辑。
- 不通过关键词判断作者意图，不把模型自报的“逐字保存”作为证据。校验只证明所选原文片段的来源和字节一致，不声称自动识别了所有资料范围。
- G4 的服务端日志证实 618 秒中模型阶段约 616.9 秒，工具约 0.9 秒；4 次业务失败后锚点编辑恢复成功。统一工具 schema、共同重试提示与中英文自查提示：完整失败批次仍待修改，但应拆成几个小的原子批次，逐字复制较短且唯一的锚点。不降低失败阈值、不改变批次原子性。
- 上游流失败无法继续切换时记录固定的跳过原因（只配置一个供应商、供应商已尝试完、已开始答复、已完成响应）及候选数/索引。不记录正文、异常原文或凭证；不改变 failover、计费或重试。

## Alternatives considered

- **只加强逐字保存提示。** 改动最少，但已有提示在本次验收中被违反，因此需要工具层校验复制的来源。
- **按关键词自动识别并抽取人物/大纲。** 能绕过模型重写，但违反语义判断边界，且会把讨论和否定句误当资料，不采用。
- **新增独立导入流程和分类模型。** 可做更完整的范围审阅，但超出本轮有限修复，复用现有工具和创建路径。
- **将锚点失败恢复改成三次即停。** 能缩短等待，但既有 11-04 决策记录显示这会误杀可恢复编辑，不能仅凭一次耗时样本推翻。

## Consequences

- 原文复制与协议残片先补失败回归再实现。新增完整 HTTP → AgentService → SDK 工具 → SSE → 数据库/历史/计费测试；复制参数不匹配、没有请求原文、跨请求残留、空白片段和同名复用回执均有覆盖。普通生成资料仍使用原有两次回复协议。
- 本地现有 agent 与 loop E2E 套件 2420 项通过、27 项因专用环境条件跳过；使用脚本模型和临时数据库，没有付费模型调用。
- 原文复制只保证模型选择该路径后的逐字来源，不保证模型总能选择正确路径或完整资料范围。小批次提示对真实模型的延迟改善仍须 staging 复测，不能据静态或脚本测试宣称 618 秒问题已经消失。
- 不修改生产或云配置；上游自身 APIError、未授权新模型配置和计费政策不在本轮改动范围。
