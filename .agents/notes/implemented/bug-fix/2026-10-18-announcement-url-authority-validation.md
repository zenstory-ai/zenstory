# 公告链接：保存前校验原始 HTTPS authority

## Problem

生产 tag 到当前代码的上线复核发现，[此前公告 URL 校验修复](2026-10-17-announcement-billing-review-regressions.md)仍存在前后端解析差异。浏览器的 `new URL()` 会将 `https:example.com`、缺少或多出斜线的同类输入修正为完整 HTTPS 地址，也会移除 `https://@example.com` 的空凭据；管理页因此允许保存，但提交的仍是原始字符串。API 使用 `urlsplit` 校验原始 authority，拒绝这些输入并返回 422，导致已通过页面校验的公告保存失败。

## Decision

- 共享公告链接校验在浏览器解析前确认原始字符串包含 `https://` 后的非空 authority，并拒绝 authority 中的 `@`，对应 API 对用户名／密码字段的禁止规则。继续使用浏览器 URL 解析约束可打开的地址，保留空白、反斜线和端口 0 检查。
- 站内根路径、正常 HTTPS、大小写不敏感的协议、合法端口、查询、锚点和 IPv6 地址保持原有行为；不改变服务端规则或存储内容。
- 先扩展现有管理页回归，证明五种输入在修复前均错误启用保存按钮，再实施修复。有效地址回归同时确认按钮可用且原始合法地址完整提交。

## Alternatives considered

- **保存浏览器修正后的 URL。** 可让较宽松的输入直接成功，但会默默修改管理员输入，并让前端与 API 接受的原始内容仍不一致；保持现有 API 契约，选择保存前拒绝。
- **放宽后端验证。** 可以统一采用浏览器的容错效果，但涉及服务端 URL 存储和安全契约，超出这次已确认的前端校验缺口；不修改后端。

## Consequences

管理页不会再提供必然被 API 拒绝的五种链接写法，正常公告与已有链接行为保留。增加一次简短的原始 authority 检查，无新依赖、迁移、线上发布或付费调用。
