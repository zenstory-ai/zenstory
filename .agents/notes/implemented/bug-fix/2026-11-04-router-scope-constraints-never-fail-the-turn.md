# Agent Note: scope_constraints 不再让整轮路由报错

## Problem

[2026-11-01 混合请求逐项限制](2026-11-01-agent-mixed-request-item-scope.md) 让路由输出 `scope_constraints`，服务端按「最多 8 项（含短 scope）、每项 80 字、JSON 2048 字」校验，超限或格式不对就以 `schema` 技术失败结束本轮。上线后 63 小时（11-01 13:33 至 11-04 05:00 UTC）117 次请求在路由这一步失败，占全部请求约 12.7%；只涉及 4 个重度用户，其中一人占自己请求的 24%，半小时内连续失败 29 次（重发同一条消息照样失败）。都已退款，但作者无法写作。

落库的成功轮次里正好 8 项的有 67 次、7 项 40 次，最长一项 74 字：失败多半是条数超限。抽样看，路由把整个任务的内容、设定细节和步骤逐条写进了 `scope_constraints`（如「陆家家主统一为陆含章」「第11章改用《引气决·基础篇》」），真正的读写边界只有一两条（「只推演…暂不落档」）。提示词「逐项保留本轮原话中的读写边界与待确认条件」诱导了这种写法。

## Decision

- `ROUTER_PROMPT`：`scope_constraints` 只记 read_only / write_content / scope 表达不了的读写边界，尽量用作者原话，通常一条（如「第一项只推演、不落档，其余几项直接改」）；整轮权限一致时为空；任务内容、设定细节、修改要点和步骤不写进来。
- 模型给的字段按协议收成字符串列表，不报错：缺失 / null 为空，单个字符串为一项，非字符串项保留其 JSON 文本，空项丢弃；不再限制单项长度。
- 条数上限 8 → 24，JSON 总长 2048 字不变。合并后仍超预算时不截断、不丢限制，也不报错：本轮改为 `clarify_first=true`（不写文件，由角色问作者），落库限制为空，记 `Router scope constraints over budget; asking the author instead of failing`（只记超的是哪一项、条数和 JSON 字数，不记内容）。
- follow-up 的 scope 超过 80 字时不再报错：全文并入限制，落库的短 scope 截到 80 字（全文仍在限制里，不放宽范围）。
- 继承上一轮落库的限制时仍校验类型；落库内容由服务端写入、始终在预算内，校验失败说明状态损坏，照旧技术失败。

## Alternatives considered

- **超限时截断或只保留前 N 条。** 最强理由是实现最简单、作者永远能继续写。被否：限制只会收窄这一轮能改的范围，丢掉任何一条都等于放宽授权，会重演 11-01 前「未经确认就落档」的事故。
- **保留硬失败，只调高上限。** 最强理由是改动最小、语义最严格。被否：上限再高，模型偶尔多写或格式不对仍会让作者卡死在同一条消息上；限制的完整性用「先问作者」就能保住，不需要报错。
- **超限时再调一次路由让模型精简。** 最强理由是能自动恢复、不打扰作者。被否：多一次付费模型调用和延迟，且不保证第二次合规；提示词先把条目收敛到读写边界，超预算已很少见。

## Consequences

- 路由不再因 `scope_constraints` 的条数、长度或格式报错；提示词收敛后条目应明显减少，`scope_directive` 也更短。
- 极少数超 2048 字的轮次会先问作者、本轮不写文件；这一轮落库的限制为空，作者回答后由路由按本轮原话重新给出限制。
- 非字符串项以 JSON 文本进入范围指令，可读性差一些，但内容不丢。
- 限制仍是写给模型的文字约束，不是程序可证明的文件 ACL。
