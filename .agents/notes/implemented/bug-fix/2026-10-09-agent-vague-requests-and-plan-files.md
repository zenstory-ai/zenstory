# Agent Note: 笼统要求先问清楚；计划交接不扩大交付；规划写进大纲文件

Status: implemented

相关：`bug-fix/2026-10-03-agent-handoff-respects-user-scope.md`（交接以作者本轮范围为准）、`bug-fix/2026-10-09-planner-question-keeps-requested-prose.md`。

## Problem

2026-10-09 新用户审计：

- P2-16（浏览器 2/2）：短剧作者交付第一轮后发「帮我优化一下」，AI 不问优化哪里，直接把上一轮审稿的三条建议当成要求，一次改了三集（加场次、重写分镜表）。作者如果只想改台词，要回滚三个文件。同一项目首轮「先给我大纲和前三集剧本」，规划师已经把大纲和三集剧本都写完了，计划交接给 writer 后，writer 自己判断「剧本缺拍摄执行版」，给三集追加了作者没要的分镜表，还「顺手修正了一处人名」。
- P2-13（浏览器 1/1）：连载作者要「先列前十章大纲，再写第二章」，规划师把十章规划贴在对话里，大纲目录只多了一个「第2章」大纲文件。之后换设备、开新对话都找不到这份规划，后续写作也不会引用它。

## Decision

**笼统要求先问一句（`agent/graph/author_scope.py`、`writing_graph._should_clarify_first`）**

- 整句只有「（帮我 / 再）优化 / 润色 / 改改 / 完善（一下）」这类说法（`is_vague_edit_request`，去掉标点后不超过 16 字）时，不走路由：writer 单独一轮（`clarify_first_route`，`workflow_agents=[]`，`routing_metadata.clarify_first=true`）。
- 系统提示换成 `SCOPE_DIRECTIVE_CLARIFY_FIRST`：本轮不改文件、不交接，看一眼相关内容后用一句话问作者改哪部分、想要什么效果，给 2–3 个具体选项。
- 工具层：graph 置 `state["clarify_first"]`，runner 把它当作只读传给 `tools_adapter`（`read_only_reason="clarify_first"`），写文件工具仍在清单里但调用不执行，返回 `error_type="clarify_first"` 的拒绝说明（「先问作者想改哪部分」）；描述前缀写「作者的要求还不清楚，先问清楚再改」。这一轮的显式 handoff 也丢弃。
- 不问的情况：带着选中文本、附加或引用了文件；上一轮是结构化澄清卡；上一轮 AI 收尾的提问 / 选项里只提了一处修改（`previous_question_offers_one_edit`：「要我继续写第5章，还是先把第4章开头改紧凑一点？」，作者回「改改」就是答应这一处；只数收尾的选项行和问句，「我把节奏改快了一些。」这种交代做了什么的句子、「命运从此改变」里的「改」不算提议）；上一轮已经为笼统要求问过一次（`clarify_first` 随 routing 落库，只问一次）。上一轮只是按回复协议以选项 / 问句收尾、选项里有两处以上修改或没有修改时照样先问。
- 判断放在「沿用上一轮路由」（`inherit_routing_after_clarification`）之前：否则上一轮以选项收尾时，「帮我优化一下」会被当成简短作答直接沿用上一轮的 writer 路由，又一次改好几个文件。

**计划交接不扩大交付**：计划交接的交接说明固定追加 `PLANNED_HANDOFF_SCOPE_NOTE`：上一位完成的不重做、不改刚交付的文件，只补作者范围里还没完成的部分，不追加作者没要的产出（分镜表、拍摄执行版、额外文档），已经全部交付时一句话确认后结束。`WRITER_PROMPT` 和 `UNIFIED_EXECUTION_PROTOCOL` 加同样的要求。

**规划写进大纲文件**

- 提示词：`PLANNER_PROMPT` 和 `UNIFIED_EXECUTION_PROTOCOL` 要求作者要的大纲、分章 / 分集规划、人设、设定写进对应目录的文件，对话里只说写在哪个文件和一两句要点。
- 图兜底：规划师一轮结束（没有显式交接、没停下、不是只读 / 先问清楚的请求，且作者这一轮叫 AI 产出一份规划，见 `request_asks_for_a_plan`：提到「大纲 / 细纲 / 章纲 / 分章 / 分集 / 规划 / 梗概 / 目录」的那一分句里有叫 AI 产出的说法（写 / 列 / 做 / 出 / 整理 / 给我 / 帮我…），或者整句就是「前十章大纲」这样的短要求；讨论（「先聊聊前十章大纲怎么安排」「大纲怎么写比较好」）不算，除非同一分句里明说「帮我 / 给我 / 请」；回答 / 评价上一轮的规划（「大纲没问题，开始写第一章吧」「分集规划挺好」「大纲写得不错」）不算；拿规划当依据（「按大纲写第5章」）不算；回答规划师的提问（「爽文，主角叫陈默」）没提规划，也不算；问进度 / 在哪（「大纲好了吗」「大纲写了吗」「我的大纲在哪」）和提意见（「你的大纲有问题」「这个大纲第5章节奏太慢」）不算，除非同一分句里明说「帮我 / 给我 / 请」——要改已有大纲走修改大纲文件，不是补一份新规划）时，看最后一次工具调用之后、最后一个 `</file>` 之后的收尾文字（`chat_only_plan_units`）：至少 200 字、逐行列出至少 5 个不同的「第 N 章 / 集」时，视为把规划贴在了对话里。本请求写过的大纲文件已经覆盖其中 80% 以上的章 / 集时不补；否则同一个规划师再跑一轮（`chat_plan_correction_context`：新建或补进大纲文件，用 `<file>` 写完整规划，对话里不再贴），每个请求只补一次。规划师原本以提问收尾的，「等作者回答」带过补写轮（与空文件纠偏同一机制）。

## Alternatives considered

- **让路由 LLM 多输出一个 `needs_clarification` 字段。** 最强理由：能识别更多说法（「感觉不太对，弄弄」）。被否：多一个字段就多一次判错的机会，判错时整轮什么都不改；「帮我优化一下」这类整句笼统要求用规则就能稳定识别，命中时还省掉一次路由调用。长尾说法仍交给路由和提示词。
- **笼统要求复用只读（`read_only=true`）。** 最强理由：工具层、交接拦截都现成。被否：只读的拒绝说明是「作者要求不改文件」，交接被拦时还会给作者一张「你要求本轮只回答、不改文件」的卡片，和作者说的话对不上；作者下一句「改吧」又会被只读沿用规则挡住。
- **规划贴在对话里时由服务端直接把那段文字存成大纲文件。** 最强理由：确定、不多花一次模型调用。被否：收尾文字里混着说明、选项和提问，原样存进去需要再清洗；文件标题、放在哪个目录、是否并进已有大纲，需要规划师判断。
- **规划师已经写了正文时跳过计划交接给 writer。** 最强理由：P2-16 首轮里规划师已经写完三集，writer 那一轮纯属多余。被否：规划师常常只写了一部分（作者要三集只写了一集），跳过就少交付；交接说明里写清「已经全部交付就一句话确认后结束」，代价只是一次很短的模型调用。

## Consequences

- 收益：「帮我优化一下」不再一次改多个文件，作者先选方向；计划交接后的 writer 不再给作者加分镜表之类的额外产出；作者要的分章规划能在大纲目录里找到。
- 代价：
  - 笼统要求那一轮也计一条额度，作者回答后才真正修改（只问一次）。只认整句笼统的说法，「帮我优化一下，节奏有点慢」不算笼统，照常路由。
  - 规划补写轮多一次模型调用，前端会多出一张「大纲规划师 · 第 2 步」；作者要了规划、规划师贴的却是选项列表（5 行以上「第 N 章」）时也会被要求存文件。只认中文说法；hook_designer 贴在对话里的规划不补。
  - 作者上一轮要了规划、规划师先问了一句，作者这一轮只回答（「爽文」）时，规划师这轮贴出的规划不补写（作者这句没要规划），只靠提示词让规划师写进文件。
  - 「只提了一处修改」靠关键词数选项，作者回「帮我优化一下」而上一轮恰好只提了一处修改时按那一处改；只认中文的笼统说法，英文「improve it」照常走路由。
  - 补写判断依赖请求级读写台账里的文件 id；台账查库失败时不补写（宁可漏补，也不重复建文件）。
