# Agent Note: 作者手动改过的文件，作者没点名时 AI 不改、不删，改为问作者

Status: implemented

相关：`bug-fix/2026-10-09-ai-write-backs-up-unversioned-text.md`（AI 覆盖前先备份没进历史的正文）只保证「改了还能找回来」；本 note 让 AI 在作者没要求时根本不去改。`bug-fix/2026-10-03-agent-handoff-respects-user-scope.md` 管的是交接范围，不涉及具体文件。

## Problem

2026-10-09 新用户审计 P1-3（浏览器 1/1）：连载作者写完第 1–3 章后，在第 3 章把配角「老周」手动改成「老秦」（19 处），等到「刚刚保存」，再发「继续写下一章」。AI 写完第 4 章，总结里写「顺手修的两处：第3章摊主名统一成『老周』（原文写成『老秦』，共19处）」，第 3 章被改回老周=19、老秦=0。

作者是故意改的名。没细看总结的话，会以为自动保存坏了；作者从此不敢让 AI 碰项目。原因有三层：

- 提示词只说「未授权的连带修改只报告」，没说已有章节不能动，也没说作者手改的写法优先；审稿规则把「和前两章矛盾」列为必须返工的客观缺陷，writer 返工时又被要求把修好的问题写成「顺手修的」。
- 工具层对「改哪个文件」没有任何约束，`edit_file` 对已有章节和本轮新写的章节一视同仁。
- 工作集把第 3 章标成「上一轮已修改」，agent 不知道之后作者又手动改过。

## Decision

**工具层（`agent/tools/author_edit_guard.py`，`mcp_tools._author_edit_refusal`）**

`edit_file`、`delete_file`（包括 `parallel_execute` 里的同名子任务，它们走同一个函数）执行前判断；递归删除文件夹时，作者点名这个文件夹并说删（「把废稿文件夹删了」）才整个删，否则逐个检查里面的文件，作者手改过的要作者点名并说删（或答应了上一轮的提问）才跟着删——「正文改紧凑一点」「第3章改一下」都不是要删（`request_deletes_folder` / `request_deletes_file`）；剧本项目里 `create_file` 命中同名剧集的幂等复用（`reused_existing=true` 且原本非空，接下来的 `<file>` 正文会整份覆盖它）时同样判断，不放行就不复用、返回拒绝（说明里告诉模型不要用 `<file>` 写它、新的一集换集数和标题）：

1. 文件当前正文是不是作者写下的（`latest_text_is_authors`）：正文非空、有版本，并且最新版本不是 AI 写的（`change_source=ai` 或作者接受的 AI 修改 `change_type=ai_edit` 之外的都算：作者编辑、恢复、导入、系统备份），或者正文和最新版本不一致（作者版本额度满时保存不留版本）。没有任何版本的旧数据不拦。
2. 作者这一轮的话有没有指向这个文件（`request_targets_file`），满足任一即放行：
   - 本轮附加了它，或引用的选中文本来自它；
   - 上一轮 AI 因为这条规则没改成它（落库在 assistant 消息 routing 的 `author_confirm_file_ids`），并且作者这一轮答应了（`author_confirms_change`）：有「可以 / 确认 / 没问题 / 改吧 / 统一成…」这类说法，或单独成句的「好 / 行 / 嗯」（「写好一点」里的「好」不算），没有「不用 / 别 / 先不 / 保持 / 就叫 / 按我的 / 我自己」这类不改的说法。不带方向的「统一」（「统一吧」「要统一」「人名要统一」）不算答应：作者改的写法是最新设定，往作者这边统一用不着动这个文件，往回统一要作者说「统一成老周」。作者在让 AI 往下写（下一章、继续写 / 接着写、点名的是别的章）时，要明确答应改（「可以，统一成老周再写下一章」「好，改吧，然后写下一章」）才算；「好，继续写下一章」「继续写第5章，写好一点」「继续写下一章，开头改得有悬念一点」（说的是新的一章）不算。只记下被拒的文件不等于作者同意：「不用改，继续写下一章」「不用改，第3章就叫老秦」下一轮仍然拦；
   - 作者原话（含运行中追加的消息）里点名它并要求改：完整标题、标题里去掉「第N章」后至少 2 个字的词、第 N 章 / 集（含中文数字、「第1-3章」「前三章」「第2、3章」），所在分句或紧跟的下一分句（下一分句没有另外点名章节时）里有改动的说法（改 / 修正 / 润色 / 精简 / 调整 / 统一 / 重写 / 删…）。「继续写第四章，夜市那段的氛围延续下去」不算改「第3章 夜市」，「参考第3章的写法写第4章」不算改第3章，「第3章写得太拖了，帮我精简一下」算；
   - 改动的说法不包括：「改变 / 改天」（「夜市里主角命运改变」）、发新章的「继续更新 / 今天更新两章」、作者讲自己改过的（「我把第3章的老周改成老秦了」「第3章我改过了」「第3章已经改好了」）、抱怨（「你怎么把第3章改了」）；
   - 「全书 / 所有章节 / 每一章」这类全局说法并要求改（同样看分句）。「统一」单独不算全局：「统一一下格式再写下一章」「继续写下一章，人名要统一」不放开已有章节；
   - 作者正开着它：说了「这一章 / 这里」，或者提了改动（「把开头改得更有悬念一点」「精简一下对话」），并且没点名别的文件（别的章 / 集号、别的《标题》、别的文件类别）、不是在要下一章或接着往下写（「接着写，节奏改快点」只能往后追加）。没点名时不带方向的「统一」不算改动：作者刚把老周改成老秦、第 3 章还开着，说「人名要统一」「把格式统一一下」时 AI 仍不能改第 3 章（「这一章的人名统一一下」「老秦统一成老周」算）；
   - 大纲 / 人设 / 设定这类文件类别并同时有改动的说法（「按大纲写第5章」不算）；
   - 同一分句里前面带否定（「别动第3章」「别改我已经写好的章节」）的不算；
   - 「把老秦改成老周」这类改名：每一处替换 / 删除的原文都含被换掉的词；「把主角的名字改成李明」这类被换掉的是泛称（名字 / 称呼 / 叫法）时，每一处替换的新文字里有「李明」、原文里没有、原文不超过 80 字；
   - 作者正开着它、本轮不是写下一章、这次只往末尾追加（作者写了半章说「继续写」）。
3. 不放行时不执行，返回 `error_type=author_edit_protected`：`error` 给模型（正文是作者改过的、以作者为准、不要重试也不要改回去、新内容沿用作者写法、有出入在回复里问作者往哪边改，默认建议按作者的写法改其他章节，例如「要把第2章也改成老秦吗？」），`user_message` 给作者看的工具卡片（「《第3章 三十年》有你手动改过的内容，AI 没有动它；需要改的话会先问你。」）。文件 id 记进请求级 `AuthorEditRefusals`，`service.py` 落库时并进 routing，下一轮放行。

只在应用内对话里生效：`ToolContext` 带着作者原话（`author_message`）时才判断，Agent API、测试直接调工具等路径不受影响。判定本身出错时不拦，交给后面的正常路径。

**上下文**：跨轮工作集（`session_loader._build_working_set_context`）里，当前正文是作者手改的文件在标题行后标注「现在的正文是作者手动改过的：…以作者为准，后面的内容沿用，不要改回去；作者没要求改这个文件时不要动它」，第 4 章就会沿用「老秦」。

**提示词**：`UNIFIED_EXECUTION_PROTOCOL` 加「只改作者本轮点名的文件；没点名的已有章节一律不动，不顺手统一人名、改错字、调时间线；对不上时一句话指出位置、问作者」和「作者手动改过的写法是最新设定」。`WRITER_PROMPT` 加同样的两条，返工时只改本轮写的文件。`QUALITY_REVIEWER_PROMPT` 的客观缺陷「和已确认事实矛盾」补充：作者手改的写法以作者为准，已有章节之间对不上不返工，写成可选建议问作者。

## Alternatives considered

- **只改提示词。** 最强理由：改动最小，模型多数时候会照做（作者说「别改我写好的章节」后它立刻照做）。被否：这次就是在提示词已经写着「未授权的连带修改只报告」的情况下发生的；审稿返工、writer 顺手修的路径都能绕过去，作者信任的底线需要硬保证。
- **只要最新版本是作者的就一律拒绝，不看作者这一轮说了什么。** 最强理由：规则最简单、最不会漏。被否：作者说「把第三章结尾改一下」「全书统一叫老周」时也改不了，只能反复确认；作者写了半章说「继续写」时连追加都不行。
- **让模型在调用时传 `author_requested=true` 自证（像 `update_project` 改名那样）。** 最强理由：模型能理解「作者在回答我的提问」这类语义，比关键词准。被否：P1-3 里模型自认为在修笔误，同样会传 true；`update_project` 那里也是由服务端拿作者原话复核，模型的自证不作数。
- **按 `File.updated_at` 和最近一次 AI 写入时间比较。** 最强理由：不用重放版本 diff，查询便宜。被否：AI 写入同样更新 `updated_at`，判断不出最后一笔是谁写的；版本表的 `change_source` 才是可信的来源记录（客户端可传的 `change_source` 也只在作者自己的保存接口上，影响不了 AI 的判断）。
- **作者正开着的文件一律放行。** 最强理由：「这一章」「改一下」多半指正开着的文件。被否：P1-3 里作者正开着第 3 章说「继续写下一章」，放行就等于没修。只在作者用「这一章 / 这里」、提了改动且不是要下一章、或只追加时放行。
- **正开着的文件只认「这一章 / 这里」。** 最强理由：最不会误放。被否（第一版就是这样，评审实测）：作者自己写或导入的第 1 章开着，说「把开头改得更有悬念一点」被拒，模型回「第3章是你手动改过的，动它之前我先跟你确认一句」，作者要多发一条、多花一条免费额度；对自己写稿的作者这是最常用的流程。
- **「统一」算改动的说法，没点名哪一章时也放行正开着的文件和上一轮问过的文件。** 最强理由：作者说「人名要统一」多半就是想统一，再问一句要多花一条额度。被否（第二轮评审）：作者刚把老周改成老秦，第 3 章还开着，说「统一一下格式」或回「要统一」时，AI 会按大多数章节的写法把老秦改回老周，正是审计的场景；不带方向的「统一」往作者这边统一用不着动作者改过的文件，往回统一要作者说清楚「统一成谁」。
- **上一轮记下被拒的文件，下一轮无条件放行。** 最强理由：作者回「可以」这类短句时不用再猜语义。被否（第一版，评审指出）：被拒就记、不管作者回了什么，「不用改，第3章就叫老秦」「继续写第5章」都会放开，审计场景晚一轮照样发生，工具层兜底恰好在最需要的时候失效。

## Consequences

- 收益：作者没点名的已有章节，尤其是作者手改过的，AI 不会再改回去或删掉；AI 只能在回复里提醒、问作者，作者回一句「可以」下一轮就能改。作者说清楚要改的（点名、全书、改名、这一章、附加 / 选中）照常改；本轮 AI 新写的章节、审稿返工不受影响。
- 代价：
  - 关键词判断有漏判：作者用别的说法指代没开着的文件（「主角那段」「上回那章」）时会被拒一次，AI 改为问作者，作者要多回一句。
  - 也有误放：作者说「全书 / 所有章节」并要求改时整轮放开；正开着的文件只要提了改动、没点名别的文件就放开，AI 仍可能在这一章里顺手改作者的用词（提示词兜底）。
  - 作者没回答、换了话题（「继续写第5章」）时，上一轮问过的文件仍受保护，AI 下一轮会再提一次。
  - 作者手改过的大纲 / 人设也受保护：「继续写下一章」时 AI 想顺手更新作者改过的大纲会被拒，只能新建文件或在回复里提。
  - 每次 `edit_file` / `delete_file` 多一次版本查询和 diff 重放（只查一个文件；递归删除文件夹时每个子文件一次，最多 500 个）；工作集每个文件多一次版本查询。长章节、增量链很深时会多一些查库和 difflib 开销，目前可以接受。
  - 工具卡片（`ToolResultCard`）：`author_edit_protected` 和 `clarify_first` 是 AI 有意没动文件，标题不写「编辑文件失败」，写「保留了你改过的内容」/「先问清楚再改」（`chat:tool.skippedTitle.*`），图标用信息图标。中文界面正文用后端的 `user_message`；其他语言按 `error_type` 用 `chat:tool.failureHint.authorEdited`（带标题）/ `authorEditedUntitled` / `clarifyFirst`。
  - 改动说法的排除规则（作者讲自己改过的、「改变」、「继续更新」）也是关键词：「我想改」「我觉得…改一下」照常算要求，但「我把第3章改短点」这种第一人称祈使句会被当成讲自己改过的，被拒一次后 AI 去问作者。
  - 拒绝经熔断器记账，模型无视说明连续重试同一调用 3 次时本轮以错误结束（与只读拒绝相同）。

## Verification

`cd apps/server && venv/bin/python -m pytest tests/test_agent/test_author_edit_guard.py tests/test_agent/test_session_loader.py -q --no-cov -n 0`：审计原样（AI 写的第 3 章 → 作者经真实保存接口改名 → 「继续写下一章」时 `edit_file` 把老秦改回老周）被拒、正文不变、文件 id 记入 `AuthorEditRefusals`；点名第 3 章、回答上一轮提问（`author_confirm_file_ids`）、本轮 AI 写的章节可以改；上一轮被拒、作者回「不用改，继续写下一章」时仍然拒绝；作者开着自己改过的第 1 章说「把开头改得更有悬念一点」直接改成功；剧本项目 `create_file` 复用作者手改过的「第3集」被拒（作者说「第3集重写一下」时照常复用）；递归删除含作者手改章节的文件夹被拒（「继续写下一章」「正文改紧凑一点」都拒）、章节和文件夹都还在，作者说「把正文文件夹删了」时照常删；不带方向的「统一」不放开正开着的第 3 章、也不算答应上一轮的提问；「改变」「继续更新」、作者讲自己改过的、「继续写第5章，写好一点」「我自己改好了」都不放行；答应 / 不答应的各种回复、「把主角的名字改成李明」、标题里的词和「统一」不再误放；额度满时没留版本的手改同样受保护；`delete_file` 被拒；没有作者原话时不拦；否定说法、改名、只追加、「这一章」、文件类别等判定规则；工作集给作者手改过的文件加标注、AI 写的不加。

真实模型（deepseek，本地 SQLite + 真实工作流和工具，2026-10-09，各 1 次）：
- 审计原样（第 2 章 AI 写「老周」，第 3 章作者改成「老秦」，正开着第 3 章，发「继续写下一章」，带工作集标注）：第 3 章没被改；新写的第 4 章用「老秦」28 处、「老周」0 处；回复里问作者第 2 章要不要统一，没有自己改。守卫没被触发（提示词和标注就够了）。
- 评审修复后（同一脚本）：作者手改过的第 3 章开着，发「把开头改得更有悬念一点」：只跑 writer，`edit_file` 一次成功、没有被拒，第 3 章开头改了、「老秦」5 处保留、「老周」0 处；回复里把第 2 / 3 章人名不一致作为问题问作者，没有自己统一。
- 去掉工作集标注、作者还说「前后人名对不上的地方顺手改掉」：模型去改第 3 章，被守卫拒绝 1 次，第 3 章不变；模型没有重试，在回复里给作者 A / B 两个选项（统一成老周 / 保留老秦）。回复里出现「第3章这轮我改不动」，随后把拒绝说明改成建议说「第3章是你手动改过的，我没动它」，不说「改不动」。
- 第二轮评审修复后（同一脚本，不给工作集标注）：作者手改过的第 3 章开着，发「继续写下一章，人名要统一」：第 3 章没被改（老秦 3 处），守卫没被触发；回复里给作者 A / B 两个方向（把第 3 章改成老周 / 三章都改成老秦）让作者选，没有自己统一。新写的第 4 章用了「老周」：这个脚本没给工作集标注，模型不知道第 3 章是作者改的（真实对话里有标注）。
- 上一轮 AI 问过「要统一吗？」、作者只回「要统一」（第 3 章在 `author_confirm_file_ids` 里）：第 3 章不放开；模型把第 2 章的老周改成老秦，回复说「第3章是你改过的写法，我保持原样没动」。
