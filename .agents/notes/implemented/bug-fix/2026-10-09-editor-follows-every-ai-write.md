# Agent Note: 编辑器跟随本轮 AI 的每一次写入；有未保存修改时进入对比而不是覆盖

Status: implemented

## Problem

新手审计（PR163 审计 P1-4）：在第 1 章页面发「接着写第二章」，AI 先用 create_file 流式写出第 2 章 v1，同一轮里写作者又改了几处（v2）。这一轮结束后编辑器一直停在 v1，字数和 AI 回复里报的不一致；作者在 v1 上打字，就是在旧稿上改。

服务端日志定位了根因：第二次写入发生在 `parallel_execute` 的子任务里（`parallel_execute completed: 2/2 tasks`）。stream adapter 只为顶层 `edit_file` 发 `file_edit_*` 事件，`parallel_execute` / `update_file` 成功后前端只刷新文件树，从不让编辑器重读打开着的文件，所以日志里只有 `GET file-tree`，没有 `GET file`。

另外，原来的 AI 刷新路径（`triggerEditorRefresh` → `loadData`）在作者有未保存修改时会直接把编辑器显示的正文换成服务端版本，作者刚写的字从屏幕上消失（草稿还在 SimpleEditor 内部，要等下一次保存撞 409 才以对比的形式出现），属于「静默覆盖」。

审计里还记录了一次「打字后页面卡死、renderer CPU 100%」，根因仍未定，排查记录见下面的「卡死排查」。本次修复去掉了触发它的前置状态（编辑器停在旧版本、作者在旧稿上打字）。

## Decision

- `useChatStreaming`：`parallel_execute` 成功后，让编辑器重读作者当前打开的文件（`refreshOpenFileFromServer`，正在流式写入的那份除外，它有自己的收尾重读）。一轮结束（`onComplete`）或出错（`onError`）时，只要本轮写过文件或服务端确认有改动，再兜底重读一次。
- `Editor`：AI / 撤销触发的刷新改走 `syncOpenFileFromServer`（读取失败按 1s、3s 重试两次；仍失败时编辑器顶部出现提示「AI 刚改过这个文件，但最新内容没能载入，你看到的可能是旧版本。你的修改不会丢。」和「重新载入」按钮，不再只记一条日志；保存令牌照样兜底，旧稿保存会撞 409 进入同一套对比）：
  - 服务端版本与编辑器当前基线相同：什么都不做。
  - 正文没有未保存修改（包括打了字又删掉）：跟随服务端版本，并通过 `serverBaseline` 信号让 SimpleEditor 把草稿、保存令牌、未保存标记和字数基线一起换成服务端版本。作者没改过的标题跟随服务端（AI 可能改了名）；作者改了还没保存的标题保留，下一次自动保存带新令牌写回。
  - 正文有未保存修改：不替换作者的文字，做三方合并后打开对比审阅。基线 = 作者开始改的那一版（编辑器上次加载或保存的正文），作者的改动（基线 → 本地）先按段落、两边都改过的段落再按字符重放到服务端版本上。对比左边 = 服务端最新版本，右边 = 服务端版本 + 作者的改动，所以提案只包含作者真正写的内容；两边改了同一处的冲突也作为提案显示，但初始为「拒绝」，作者直接点完成时冲突处保留服务端（AI）的内容。提示「AI 刚改过这个文件，你还有没保存的修改。两边的内容都在，请在对比里逐处选择要保留哪一份。」已经在对比审阅中时不重复进入。
  - 保存撞 409、完成审阅撞 409 两条已有路径也改用同一套三方合并（前者的基线是编辑器上次的正文，后者是这次审阅的左侧正文），不再用「服务端 vs 作者整篇」的两方对比。
  - 完成审阅时，作者在进入审阅前改了但没保存的标题随这次写回一起保存（审阅结束会把编辑器标记为已保存，以前标题会就此丢掉）。
- `SimpleEditor`：对比审阅打开期间不排防抖自动保存。审阅完成时由 `handleFinishReview` 带服务端令牌整体写回；此前若继续按旧令牌自动保存，只会撞 409 并把作者已做的逐处选择重置。离开编辑器（卸载）时：对比还开着就不发注定 409 的保存，直接写本地草稿快照；不在对比中则照常保存，保存没成功也写快照。
- 对比中离开（离开项目、关页面、刷新）：本地快照存的是「此刻点完成会保存的内容」（服务端新版本 + 作者的改动，按作者已做的逐处选择），令牌是服务端新版本的 `updated_at`；不再存作者在旧版本上的整篇草稿（旧令牌、恢复后会把 AI 的新版本改回去）。`Editor` 卸载时关闭这类对比，不让它带着旧状态在项目状态里残留。回到这份文件时令牌一致，走已有的「已恢复」路径直接显示合并后的正文，作者接着写会带新令牌保存。编辑器只是被临时换下（例如素材预览）时对比保留；之后完成对比会清掉这期间留下的快照（作者还没处理的恢复横幅除外）。
- AI 的 `<file>` 流结束后重读这份文件时，读到的正文同时作为 SimpleEditor 的基线（`loadData({ followServer: true })` → `serverBaseline`）。此前字数基线停在流式输出的第一个片段，作者第一次保存会把 AI 写的整章算成作者新增的字数，并按「作者编辑」生成一个版本。
- 回归：`Editor.aiRoundSync.test.tsx` 用真实 ProjectProvider + useChatStreaming 回调 + Editor/SimpleEditor 复现「同轮 create 再 edit / parallel_execute，然后打字」，并覆盖：直接完成对比后正文 = v2 + 作者补的一句；冲突处默认保留 AI；打字又删掉后不会带旧令牌发出 v1；只改标题时正文跟随 v2、标题保留并一起保存；对比中改过的标题随完成审阅保存；字数统计只算作者的字；读取失败后重试；重试仍失败时出现提示、点「重新载入」后跟上 v2；对比中离开不发 PUT、本地快照是 v2 + 作者的句子（v2 令牌）、对比关闭、回来后接着写保存在 v2 之上；对比中关页面（pagehide）同样存合并后的正文；只有流式写入时作者打一个字只算 1 个字、不生成版本。`rebaseLocalEdits.test.ts` 覆盖合并本身。`e2e/editor-ai-round-sync-mocked.spec.ts` 在真实页面里喂同样的 SSE 序列，覆盖「作者有未保存修改时进入对比、不发 PUT」「直接完成对比后 v2 仍在」「对比中离开页面再回来，正文 = v2 + 作者的句子，接着写不撞 409」，并在打字后的自动保存窗口里探测页面响应、断言没有超过 1 秒的 long task。`Editor.lifecycle.test.tsx` 原来断言「AI 刷新把编辑器显示换成服务端正文」的评估用例改为断言新约定。

## Alternatives considered

- **服务端为 parallel_execute 子任务补发 file_edit_* 事件。** 最强理由：前端无需特判，进度条也能显示子任务改了哪几处。被否：子任务结果被截断后没有可靠的逐条编辑明细，还要改事件协议；前端「写入后重读打开的文件」对任何写入路径都成立，以后新增的写工具也不会漏。服务端补事件可以以后单独做。
- **有未保存修改时仍然显示服务端版本，等保存撞 409 再进对比（原行为）。** 最强理由：改动最小，令牌语义不变。被否：在保存之前作者看到自己刚写的字消失了，继续打字时打在服务端版本上，之前的修改只剩在内部草稿里，很容易被后续输入覆盖掉。
- **每次刷新都直接进对比。** 最强理由：作者对每次 AI 改动都有确认机会。被否：没有未保存修改时，对比只是在复述 AI 已经落库的改动，打断写作；AI 改动在版本历史里可回看。

## Consequences

- 收益：同一轮里 AI 多次写同一章时，编辑器停在最后一次写入之后；作者手里的未保存文字不会被替换，冲突以对比的形式出现；对比期间不会被自动保存打断。
- 代价：每次 parallel_execute 成功和每轮结束各多一次 `GET /files/{id}`（只针对打开着的文件）；对比打开期间作者的修改要等完成对比才落库。三方合并是启发式的：段落和字符层面都对不上的地方按冲突处理，默认保留服务端版本，作者的那一份在对比里可以手动接受。
- 未解决：审计中的一次性页面卡死未能复现，根因未定；若再次出现需要带 performance profile 重新定位。已知会让编辑器停在旧版本、或带旧草稿/旧令牌保存的路径（未重读、读取失败、打字又删掉、只改标题、对比中离开）都已处理。

## 卡死排查（2026-10-09，未复现）

- 现有证据：审计 API 日志里，卡死那个标签页每 60 秒一次的额度轮询（12:43:14.8、12:44:14.9）此后不再出现，卡死发生在 12:44:15 到 12:45:15 之间，即作者打字后、3 秒自动保存之前（日志里没有 PUT）。截图 `tgtnext-15` 显示「未保存 / 字数 1434 / 段落 136」，编辑区滚到底部却是空白，像主线程卡住后未绘制的区域。CDP `Runtime.evaluate` 超时说明是主线程上的同步长任务，不是 React 调度器那种会让出的循环。
- 复现尝试：mocked Chromium（Playwright，真实页面，页面内 SSE 按事件喂入），create_file 流式写 v1，再在同一轮写 v2，然后在末尾打一个字，测量 `PerformanceObserver('longtask')` 和每 750ms 一次的 `page.evaluate` 往返。变体：v2 来自 `parallel_execute`（无 file_edit 事件）、只有 `file_edit_start` 没有 `file_edit_end`、完整 `edit_file`；`keyboard.type` 和 `insertText`；24 段长句章节，以及在修复前代码上再跑一遍 136 段短句章节（贴近审计的段落数）。分别在当前代码和修复前代码（`9cfd957` 之前的 Editor / SimpleEditor / useChatStreaming / diffReview）上跑：修复前代码能复现「停在 v1」，打字 3 秒后自动保存撞 409、进入对比，最长任务约 100ms（409 后的段落对比），页面一直响应；当前代码跟随 v2，没有超过 50ms 的长任务。都没有卡死。
- 读代码排除：Editor / SimpleEditor 里会 setState 的 effect 都有一次性门槛（流结束重读按上一次的流式文件 id，`serverBaseline` 按版本号，草稿恢复按恢复 key，退出审阅只在状态翻转时，自动保存 effect 每次清掉自己的定时器），没有「每次渲染都从 props 回写 state」的循环；全局监听里 ProductTour 的 scroll/resize/ResizeObserver 只在导览进行中挂载，SEOProvider 的 MutationObserver 只在 /docs；打字路径上的正则（字数、段落数、`PARAGRAPH_BREAK_RE`）都是线性的。没有找到可以加防护的循环，所以这里不加「看起来像防护」的代码；改为在 e2e 里对打字后的长任务设上限，回归时能第一时间发现。
