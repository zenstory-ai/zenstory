# Bug-fix Note: 中断后「继续」接上原计划剩余阶段，完成标记不取消计划阶段

Status: implemented

关联：[路由延续](2026-10-08-agent-routing-continuity.md)、[路由继承任务负责人](2026-10-11-routing-inherits-the-task-owner.md)。

## Problem

#269 两处已证机制：

1. `resume_route_after_exhaustion` 在上一轮被时限/上限截停、作者只回"继续"时，恢复到上一轮的 agent，但一律 `quick` 且 `workflow_agents=[]`。"先规划，再写第1—3章"（planner/standard）在规划阶段被截停，继续之后只剩 planner，原计划的 writer 阶段丢失。
2. 有计划交接待走时，`[TASK_COMPLETE]` / `[任务完成]` 标记仍可结束整个工作流。规划师写完自己那一段加上标记，就把作者要求的正文阶段一起取消了。

## Decision

- 恢复时用上一轮**落库的结构化路由**重算原计划：`[initial_agent, *plan_workflow_agents(...)]`，沿用同样的 write_content / read_only 裁剪，取被恢复 agent 之后的阶段作为 `workflow_agents`，`workflow_plan` 保持原 workflow。被恢复的是审稿人、路由不完整、agent 不在原计划里时，照旧不接任何阶段。read_only、scope 等限制原样带过来。
- 图里区分"计划交接"和"自动送审"：只要还有计划交接待走，完成标记只结束当前阶段，不触发 `task_complete`，并记一条日志；自动送审仍可被显式完成标记打断（原行为）。计划已按作者范围裁剪（只要大纲时没有 writer），所以只要大纲时标记照样结束。
- 不靠回复文字猜进度，不自动续写，不增加生成请求或重试；时限、熔断和计费不变。

## Alternatives considered

- **把任务板的剩余编号单元作为完成门，未完成就自动继续写。** 最强理由是能精确续接"第2、3章还没写"。未采用：任务板保存是可选的 Redis、有 TTL，且只在完成时更新，不是每次中断都可靠的检查点；没有可靠合同时自动继续写会扩大成本和范围。留待后续有可靠检查点再做。
- **恢复时重新走 LLM 路由。** 最强理由是能理解新的上下文。未采用：原先就是为避免"继续"被重新规划成多 agent 流程、从头重读文件才加的确定性恢复；落库路由已经包含原计划。
- **完全忽略完成标记。** 未采用：审稿人和单阶段任务依靠它正常收尾；只在还有计划阶段时不让它越权。

## Consequences

- 规划阶段被截停后"继续"，规划完会按原计划交给 writer；writer 阶段被截停的仍只恢复 writer。交接说明照旧带"已完成的不重做"和作者范围。
- 中途同一阶段内的剩余单元（例如 writer 写完第1章后被截停）仍由 writer 依据交接/任务板自行接续，本批不新增单元级检查点。
- 新要求、只读和局部范围仍按原规则生效：只有固定"继续"短句走这条恢复，其余消息正常路由。
