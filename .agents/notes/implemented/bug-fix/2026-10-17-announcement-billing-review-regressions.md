# 公告与订阅最终回归中的边界修复

## Problem

用户确认当前视觉后要求整体回归与独立 review。[轻量公告](../feature/2026-10-17-lightweight-announcement-banner.md)后台使用共享查询缓存，但编辑器只在挂载时初始化草稿；从其他页面返回时可能拿旧缓存初始化，再忽略刚获取的新配置。公告链接前端允许包含空白或端口 0，而 API 拒绝，导致可点击保存却收到 422。初次创建时捕获数据库完整性异常的范围过大，审计故障会被误报为 409。

订阅页在目录慢或失败时可以先打开结算窗口；此前未收到价格也能点击付款。用户尚未看到金额，不应创建订单。

## Decision

- 保持已经确认的[原订阅布局](../feature/2026-10-17-subscription-original-layout-restored.md)与[无手动兑换入口](../feature/2026-10-17-remove-billing-redemption-entry.md)，不追加营销设计。
- 公告后台本次挂载的初始请求结束后才初始化编辑器；成功保存或显式加载最新配置均更新缓存。保存后失效普通端公告查询，使 SPA 返回首页能获取新配置。后续后台刷新不覆盖未保存草稿，真正的并发冲突仍走双 token 校验和显式恢复。
- 前端拒绝空白（含 Unicode 空白）与端口 0，和后端公告 URL 约束一致。横幅标题保留原外观，使用段落避免出现在页面 h1 之前的 h2。
- 仅公告首次插入 flush 的完整性异常按并发冲突处理；审计或提交的完整性异常回滚后保留 500 语义，不伪装成管理员冲突。
- 付款必须已显示所选周期的正整数分价格；没有有效价格时禁用按钮并阻止创建订单。目录加载中与无法确认价格分别提示，中英文同步。实际扣款价格仍由服务端决定。
- 先以失败回归证明缓存、URL、无价格付款及审计异常问题，再实施修复。补充一次性 SQLite 数据库的公告迁移升降级、单例约束和其他表保留验证。

## Alternatives considered

- **每次服务端值变化就重挂编辑器。** 最容易保持一致，但会在后台查询完成时抹掉管理员未保存输入；仅在进入页面初始化前等待新数据，编辑中保留草稿。
- **只禁用页面顶部购买按钮。** 入口处可阻止一次竞态，但不能保护其他页面及已经打开的结算窗口；守卫放在共享结算组件的付款按钮和实际处理函数，不改正常入口布局。
- **继续将所有完整性异常返回 409。** 用户可以统一刷新重试，但把审计故障误判成冲突会掩盖真实故障；只收窄插入冲突捕获，保留原事务回滚。

## Consequences

正常展示与付款流程不变，后台返回页面不会无故使用旧版本，异常路径不再创建未展示金额的订单或误报故障。没有新依赖、线上部署、真实付款、模型调用或共享数据库迁移。完整证据与最终源码散列保存在 `.omx/verification/final-regression-review/`，最终截图在 `.omx/design/final-regression-preview/`；本地模拟不能替代正式环境支付与 PostgreSQL 发布验证。
