# Agent Note: 历史窗口按负载自适应分批读取

Status: implemented

## Problem

历史窗口的 token 预算只限制最终回放内容，不能限制数据库先读入的数据量。`SessionLoader._load_history_window_under_token_budget` 原来每页加载 200 条完整 `ChatMessage` ORM 行，然后逐条格式化、计 token，遇到预算边界再停止。尚未入选的行也已把正文、思考、工具 JSON 和界面 metadata 带入 Python。

只读生产聚合样本的 assistant 消息平均总文本约 309 KB；思考和工具结果占很大比例。staging 合成数据证明，一页载入 200 行而最后只保留 6 行时存在明显的额外分配；但固定改成 20 行会让 300 条小消息的查询从 3 次增至 16 次。

## Decision

默认读取从 20 行开始；需要继续向前翻页时按上一页已加载字符串缓冲的大小调整下一页，最多翻倍、最多 200 行、至少 20 行。使用 `sys.getsizeof` 汇总 `content`、`reasoning_content`、`tool_calls` 和 `message_metadata` 的现有字符串占用，避免为了计量再创建一份 UTF-8 bytes。4 MiB 是控制增长的启发式目标，不是硬内存上限；单行或首批大消息仍可能超过它。

显式传入 `page_size` 时保持固定分页，含原来的 `0 → 200`、负数钳制为 1；省略参数才启用自适应。原有 session/role 过滤、`created_at DESC, id DESC` keyset 游标、逐消息 token 计算、超大最新单条保留、非正预算行为和最终时间升序均不变。formatter 及最终历史字典不改，思考、状态卡、路由和工具面包屑仍完整保留；模型、提示词、历史 token 预算和审稿流程不变。

## Alternatives considered

- **固定每页 20 行。** 最强理由是实现简单，大消息提前停时的读取量直接缩小。未采用，因为小消息需要很多页，300 条历史即从 3 次查询增加到 16 次；几何增长可以减少这些往返。
- **继续每页 200 行，只降低历史 token 预算。** 最强理由是业务代码几乎不变，也能减少最终回放内容。未采用，因为预算不限制已经解码的一整页，而且删减回放会影响写作连续性，与本轮质量约束冲突。
- **按最终 token 数估计下一页大小。** 最强理由是与停止条件直接对应。未单独采用，因为不参与回放的思考和大型工具 JSON 仍会占用内存；可见文本很短的页也可能很重。
- **不加载历史 reasoning 或改存紧凑面包屑。** 最强理由是进一步减少每一行的数据；SDK 最终会丢弃 thinking 块。留待后续，因为需要核对所有历史消费者及持久化契约，本轮只调整读取批次，不改消息内容或存储格式。

## Consequences

- 收益：只需要最近几条历史时，不再先解码整页 200 行；小 payload 可以逐步扩大读取批次，避免固定小页的过多往返。
- 不变：固定 200 行与默认自适应模式在大/小/混合消息、token 边界、相同时间戳跨页、状态卡和工具面包屑场景中返回完全相同的历史字典及标准化 SDK messages。
- 代价：第一页额外几次轻量查询可能提高短消息历史的往返数；300 条全部入选的小消息以不超过 6 次 SELECT 为回归上界。重 payload 会维持较小批次；这里优先减少额外读取，不能同时保证任意历史规模的固定查询数。
- 边界：保留的消息本身仍须占用内存，且字符串计量不包含全部 ORM/驱动开销。这不是硬内存限制，也不能据单次 Python 分配峰值推算 Railway 账单降幅。

## Verification

新增 `tests/test_agent/test_history_read_batching.py`，旧实现的首批大页和隐藏 payload 两项回归先失败。实现后差分比较固定 200 与自适应：覆盖多组 token 边界、非正预算、超大最新单条、显式分页兼容、相同时间戳/ID 排序、session/role 隔离，以及状态卡、路由、思考和工具面包屑。使用真实 SQLAlchemy ORM 装载事件统计读取行数与查询数，不以字符串修改本身作为通过条件。

测试默认使用独立 SQLite；设置 `ZENSTORY_TEST_POSTGRES_URL` 时，每个用例在该测试数据库新建并销毁独有 schema，不触碰共享表。独立本地 PostgreSQL 14 上，新回归、失败/取消历史收尾与会话时间排序共 50 项已通过；生产 PostgreSQL 为 17，发布前仍需最终来源的 CI 与 staging 验证。

候选源码另在 staging 的独立 Python 3.13 子进程中内存加载，与已安装的基线模块做同一份合成数据对照，不替换运行服务：大历史最终 6 条内容哈希一致，读取 200→20 行，Python traced peak 30,986,410→6,985,838 bytes；300 条小消息仍完整一致，SELECT 从 3 次增至 5 次而非固定小页的 16 次。这里没有真实模型调用或应用数据库写入，候选代码也未部署；单次分配下降不能视为整机内存或账单下降。
