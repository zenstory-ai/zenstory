# Bug-fix Note: 去AI味脱敏失败分型

Status: implemented

## Problem

生产日志在一个固定的 48 小时窗口里记录到自然润色 105 次完成请求中有 38 次返回 500，但旧链路只留下通用错误码。模型调用、协议解析、锚点应用、内容保护和退额失败在 API 层被压成同一种异常，无法按 `request_id` 判断失败阶段、固定分类和退额结果。旧退款告警还记录用户 ID 与原异常字符串；异常字符串可能包含供应商响应或正文，不适合作为生产诊断字段。

生产 38 次的底层异常和模型输出不可用。现有证据不能确定它们来自供应商、协议、锚点、截断或其它实现错误，因此本次不能改写协议行为来猜测修复，也不能宣称线上高失败率已经根除。

## Decision

- 保持现有严格协议、精确/歧义锚点和内容保护行为不变。非法标记、半对截断、缺失/多义/重复锚点仍 fail closed；不降级成整篇覆盖，也不自动重试模型。
- 服务把一次润色划分为固定阶段：`model_call`、`protocol_parse`、`anchor_apply`、`content_protection`。失败只向 API 传固定分类，不携带选区、模型原文、用户/项目/文件 ID 或原异常文本。
- `NaturalPolishProtocolError` 在每条现有协议规则产生异常的位置携带项目拥有的固定分类；上层不解析异常文案猜测类型。解析阶段区分空输出、非法标记和 EOF 半对截断；锚点阶段区分缺失、多义和重复锚点。
- API 在退额之后记录一条固定字段的失败事件：阶段、分类、退额是否成功。`request_id` 继续由已有请求上下文自动注入，不新增表、采样器或诊断框架。
- 共享 acomplete 的供应商失败日志也移除原异常文本与 traceback，只保留固定分类、安全类型、数字状态码和既有耗时，避免在服务捕获前泄露原载荷。
- 成本保护 APIException 的 402/503 与错误码保持不变，失败照常只退额一次，不把预算拒绝误记成通用 500。
- 退款自身失败只记录固定 `refund_failed` 分类和固定退款原因，不记录用户 ID、原异常字符串或 traceback。额度仍只预扣一次；失败仍只尝试退额一次。

## Alternatives considered

- **根据合成的某一种模型格式偏差修改解析器。** 最强理由是能让该构造样例从 500 变为成功。未采用：可构造不等于生产 38 次的原因；没有实际证据时改变协议会制造一项与事故未证相关的兼容行为。
- **把所有协议失败当成无改动并返回 200。** 最强理由是作者不会再看到 500，而且原文不会被误改。未采用：这会把截断、非法标记和锚点歧义伪装成成功，也掩盖真实稳定性问题；继续返回失败并退额更诚实。
- **记录原异常与模型输出以便直接定位。** 最强理由是单条日志就可能看出供应商错误或具体坏格式。未采用：异常和模型输出可能包含作者正文、供应商载荷或标识，违反日志最小化；固定分型足以先建立安全的生产分布。
- **放宽锚点为首个匹配，或在失败时整篇覆写。** 最强理由是能显著减少协议拒绝。未采用：重复与归一化碰撞时会改错作者正文，整篇覆写还会绕过逐行格式和内容保护。
- **自动重试一次模型。** 最强理由是随机格式错误可能在第二次消失。未采用：会增加付费调用并使一次记账对应多次成本，也会掩盖失败分布。
- **按异常字符串在 API 层分类。** 最强理由是改动少。未采用：错误文案不是稳定接口，且容易把正文片段带进诊断；分类必须在协议规则产生异常的位置确定。

## Consequences

- 收益：后续生产请求可以按 `request_id` 聚合阶段、固定分类和退额结果，同时不采集作者内容、模型原文或用户/项目/文件标识。
- 收益：非法协议、截断、缺失/多义/重复锚点和内容保护继续 fail closed，原稿不会因诊断改动而被宽松套用。
- 代价：这是一项必要的安全观测改动，不直接降低由未知原因造成的 500；真实修复必须等分型证据指向具体机制后另做最小回归。
- 限制：历史 38 次的真实底层原因仍未知，需要部署后用新的分型统计和受控 staging 合成请求继续验收，不能把本次单元/集成测试当作线上稳定性证明。
