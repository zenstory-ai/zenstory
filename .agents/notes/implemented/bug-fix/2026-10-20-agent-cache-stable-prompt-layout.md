# Agent Note: 系统提示只放跨轮、跨角色不变的内容

## Problem

[项目 ID 后置](2026-10-16-agent-shared-prompt-prefix.md)、[工具协议先于目录映射](2026-10-16-agent-static-tool-guide-prefix.md) 和 [项目目录资料后置](2026-10-16-agent-base-project-data-tail.md) 已让基础提示跨项目共用前缀，但每一轮的系统提示后半段仍随轮次和角色变化：

- `MessageManager.build_system_prompt` 把叙事约束（取自本轮上下文条目）、作者本条消息选的技能、组装的项目上下文、当前文件、任务计划板和本轮回复语言都拼进系统提示。
- `nodes.run_streaming_agent` 再把角色提示（`## 当前角色`）、范围约束、截断续写、篇幅要求和快速模式追加到系统提示末尾。

DeepSeek 按逐字前缀命中缓存，miss 单价是 hit 的 50 倍（`apps/server/services/usage/pricing.py`）。系统提示一变，后面回放的整段历史全部 miss。2026-10-19/20 生产数据：一次 run 的首次模型调用平均 47.6k 输入 token，只有约 12.2k 命中、35.3k miss，占每天 ¥18.9 cache-miss 中的 ¥11.1；同一请求里 writer → quality_reviewer → writer 切换（约 25% 的 run）时系统提示在角色段分叉，历史和上下文再整段 miss 一次，约 ¥3.5/天。

## Decision

- 系统提示只保留跨轮、跨角色不变的内容：项目基础提示、回复语言规则、新增的固定说明「本轮上下文与本次运行指令」、技能目录。`build_system_prompt(session, language, skill_catalog)` 不再接收本轮参数。
- 本轮内容由新的 `MessageManager.build_turn_context` 组装成 `<turn_context>…</turn_context>`，段落与文字和原来相同（叙事约束、作者本条消息选的技能、世界模型可见性合同 + 项目上下文、当前文件、任务计划板、本轮回复语言），开头写明「由系统附上、不是作者写的，项目事实是权威信息，与之前的对话不一致时以这里为准」。`service.py` 把它和工作集、作者改动一起放在本轮用户消息的 `【本轮用户消息】` 标签之前（`SessionLoader.attach_working_set_to_user_content`）。落库与回放的仍是作者原话，`<turn_context>` 不进历史。
- 每个 agent 运行的指令由 `nodes.build_agent_directive` 组装：`[本次运行的系统指令]` + 角色提示 + `## 本轮用户范围约束 [最高优先级]` + 截断续写 + 篇幅要求（writer）+ 快速模式（非审稿人），文字与原来相同。runner 的 `build_run_input` 把它作为这次 SDK 输入的最后一条消息，不写回 `state["messages"]`，所以下一个 agent、下一轮都看不到上一个角色的指令；同一次运行内后续模型调用都带着它，运行内前缀仍然稳定。
- 用 user 角色而不是 system：DeepSeek 的对话模板把所有 system 消息合并到最前面，末尾的 system 消息会重新打断前缀。效力由系统提示里的固定说明保证：`<turn_context>` 与系统提示同等效力；最后一条系统指令按系统提示的效力执行，标注 [最高优先级] 的范围约束高于其他所有规则。
- 上下文与工作集去重沿用现有规则：上下文里以 [全文] 出现的文件，工作集只列一行指向它（提示文字改为指向 `<turn_context>`）。
- 历史预算台账改为系统提示、本轮上下文、工作集各计一次（总量与改动前相同）。
- 不改模型、推理强度、预算、路由、自动质检、计费和退款；不调用付费模型。

模型输入的布局（`|` 之前是跨 agent 共享的前缀）：

```
[系统提示（静态）][历史][本轮用户消息：<turn_context> + 工作集 + 作者原话] | [本 agent 的输出 / 交接消息…][本次运行的系统指令]
```

## Alternatives considered

- **把四个角色提示全部放进系统提示，末尾只写「当前角色：writer」。** 最强理由是角色规则保持系统提示的效力，切换角色时连角色提示也命中缓存。未采用：每次调用都带着另外三个角色的规则（审稿人「不写正文」、writer「写完送审」互相冲突），此前已出现过 writer 把自己当成审稿人反复纠结的事故（`2026-10-10-writer-handoff-reviewer-task-and-length-stop.md`）；角色提示每份约 1–3k 字，按 miss 付一次的代价远小于整段历史和上下文。
- **本轮上下文放在历史之前（系统提示之后单独一条消息）。** 最强理由是上下文不变时，跨轮可以连上下文带历史一起命中。未采用：上下文里有任务计划板、当前文件和本轮语言，而且 agent 每轮都在改上下文里的文件，几乎每轮都会变；放在历史之前会让每轮的历史全部 miss，正是要解决的问题。
- **系统指令用 system / developer 角色放在末尾。** 最强理由是角色语义更强。未采用：DeepSeek 对话模板把 system 消息合并到开头，等于又改了前缀；developer 角色 DeepSeek 不保证支持。
- **保持现状，只靠服务端缓存。** 无行为风险；未采用，理由见 Problem 中的生产数据。

## Consequences

- 离线合成对比（`origin/main` 49ad2234 与本分支，同一套真实 `process_stream` + `run_streaming_agent` 组装，拦截交给 `Runner.run_streamed` 的 instructions + input，按字符比较与此前任一次调用的公共前缀；3 段历史、每轮约 14.5k 字上下文）：
  - 第二轮首次调用：共享 12,653 → 17,860 字（31.5% → 44.0%），多出的部分就是上一轮之前的历史。
  - 同一请求里的 quality_reviewer：74.6% → 91.2%；历史放大到 6 段时 58.4% → 93.1%。
  - 返修 writer：98.6% → 92.4%（6 段历史时 98.9% → 94.0%），因为角色指令现在排在共享前缀之后，每次切换角色都要按 miss 付一次角色提示和范围约束（约 3k 字）；换来的是审稿人不再整段 miss 历史和本轮内容。
  这些是可复用字符范围，不是 DeepSeek tokenizer token 数、实际命中或节省金额；真实效果以发布后的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 为准。
- **历史窗口滑动仍会打断跨轮前缀。** 历史按 32k token 预算从新到旧取，一旦会话历史超过预算，每轮都会丢掉最老的一问一答，前缀在系统提示之后立刻分叉（合成 6 段历史时两份代码的跨轮共享都只有系统提示，约 24.5%）。生产首次调用平均 47.6k token、命中只有 12.2k，说明相当多的会话已经顶到历史预算；这些会话要拿到跨轮收益，还需要让历史窗口的起点按块前移（例如按消息序号量化），这会改变平均加载的历史量，需另行决策。
- **同一请求内 agent 运行之间的回放不是 append-only。** 一次运行结束时 `runner._append_assistant_turn_to_state_messages` 把这次运行折成一条 assistant 消息，下一次运行经 `normalize_messages_for_openai_agents` 只回放其中拼接后的文字（工具调用 / 结果和思考按既有决定丢弃）。所以运行 N+1 的输入在共享的本轮用户消息之后就与运行 N 的后续调用分叉：运行 N 在工具调用之间写出的文字（包括中途流式写出的 `<file>` 正文）在 N 的后续调用里本已命中，到 N+1 被拼成一条消息、两侧没有工具条目，又按 miss 计价；批量写作的逐章续写轮受影响最大。要做到 append-only，下一次运行得逐字回放上一次运行的全部 SDK 条目（含工具调用 / 结果、思考和上一个角色的系统指令），这推翻「不回放工具 JSON」和「返修前去掉审稿任务消息」两项既有决定，并可能重新引入角色混淆，需另行决策，本次不做。
- 本轮上下文从系统提示移到 user 消息，模型对它的重视程度可能变化；通过固定说明和 `<turn_context>` 开头的权威性声明弥补，但结构性测试不能证明生成质量不变，需在 staging 真实生成对比后再判断。角色提示从系统提示末尾移到输入末尾，离模型输出更近，可能比以前更强势。
- 改动发布时所有旧前缀失效一次。

## Verification

- 新增 `tests/test_agent/test_prompt_cache_prefix.py`：(a) 用真实 `process_stream` 跑两轮，断言两轮系统提示逐字相同、不含任何一轮的上下文 / 当前文件 / 任务板 / 本轮语言，`[系统提示][上一轮之前的历史]` 序列化后逐字节是两轮共同前缀，而本轮上下文各不相同；(b) 用真实工作流跑 writer → quality_reviewer → writer，断言三次运行的系统提示逐字相同，`[系统提示][历史][本轮用户消息]` 逐字节共享，角色指令只在各自运行的最后一条、不回流到返修 writer 的输入。
- 受影响的提示组装、语言、技能、首条消息、服务、节点、路由延续、篇幅要求、截断续写、会话加载测试随布局更新断言。
- 不调用付费模型，不修改数据库或生产配置，不发布。
