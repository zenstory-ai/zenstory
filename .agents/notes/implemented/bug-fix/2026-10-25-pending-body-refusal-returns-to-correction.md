# Agent Note: 待补正文被拒后回到纠偏轮；待补期间只能取消那份文件

Status: implemented

关联：[create_file 之后那次回复只能写正文](2026-10-21-fast-mode-summary-and-file-body-turn.md)（本 note 收窄其中「delete_file 除外」的放行范围，旧决定不改写）、[空文件纠偏轮恢复正文捕获](2026-10-24-empty-file-correction-resumes-capture.md)、[工具失败熔断](2026-10-03-agent-tool-failure-circuit-breaker.md)。

## Problem

2026-10-25 生产事故（脱敏取证，源码 `fa1737fc`）：模型建好第 4 份稿件后没写正文，转去建第 5 份、读待补文件，均被 `file_body_pending` 拒绝；随后删除了第 3 份已写好的稿件、同名重建，再重试建第 5 份。全轮 5 次拒绝，其中同参数创建 3 次触发致命熔断，工作中断、留下空稿，被删稿件的 6620 字正文只剩历史版本。程序侧确认三处缺口：

1. 熔断器的顺序性拒绝豁免只有 `pending_empty_file_unwritten`，漏了前置守卫的 `file_body_pending`，同参数第 3 次即熔断。
2. 前置拒绝之后 SDK run 继续发起模型调用，模型盲试到熔断；图已有的待补核验与 `FILE_BODY_RESUME` 纠偏轮从未有机会运行。
3. 待补期间按工具名放行任意 `delete_file`（任意 id、可递归），模型因此删到了别的稿件；前置拒绝不经过工具调用函数，运行摘要 `tool_failures={}`。

## Decision

- **被拒即交回纠偏**：`runner._stop_run_on_control_flow_tool` 在熔断、重复读取守卫、交接/澄清、模型调用预算之后增加一项：本轮某个工具输出是结构化 `status=error`、`error_type=file_body_pending`，且 `ToolContext` 此刻仍有逾期待补条目时，以空 final output 正常结束当前 SDK run（`MESSAGE_END(end_turn)` 带真实用量，不发 ERROR、不另起生成请求）。图随后按既有流程落库核验并经 `FILE_BODY_RESUME` 为同一个文件安排纠偏轮；纠偏轮里再被拒同样结束该轮、消耗既有纠偏配额（2 次），用完走既有回滚/未完成卡。不看拒绝文案或模型文字。
- **熔断分类**：`file_body_pending` 加入 `_ORDERING_ERROR_TYPES`：不参与同参数 3 次规则，仍经 `failure_breaker.observe` 计入请求累计 10 次上限；已到上限照常熔断，熔断优先于纠偏。
- **预算先判**：图的纠偏条件加上 `not run_meter.exhausted and not run_meter.past_wrap_up`，在发 `FILE_BODY_RESUME` 之前判断；不够再跑一轮时直接回滚/报告未完成，不先恢复捕获再停下。模型调用预算在 run 内用完时 runner 本来就以模型调用上限终态结束，这一条是图侧兜底。
- **运行摘要**：前置拒绝在已有 `run_meter` 里记一次固定分类 `file_body_pending`（`rolled_back_batches` 不加、不记首个工具开始；工具没执行，正常执行路径的计数入口不变，不重复计）。日志不带参数、标题、正文或异常原文。
- **删除只放行取消本请求新建的那份待补文件（新决定，收窄 10/21 的放行）**：逾期待补期间 `request_clarification` 照旧放行；`delete_file` 只有参数（与执行路径同一个解析函数）里的 `id` 精确等于某个逾期待补文件、这份文件是本请求新建的（记下了 create_file 结果里的建好版本；复用的已有剧集没有，可能已有正文），且 `recursive` 按 `coerce_bool` 判为假时才执行；别的文件、复用的剧集、递归删除（含父目录）、解析不了或没有 id 一律返回原 `file_body_pending` 拒绝，交回上面的纠偏。只读视图 `_PendingEmptyFileState.overdue_unwritten_files()` 返回精确 `{id, title, created_here}`。不按标题、作者原话或模型解释判断目标。非待补期间的删除不变。
- **取消闭环**：放行的那次删除确实执行成功（结构化 `status=success` 且 `mutation_applied=true`）时，两侧按同一个删除结果收敛：tools_adapter 清除这份文件的待写守卫条目，StreamAdapter 记下 `delete_file` 调用的目标 id、收到删掉自己正在等正文那份文件的成功结果时收尾这份等待（缓冲按既有语义回到对话）并解除绑定。同一 run 之后的 `<file>` 不会落进已删文件，模型接着建下一个文件也不再被已删文件的守卫拒绝；图在 run 边界的 `_probe_pending_file_body`「已删除」核验保留为兜底。删除失败或没确认删掉时两侧都不动。
- **锚点反馈**：`EditBatchError` 的失败项含 `anchor_not_found` 时，在错误末尾补一句：本批所有 new 没有保存，不能当作下一次的 old/anchor；按失败项候选的当前原文重建完整批次，没有可靠候选再用 `query_files` 按 id 读取相关段落。匹配阈值、引号/段落/歧义/并发保护和原子批次不变；`continue_on_error` 的部分成功/全失败路径不经过它。

## Alternatives considered

- **只把 `file_body_pending` 加进熔断豁免。** 最强理由：一行改动，消除同参数 3 次误熔断。被否：模型仍可能盲试到累计 10 次，纠偏轮依旧跑不到，不能证明能补回同一个文件。
- **前置拒绝不计入累计失败上限。** 最强理由：保证纠偏一定先于熔断。被否：放宽了既有总预算；事故并不需要，纠偏配额与累计上限一起才是有界的。
- **在同一个 run 里让模型自己纠正（不提前结束）。** 最强理由：同一 run 里捕获还在等正文，少一次 run 边界。被否：事故里模型正是在同一 run 里接着乱试；纠偏轮有明确指令、经图核验版本与权限，且受既有配额约束。
- **待补期间完全不放行 delete_file。** 最强理由：最简单，彻底杜绝误删。被否：模型发现建错了文件时没有办法撤回，只能等纠偏/回滚；精确 id 非递归取消已足够安全。
- **取消后守卫只在 run 边界由图的「已删除」核验清除（复核计划最初的写法）。** 最强理由：守卫只由图落库核验后改动，路径单一。被否：独立审查复现——取消后模型的下一次工具调用仍被已删文件的守卫拒绝，run 被结束，图核验为已删除后按正常结束往下走（计划交接、送审甚至宣告完成），把被系统打断的一轮当成完成。按真实执行的删除结果收敛两侧，图的核验仍兜底。
- **按标题或作者原话判断要删的是不是待补文件。** 最强理由：模型往往用标题指代文件，作者也可能点名。被否：违反 Agent 语义判断规则，标题可重名，事故里重建的就是同名文件。
- **允许按精确 id 删除任何待补条目（含复用的已有剧集）。** 最强理由：规则更简单。被否：复用的剧集可能已有正文，正是本事故“待补期间删掉已写稿件”的同类。

## Consequences

- 收益：首次拒绝就回到既有纠偏，正文写回同一个 id、只写一次；不再因同参数重试致命熔断；待补期间不会删到别的稿件或整个文件夹；运行摘要能看到这类拒绝。
- 代价：纠偏轮里先调工具也会结束该轮并消耗一次纠偏配额；同一工具批里与取消并发、在删除完成前就被拒的调用，模型要在下一次回复重发（此时守卫已收敛，不会结束 run）。
- 锚点那句反馈只让错误说明更明确，不保证模型遵循；真实失败率是否下降要后续按固定分类观察，不能据此宣称锚点问题已根治。
- 首次为何漏写正文（模型行为）仍未知；本修复只让恢复路径闭环并收窄误删面。

## Verification

- 先写红例，最终测试在基线 `fa1737fc` 上失败 20 项：熔断分类、删除收窄与解析不了的参数、复用剧集不得按取消删除、取消确实删掉后守卫收敛、前置拒绝计数、runner 同步结束；跨层（真实 graph / runner 事件映射与钩子 / tools_adapter / create_file / StreamAdapter / 临时 SQLite，只替换模型与路由）：事故形态首次拒绝即交回纠偏并写回同一 id、同批拒绝 + 删别的稿件、递归删父目录、复用的已写剧集不被删、精确取消后正文不进已删文件、取消后同一 run 建下一份并写完、收尾时间/模型预算在边界用完不先恢复捕获。修复后全部通过；累计 10 次上限、模型调用上限终态优先、纠偏轮每次都被拒用完配额后回滚这几条守护在修复前后都通过。
- 独立审查（三路只读）后的回修：复用已有剧集仍可按精确 id 删除（major）、取消后守卫只在边界清除导致被打断的一轮按完成收尾（major），均先写跨层红例再修。
- 既有用例 `test_resumed_reply_still_refuses_edit_file_before_the_body` 的脚本把“拒绝后写正文”拆到下一次纠偏（断言不变：edit_file 未执行、正文只落一次）。
- 锚点：回滚的 new 当 old 仍被拒、一处不落库，按当前原文重建的完整批次整批生效；partial 既有用例不变。
