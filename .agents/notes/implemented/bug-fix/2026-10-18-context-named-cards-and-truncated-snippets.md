# Bug-fix Note: 点名的旧卡片进入候选，截断文件仍可补检索片段

Status: implemented

关联：[上下文保住角色卡和核心设定](2026-10-08-agent-context-keeps-characters-and-core-lore.md)、[全文标注与工作集](2026-10-08-agent-context-full-text-and-working-set.md)。

## Problem

#270 两处来源覆盖缺口：

1. 自动角色/设定加载 `_get_files_by_types` 先按 `updated_at` 每类各取 10 份，点名加分和重要度排序都发生在这之后。第 11 张卡（作者本轮明确点名，但最久没改）根本不在候选里；高重要度设定若较旧也一样。
2. 预选之后，检索按"已入选文件"的整个 ID 排除。预算不足时长设定只显示前缀（带截断标签），尾部的必要规则无法再从片段检索补入。

## Decision

- `_get_files_by_types` 在原来的"每类最近 10 份"之外，再补最多 10 份被最近窗口漏掉的卡：先选本轮查询里点名的角色/设定（标题作为子串出现在查询中，长度 >= `MIN_QUERY_NAME_CHARS`，与现有点名加分同口径），再选 `importance=high` 的设定。两条筛选都在 SQL 里带 LIMIT、只取 id/标题/类型/元数据，然后在 Python 里按原规则逐个核对（标题中的 `%`/`_` 不会误入），选中的才加载正文。整个项目的正文仍不全量读取。
- 检索只排除**全文入选**的文件。只显示前缀的文件把已显示的前缀传给 `_get_retrieved_snippets`：片段文字已在前缀里的跳过，其余片段照常进入 RELEVANT 档，带原有的"检索片段，非全文"标注。总预算、作者附件/焦点保底、项目隔离不变。
- 不加入向量依赖或事实库，不做全项目全文注入，不在普通日志里记录正文。

## Alternatives considered

- **提高 `limit_per_type`。** 最强理由是改动最小。未采用：只是推迟问题，并成比例增加每次对话的正文读取；点名的旧卡在大项目里仍可能落在窗口外。
- **先取全部卡片的标题/元数据再在 Python 里筛。** 最强理由是逻辑最直观。未采用：大项目每轮多读一整类的行，违反既有"正文查询必须下推 LIMIT"的约束测试；SQL 粗筛加 LIMIT 足够。
- **截断文件按行区间计算未覆盖范围。** 最强理由是更精确。未采用：检索片段不总带可靠行号；按"片段文字是否已在显示前缀中"判断即可防止重复，成本更低。

## Consequences

- 作者点名的旧角色卡、较旧的高重要度设定会进入候选，并继续享受现有点名加分与 CONSTRAINT 分档；仍受总预算约束，不保证全文入选。
- 长设定尾部的相关规则可以通过检索片段补入；片段与前缀可能部分重叠（判断只看整段片段是否包含在前缀里）。
- 每轮最多多两条带 LIMIT 的轻量查询（无查询词时只有核心设定一条）。
