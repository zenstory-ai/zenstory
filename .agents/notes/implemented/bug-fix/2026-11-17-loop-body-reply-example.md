# Agent Note: 单循环写正文示例与「正文回复到 </file> 结束」一致

## Problem

单循环 agent 的两次回复协议要求：`write_chapter` / `create_file` 之后的下一次回复以 `<file>` 开头，写到 `</file>` 结束，不写总结、不调用工具（`agent/prompts/base.py` 第 4 条，见 [单循环 agent](../architecture/2026-11-16-single-loop-agent.md)）。发布后的少量样本里，建好文件后的下一次回复有一部分没有写正文：要么再调一次 `write_chapter`（被 `file_body_pending` 拒绝，run 结束后靠纠偏 run 补写），要么只给了一段被当作协议残片丢弃的短文字。每次多一段长思考和一次补写，第一次保存正文明显推迟。

同一段提示词里的示例与第 4 条相反：第 2 次回复在 `</file>` 之后紧接着 `write_chapter` 下一章，第 3 次回复在 `</file>` 之后写总结。这是多 agent 图时期「同一条回复写完上一章再建下一章」的批量写法（[2026-10-21](2026-10-21-fast-mode-summary-and-file-body-turn.md)），单循环已不再使用，示例没有跟着改。

## Decision

- 示例改成每次正文回复都到 `</file>` 结束，之后是「（系统发回保存结果和字数）」，下一次回复自查后再调用 `write_chapter` 写下一章，最后一次回复才写给作者的总结。规则文字不变，不加检测或拦截代码；`file_body_pending` 拒绝与空文件纠偏仍是兜底。
- 不为这段提示文字加镜像测试。

## Alternatives considered

- **建好文件后的那次模型调用设 `tool_choice="none"`。**（供应商确认后已在 [2026-11-17 正文回复不提供工具调用](2026-11-17-loop-body-reply-without-tools.md) 采用，下面是写这条记录时的判断。）最强理由：在请求参数上让模型无法跳过正文去调工具，覆盖上面第一种失败；2026-10-21 否决它的理由（批量写作需要同一回复里写正文再建下一个文件）在单循环里已不成立，工具清单不变也不影响前缀缓存。暂不采用：这一改动对故障转移列表里的每个供应商都生效，DeepSeek 文档写明支持 `none`，MiniMax 的 OpenAI 兼容接口文档没有列出 `tool_choice`，社区接入记录里还有它对 `tool_choice` 报参数错误（2013）的情况。若被拒，每一次写正文都会失败；若被忽略，则对主供应商无效。需要先用每个供应商各一次最小真实请求确认，再单独合入。它也拦不住第二种失败（短文字被当成残片）。
- **按回复内容判断模型是不是在写开场白然后补救。** 违反不用文本启发式判断意图 / 完成的规则，不采用。

## Consequences

- 收益：示例不再教模型在正文回复里调工具或写总结，与规则一致；不增加请求、不改变工具与计费。
- 代价：这是软约束，效果要靠发布后按同一口径复查（`file_body_pending` 拒绝次数、每个新建正文的纠偏 run 次数、被丢弃的协议残片、建文件后下一次调用是否仍返回工具调用、`first_output_ms`）。样本足够后若仍明显高于图时期，再在确认供应商兼容后推进 `tool_choice="none"`。（后来已在 [2026-11-17 正文回复不提供工具调用](2026-11-17-loop-body-reply-without-tools.md) 采用。）
