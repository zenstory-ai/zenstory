# 质量模式降本：篇幅容差，以及已附正文不再重读

Status: implemented

关联：[作者交付要求与篇幅原话](../feature/2026-10-14-writer-delivery-author-requirements.md)、[送审与返修附正文](../feature/2026-10-19-review-and-rework-handoff-text.md)、[只给作者一份总结与送审证据](../bug-fix/2026-10-11-author-reply-single-summary-and-real-word-counts.md)、[自动质检门](../bug-fix/2026-10-08-agent-review-gating-and-handoff-details.md)。

## Problem

生产 24 小时（截至 2026-10-20）DeepSeek 费用约 ¥44，246 次运行全部是质量模式。58 次触发自动审查，其中 44 次（76%）交回 writer 返修。返修理由大多是真实的连续性问题，所以审查保留；但审查加返修每天约 ¥11，其中有两类浪费与审查质量无关：

1. **追字数。** 1191 段思考里有 153 段（13%，分布在 72 次运行里）在调篇幅。一次返修 writer 为把一章从 3377 字削到 2899 字，连续调了约 25 次 edit_file，每次只删几个字（「2905，还多 5 字」），每次调用都重发约 10 万 token 的上下文。作者说「约 3000 字」本来就是约数；提示里只写「写够」「没达到篇幅要求就返工」，没有定义多少算达标，模型只能逐字逼近。
2. **重读已经附上的正文。** 返修 writer 段共 57 次 query_files、17 次 parallel_execute，对应 109 次 edit_file。#275 之后返修交接已附上「[返修对象当前正文]」，但 writer 提示仍要求「写完用 query_files 读一次核对 word_count」，返修多文件时 9000 字预算又平分给审稿意见没提到的文件，导致要改的那章只剩片段。送审包里每个文件的来源行都写着「省略内容用 query_files 读取后再核对」，即使全文已经附上。重读的结果是新的工具输出，不能命中前缀缓存。

## Decision

### 1. 篇幅容差（程序换算 + 提示规则）

- `review_evidence.length_requirement_bounds` 把一条篇幅原话换算成达标区间（`LengthBounds`）：单个目标数（「约2000字」「3000字左右」「扩写到3000字」）为目标 ±15%（`LENGTH_TOLERANCE`）；作者给了范围（「500-900字」）或明确上下限（「不超过3000字」「3000字以内」「至少2000字」「1000字以上」）时那一侧是硬要求、不放宽。上下限用语只看数字附近（「以下是要求：每章2000字」不算上限）。多个数字、「三千多字」「三四千字」这类说不清的不换算，只给原话。
- `find_length_requirements` 在原话后面附上区间（「「单章约2000字」（本轮原话） → 达标区间 1700–2300 字（目标 ±15%）」），送审的 `[作者的篇幅要求]` 和开写前的篇幅指令都用它。仍不判断说的是全篇还是单章，那由读原话的角色按上下文判断。
- `AUTHOR_DELIVERY_REQUIREMENTS`（writer 与审稿人共用）加一条：按达标区间判断，区间内不是缺陷、不返工；需要增删时每章一次改写到位（补写一次补足新情节，删减一次删整句或整段并留出余量），不逐字微调、不为差几个字反复 edit_file 或重读。审稿人的客观缺陷与「篇幅不足」返工说明同步改为「超出达标区间」。
- writer 核对字数只看工具结果：edit_file 的 `new_word_count` 就是改后全文字数；刚流式写完的文件用 `query_files(id, tail_chars=200)` 取整份的 `word_count`，不为一个数字读全文。

### 2. 返修 writer 不重读附上的正文

- 返修交接的「[返修对象当前正文]」按审稿人交回的意见聚焦：`_collect_review_payload_text(focus=…)` 只附意见里点到（标题或文件 id）的文件，其余写成一行「审稿意见没有提到《…》，没有附上，不用改也不用读」；一个都没点到或只有一个文件时照旧全附。批量写的多章不再平分 9000 字预算，要改的那章能整章附上。
- 交接头与 `WRITER_PROMPT` 的返修条款写明：附上的就是这些文件现在的正文，直接逐字引用作 edit_file 的 old/anchor，不再用 query_files / parallel_execute 读它们，也不为核对字数再读（看 `new_word_count`）；要改处不在附上的片段里时只按章节读那一段。陈旧检查不变：作者在期间改过文件，edit_file 照旧拒绝。

## Alternatives considered

- **只在提示里写「±15%」，不做程序换算。** 改动最小。未采用：模型每次都要自己从原话里找数字、换算区间，正是这些计算在思考里反复出现；区间由程序算好附在原话后面，审稿人和 writer 拿到的是同一个确定的数。
- **程序直接判定「达标 / 不达标」并跳过篇幅返工。** 最省一步。未采用：原话说的是全篇还是单章、本轮写的是哪几章，只有读上下文才能判断（原决定也刻意不把原话换算成结论）；换算区间不替角色下结论。
- **返修交接把每个文件的全文都附上（加大预算）。** 返修 writer 永远不用读。未采用：长合集和多章批量会让这条 user 消息变得很大，而且大部分正文与审稿意见无关；按意见聚焦能在原预算里把要改的那章附全。
- **给 query_files 加跨角色的重复读取拦截。** 能硬性消除重读。未采用：#275 已说明接收角色没看过别人的工具结果，把附上的片段当作看过全文会让模糊匹配建立在没看过的正文上；这里只给正文和指引，不拦截确有需要的范围读取。
- **把硬上下限也放宽几个百分点。** 能进一步减少追字数。未采用：作者写「不超过3000字」是明确要求，放宽等于改作者的要求；容差只给本来就是约数的单个目标数。浪费靠「一次改写到位、留出余量」解决。

## Consequences

- 约数目标在 ±15% 内不再触发篇幅返工，也不再被逐字逼近；明确上下限照旧严格。审稿与返修轮数上限、计费、模型与 reasoning effort 都不变。
- 返修 writer 在常见情形（一章或审稿只点到几章）下拿到要改的整章，不需要为引用或字数再读；审稿意见用了和文件标题不同的叫法（「第3章」对「第三章」）时匹配不上，退回全附，不比以前差。
- ±15% 是产品取舍：作者说「约2000字」而交付 2290 字现在算达标，以前审稿人可能要求删减。
- 节省幅度只能上线后用生产数据确认（篇幅相关思考段数、返修段的 edit_file / query_files 次数、每日费用）；本批只有合成数据的单元与图测试，没有调用付费模型。
