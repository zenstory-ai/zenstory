# Unified quota query cache

## Problem

同一个 `GET /api/v1/subscription/quota` 响应在前端使用 `subscription-quota` 和 `quota` 两套账号级 React Query key。额度徽标、首页阻断、素材入口和通用额度 hook 因此不能共享请求与缓存；聊天结算、退款、离页刷新和去 AI 味结束时还会分别失效或回写两套 key。两个请求返回相同合同，重复缓存没有产品语义。

## Decision

`quota()` 和兼容导出 `quotaLite()` 共同返回 `['subscription-quota', accountId]`。所有 observer 直接复用 `subscriptionApi.getQuota` 的规范 `QuotaResponse`，不再为旧测试 mock 在某个 hook 内制造另一种缓存形状。聊天、去 AI 味、离页结算和积分兑换 Pro 只失效一次统一缓存，确认退款也只乐观回写一次。账号 ID 继续来自原有缓存作用域，不同登录账号不会共享额度数据。

保留原有刷新时机：AI 开轮预扣完成、正常结束、错误、确认退款、去 AI 味结束和离开生成中的页面仍会重读服务器真值。首页的 `refetchOnMount: "always"`、徽标的 60 秒轮询、北京时间重置、Pro 规则、预扣和退款语义均不改变。

## Alternatives considered

- **保留两套 key，只把部分刷新节流。** 最强理由是改动更少，也避免影响依赖旧 key 的调用方。被否：同一响应仍会产生两份缓存和并发请求，每个结算入口也必须长期维护双失效，遗漏时会显示不一致的额度。
- **删除 `quotaLite()` 导出并一次性改完所有测试和潜在调用方。** 最强理由是 API 更干净。被否：兼容别名没有运行成本，保留它能让分支和外部引用平稳迁移；运行时已共享同一个 key。
- **降低徽标轮询或取消首页强制重读。** 最强理由是还能进一步减少请求。被否：离开长任务后的异步退款需要这些既有兜底，本批优先消除确定的重复请求，不改变作者看到最新额度的可靠性。

## Consequences

同账号同时挂载多个额度消费者时，React Query 合并为一个在途请求；一次失效会更新所有消费者。确认退款仍先把缓存恢复到开轮前基线，再重拉真值纠正跨设备使用。代价是旧代码若只失效 `quotaLite()`，现在会失效统一缓存；这正是兼容别名的预期行为。回归测试覆盖多消费者请求合并、账号切换隔离、聊天预扣/退款回写、去 AI 味刷新和离页延迟刷新。
