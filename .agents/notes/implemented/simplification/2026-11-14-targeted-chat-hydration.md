# 收尾消息按已知 ID 读取

## Problem

前端在流结束后给本地 assistant 消息补充后端 ID、反馈和时间。已有 `assistantMessageId` 时仍请求最近 50 条完整消息，再在浏览器中按 ID 查找；旧正文和工具结果也会随之传输。初次加载历史、没有后端 ID 的恢复和 CLI 等消费者仍需要原有历史接口。

## Decision

在现有 `GET /chat/session/{project_id}/recent` 增加可选 `message_id`。先按原流程核验项目权限、解析当前用户的活跃会话，再在这个会话内用 ID 过滤，最后排序和限制数量。不改响应字段和默认历史查询。

前端只在收尾元数据已给出 assistant ID 时增加查询参数，保留 `limit=50`。旧服务器会忽略未知参数并返回原有窗口，前端仍按精确 ID 匹配；新服务器最多返回一条。没有 ID 时仍走原来的窗口与匹配规则，不新增请求、重试或模型调用。

八项 ASGI 回归覆盖 ID 过滤在 limit 前、缺失/归档/其他会话 ID 返回空列表、项目越权仍拒绝、空/过长 ID 校验，以及默认窗口和排序。客户端与组件回归覆盖编码、AbortSignal、按已知 ID 查询、旧服务器返回多条仍精确匹配，以及无 ID 的原路径。后端相关 45 项、前端两个文件 182 项测试通过；TypeScript 与相关 lint 通过。

## Alternatives considered

- **单独增加消息回执接口。** 响应可只含时间和反馈，体积更小；但需要新增路由、响应类型和旧服务器 404 回退。现有接口增加可选 ID 筛选就能消除本批最明显的无关历史传输。
- **将收尾查询固定改成最近一条。** 改动很少，但并发写入、重连或切换时最新消息未必是目标消息，不能把顺序当消息身份。
- **减少默认历史条数或删除正文/工具字段。** 能减少其他调用的响应，但会影响历史恢复和现有客户端，不属于本批范围。

## Consequences

有消息 ID 的收尾查询由最多 50 条缩为最多一条，减少无关数据库读取、序列化与公网响应。没有 ID 或旧服务器保持原路径；发送给模型的上下文和缓存不变。不把单条数改善外推为全站 egress 的固定降幅。
