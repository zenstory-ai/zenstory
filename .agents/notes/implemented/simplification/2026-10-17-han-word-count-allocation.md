# 汉字计数只保留固定窗口内的临时匹配

## Problem

本地真实 Agent/SSE 大文件重放中，字数统计把每个汉字的正则匹配字符串全部放入列表，只为读取列表长度。786,433 汉字的四处顺序统计各产生约 53.5MB 临时对象，整轮分配峰值约60MB。请求结束后未发现按正文大小持续持有的泄漏，SSE 队列也不是这个峰值的主要来源。

## Decision

已仅调整 `utils.text_metrics.count_words` 的汉字计数：对现有单码点正则按4096个 Python 字符的固定窗口执行原 findall，再相加匹配数。窗口只约束临时列表的生命周期，不截断、抽样或忽略任何正文。正则 U+4E00..U+9FA5、连续 ASCII 拉丁字母计一个词、数字/符号不计，以及空输入返回0的定义均保持。[原字数口径](../bug-fix/2026-10-09-agent-word-count-matches-editor.md)。

拉丁词仍一次扫描整段，避免跨窗口长单词被拆成多个词。不改作者语言检测、提示词、正文/历史/SSE 输出、存储或额度/取消流程。不增加 helper、缓存、配置项、依赖或通用分块框架。

## Alternatives considered

- 对两个正则都用 finditer：代码更短、额外内存接近常量；但真实本地整轮无 tracing 耗时增加35%（约121ms），放弃。
- 用 subn 的替换次数计数：部分密集输入 CPU 更快；却生成不需要的重写文本，在混合 Unicode、单字母间隔和稀疏汉字/emoji 输入显著增加内存，放弃。
- 移除重复 history_buffer：确实减少文件生成中途约1.56MB持有；但整轮峰值不变，留作独立候选，不混改。
- 作者语言检测也同改：理论上能省列表；实测当前作者消息只增加约1.4KB，且它有不同字种/词长规则，不扩大本批范围。

## Consequences

固定窗口增加一个短循环，但保留原生正则 findall 的计数速度，避免每个汉字都经 Python Match 迭代器。4096是局部分配窗口而非业务限额，没有增加可调设置。密集拉丁文本的原列表开销仍保留，不声称所有输入都减少内存。整段正文仍全部计数、保存、发送，不改变上下文、输出或已有保护。
