# Agent Note: 项目资料快照、统一工具清单与锚定历史窗口

Status: implemented

关联：延续 [cache-stable prompt layout](../bug-fix/2026-10-20-agent-cache-stable-prompt-layout.md)（那份记录把随轮变化的内容移出了系统提示）。

## Problem

生产账本（2026-10-20 15:11 之后）：写作 Agent 每轮第一次模型调用只命中 28% 缓存（平均输入 6.5 万 token，命中 1.8 万），同一轮里之后的调用命中 90% 以上。抓取真实请求逐条比对后，跨轮前缀在三处断开：

1. **工具清单按角色、按轮次变化**：writer 11 个工具，审稿人 6 个；只读、先问清楚的轮次还会给写工具描述加前缀。工具清单在请求里排在对话之前，一变就只剩系统提示前面一小段能命中（实测降到约 6.5k token）。
2. **历史窗口每轮滑动**：历史超出预算后，窗口每轮从最旧处丢一条，[系统提示] 之后的前缀每轮都不同。
3. **每轮的项目上下文与工作集每轮重建、放在历史之后**：组装的项目资料（角色卡、大纲、前文……）与上两轮读写过的文件全文，大部分内容轮与轮之间并没有变，却因为位置在历史之后、每轮重新生成而从不命中，生产上每轮约 4.7 万 token。

## Decision

1. **统一工具清单**（`tools/registry.py` `EXPOSED_TOOL_NAMES`、`openai_agents/tools_adapter.py`）：每个角色、每一轮发同一份工具清单，顺序与描述都不变。角色权限与只读 / 先问清楚改在调用时检查（越权返回 `error_type=tool_not_permitted_for_role`，只读照旧 `read_only_request`），不可用说明写进这次运行的系统指令（`## 本轮工具限制`），它是输入最后一条消息，不影响缓存。
2. **锚定历史窗口**（`core/session_loader.py` `anchor_history_window`）：按预算截断后，窗口起点只落在锚点 user 消息上（会话序号每 8 条一个；没有序号时按 id 哈希兜底），只在窗口较旧的一半里找，最多让出半个窗口。起点因此停在同一个锚点上几轮，再整段跳到下一个，而不是每轮滑一条。
3. **项目资料快照**（`context/turn_snapshot.py`）：
   - 组装器（`ContextAssembler._format_context_with_blocks`）和工作集（`SessionLoader._build_working_set_context(parts_out=…)`）都按条目给出带键的块（项目状态与文件清单一块、每个条目一块、工作集每个文件一块；工作集块不带「上一轮已修改」这类每轮都变的标注，标注留在每轮的清单里）。
   - 会话第一轮把这些块渲染成 `<project_snapshot>`，作为模型输入的第一条消息，紧跟系统提示、在历史之前（`runner.build_run_input`）；它只进模型输入，不写回 `state["messages"]`。
   - 之后每轮只把新出现或内容变了的块放进 `<turn_context>` 的「本轮更新的项目资料」（声明以这里为准），工作集只发清单。
   - 在快照里、但本轮上下文已不再包含的块（焦点移走的章节、上一轮工作集里的文件）本轮不会核对：`<turn_context>` 里另起「本轮未核对的快照条目」逐条列出（块带 `label`，即标题和 id），说明快照里的 [全文] 与「← 当前焦点」标记可能已过期、需要时先 query_files（2026-10-25 审计 F-08：原先这些块最多留 20 轮 / 2 小时，模型会把过期正文和旧焦点当成最新）。这些块的大小也计入重建比例。为此快照状态多存每块的大小与 label，格式版本升到 2（上线时每个会话重建一次）。
   - 快照存 Redis（有 `REDIS_URL` 时，API 进程间共享），否则进程内存；丢了只是重建一次。改动与离开本轮的块累计超过快照一半、用满 20 轮、超过 2 小时、或项目 / 语言 / 格式版本变了时重建。
   - 请求布局：[系统提示][项目资料快照][历史（到上一轮）][本轮上下文（只含改动）+ 作者消息][本次运行指令]。
   - 组装失败等没有分块的上下文整段作为一个块，不会在快照路径上丢失；「原始上下文是否完整」按整份上下文判断。
   - 组装器的整段 context 与 blocks 逐行一致：原先「相关内容详情」段头和 `FULL_TEXT_CONTEXT_NOTICE` 只写进整段 context、不在任何块里，快照路径上从未送到模型，却仍从条目预算里预留开销（2026-10-25 审计 F-31），已删除。[全文] 的读取约定只保留在系统提示（`prompts/base.py`）里。

## Alternatives considered

- **把上一轮发过的上下文原样留在历史里，只追加本轮的差异**。最强理由：不需要额外存储，历史天然是前缀。被否：历史里会堆积每轮的旧资料，32k 的历史预算很快被占满，窗口跳动时最前面的那一轮只剩差异、缺少它所基于的全文。
- **把整段本轮上下文挪到系统提示之后，不做差异**。最强理由：实现最简单，项目资料开头相同的部分能按前缀命中。被否：任何一处变化（新建文件、刚写的章节）都会让它和后面的整段历史一起失效，写作轮几乎每轮都会变。
- **只修工具清单和历史窗口，上下文不动**。最强理由：改动小、风险低。被否：每轮约 4.7 万 token 的项目资料仍然全部按未命中计价，是剩下最大的一块。

## Consequences

- 收益：跨轮能命中的前缀从「系统提示 + 部分工具」扩展到「系统提示 + 工具 + 项目资料快照 + 到上一轮为止的历史」；审稿人、只读轮与写作轮共用同一前缀。
- 代价：快照可能带着本轮没选中的旧条目（命中缓存、很便宜，但占上下文长度；本轮会把它们列为未核对，体量大时触发重建）；改动过的文件在快照与「本轮更新」里各出现一次，模型要以更新为准（快照与本轮上下文的说明都写明了）。
- 代价：历史窗口按锚点对齐，截断时最多少留半个窗口的旧消息。
- 代价：审稿人现在能看到写工具（调用会被拒绝并经熔断器记账）；多一次 Redis 读写；快照跨进程不一致时（Redis 不可用）只是缓存命中变差，不影响正确性。
