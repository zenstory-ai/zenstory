# 项目快照只保存稳定资料

## Problem

生产快照日志与 MiniMax 写作用量账本按任务 ID 对齐后，复用快照的首轮输入命中率为 43.1%，内容变化触发重建时为 6.8%。工作集全文和章节正文占重建时新增或变化字符的约 85%。它们位于聊天历史之前，换章时会连带打断原可复用的历史前缀。

## Decision

在现有快照与本轮上下文之间重新分配资料。项目简介、写作风格、写作约定和不随焦点变化的设定继续使用快照；正文、焦点和本轮引用等资料随当前消息发送，文件清单和当前阶段独立于稳定资料。工作集使用已有的独立渲染，保留其全文、提示和读版本记录。升级快照格式，条目指纹使用 SHA-256，沿用现有快照重建条件和统计。

组装器按 token 预算选好条目并标明全文或节选。渲染本轮消息时沿用这些边界，保留正文、作者引用和写作约定的更新；全文读取记录也使用同一套条目标记。旧快照里的条目移到本轮时，本轮版本有效，快照里的旧副本仍计入重建阈值。

## Alternatives considered

- 提高重建阈值能用一个参数减少重建。实际重建样本里旧快照中未核对或变化的字符占比中位数为 81.4%，延迟重建会反复发送大段旧正文。
- 每轮都只发送新资料能避免过时的副本，也能简化状态管理。代价是稳定资料位于变化的历史之后，较难跨轮复用。
- 保留渲染器的字符上限可以拦住异常大文本，但字符数与 token 数没有固定比例，预算内的正文也可能被切掉，连同尾部的写作约定更新一起丢失。由组装器控制条目预算，渲染时保留条目边界。

## Consequences

换章或更新工作集时，稳定资料与共同历史能保持字节一致。相同的动态资料在不同请求中可能需要重新按未命中计价，同一请求仍可复用该请求的前缀。对于稳定资料很少的项目，项目简介、文风或约定的更新更容易达到重建阈值，重建会移除旧副本，但该轮的共同历史也会重新计入未命中。旧格式快照在下一轮更新。实际缓存收益以线上首轮未命中 token 为准。
