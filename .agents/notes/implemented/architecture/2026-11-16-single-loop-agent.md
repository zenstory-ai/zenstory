## Problem

一轮对话要经过路由 → 规划 / 写作 / 审稿多个角色、计划交接和自动送审。问题集中在三处：

- 成本和延迟：送审与返修约占 agent 花费的一半（见 2026-10-20 记录）；每次换角色都从折叠后的历史重建输入，读过的文件要重读，前缀缓存在角色之间断开。
- 跨轮记忆：历史只按 32k token 取最近窗口，工具结果不跨轮回放，靠面包屑和工作集补救；长对话里作者早先的要求和纠正会掉出窗口。
- 复杂度：路由合同（read_only、scope_constraints、turn_disposition、clarify_first……）、交接包、CHAT_HOLD、计划补写、送审证据等分支层层叠加，每个修复都要兼顾多角色组合，回归面很大。

对同一组写作任务做的对照里，一个模型带写作工具、一份只追加的对话、几条工作方式规则，交付质量不低于多角色流程，成本和耗时更低。

上线前又用一段多轮写作会话做了盲评回放（同一组作者消息分别由不同流程重放，评审不知道来自哪一种），暴露出整章写入的问题：

- 提示规则「同一章已有文件时用写文件 / edit_file 改它，作者给出的稿子整体替换进该章」下，多数回放里模型把整章稿子写进了别的章节的文件（作者已有的章节被覆盖），回复里却说新建了文件。目标文件靠模型自己挑，提示约束不住，程序也无法核验。
- 改成按章号定位的写入工具（这一章不存在就新建、存在就只替换这一章，结果写明是新建还是替换、原来多少字）之后，同一组回放里单循环在盲评中明显胜过多 agent 流程。
- 实现接入真实服务后，同一组回放的盲评里它先输给了多 agent 流程（文笔与忠实度），原因是正文写在回复文字里、`</file>` 之后模型直接写总结，从不自查；把 `</file>` 之后的续跑改成带落库字数的自查说明后，盲评转为明显胜出。
- 剩下的问题：一次 edit_file 往章节里插入了一段重复的文字；后面章节才出现的人物和揭示提前写出、而这一章大纲要求的关键事件被换成了别的；长会话里作者给的稿子被另存成素材副本；回复里报的字数不是工具结果给出的。

## Decision

所有聊天轮次改由一个循环 agent 完成（`apps/server/agent/loop/`）：

1. **引擎开关**：`AGENT_ENGINE=loop|graph`，默认 `loop`，只作运维回滚；图的代码暂时保留，`loop` 时不运行，之后单独一批删除。没有灰度和过渡档位。（2026-11-17 起图已删除、开关不再读取，回滚改为从 git 检出，见 [remove-graph-agent](../simplification/2026-11-17-remove-graph-agent.md)。）
2. **接入点**：`AgentService.process_stream` 里同一个生成器接口。SSE 外壳、`/stop`、`/steer`、`/suggest`、计费 / 预扣 / 退还、停止终态回执、残稿补存、文件版本并发保护、作者正文保护、草稿保护都沿用。单循环 agent 落库的 `display_events` 只用 content、thinking_content、tool_call、iteration_exhausted，`routing` 为空，现有前端能直接渲染；旧会话照常加载。
3. **工具**：写作工具集去掉 `handoff_to_agent`、`parallel_execute`、`request_clarification`（需要作者回答时在聊天里问）。保留 create_file + `<file>` 正文协议（实时打字与 diff 审阅）、edit_file、query_files、update_project、load_skill / read_skill_resource、delete_file、rename_file，另加只有单循环 agent 有的 `write_chapter`。
4. **正文按章号写入**：
   - `write_chapter(chapter, title, file_type=draft|script, parent_id?, empty?)` 在本项目未删除的正文类文件里，按标题开头的章号（draft）或集号（script）解析目标；复用标题序号解析器，只认「第N章 / 第N集 / Chapter N / Episode N」这类开头，是有界的标识符检查。给了 parent_id 只看那个目录，查找前按 create_file 的同一套规则归一（非 folder 的父节点上挂到最近的 folder 祖先，剧本项目里的 `-draft-folder` 退到分集目录），查找与新建落在同一个目录；标题里的编号与 chapter 不一致时拒绝；标题没写编号时补上。
   - 没有这一章：走 create_file 的新建路径，下一次回复以 `<file>` 写正文。两次回复协议、待写守卫、空文件纠偏与回滚、退还时移除空白占位、计费与回合回执都照旧。
   - 恰好一个：定为整章替换目标，定位时不改数据库，记下当时的版本和原长度，同样等下一次回复的 `<file>`。待写守卫上记下这是替换（与本请求新建的空文件分开）：同一回复里再次 write_chapter 这一章时拒绝（`chapter_replace_pending`），不会把已有的整章当成新建的空章节走新建写入。正文写完后 StreamAdapter 用 `FileEditor.replace_body` 提交，与 edit_file 共用同一条提交路径：写锁内重读、版本核对、原稿备份、AI 版本、撤销锚点。随后发 `file_edit_start / applied / end`，end 带原稿与新稿，前端进入逐段 diff 审阅；再以同一个 tool_use_id 补发一条结果（是否保存、真实字数、原字数、撤销锚点），落库的卡片与撤销接口都用它。
   - 定位之后这一章又被保存过：不覆盖，告诉作者原文保持不变，并结束这一轮（正常结束，不是错误）：模型还在同一次回复里往下写，接着的话会当作已经换好，这些话不发给作者。模型跑在前面已经建好、作者还没看到的空文件随之撤销。没写完的 `<file>`（截断补全、中途停止）按既有覆盖保护不覆盖原文；run 结束时没写到 `</file>` 的那一次在纠偏次数内为这一章恢复捕获重试，补不成就作废定位，续跑说明如实说原文没动，不说已保存、不列原稿字数；同一章重新定位后又没写完时照样再说一次（是否已保存看 StreamAdapter 提交成功后记下的结构化事实，不看模型的文字）。
   - 作者保存过正文（或来源无法确认）的章节，定位时就拒绝，提交时在锁内再核验一次，沿用「应用内对话不整份覆盖作者保存的正文」。
   - 不止一个文件对应这一章（重复的章节文件，或没给目录而多卷同号）：不写，列出候选。正文分在几个目录里（分卷常各自从第1章编号）而没给 parent_id 时，唯一的同号章节也不当替换目标，要求指明目录。`empty=true` 只建缺的空章节，已有的不动。
   - 工具结果写明是新建（created）还是替换（replaced，附原来的字数），字数来自落库结果。计费与 create_file 同口径：新建的空章节不算产出，正文随流式内容计入；替换只认落库后补发的结果（`body_saved` 且 `mutation_applied`），正文到来之前停止或出错的轮次照常退还并移除空白占位；替换目标（定位结果 `action=replaced` 且原文非空的文件 id）的流式正文不算写入，正文流到一半时停止、断线或撞上请求时限，原文不变，这一轮同样退还；原文为空的已有章节没有要保护的正文，中途停下时流过的正文照常落库，也照常按流式正文计费；正文已写到 `</file>`、整章替换正在提交时被截停，线程里的提交不随取消中止，收尾时等它的结果写进保存回执，结算按回执补记写入（断线路径在后台等回执再决定退还），不会出现章节已经换掉却退还的情况。
5. **正文边界**：单循环轮次里 create_file 不建 draft / script，按 create_file 实际会建的类型判断（剧本分集目录下标题带集号的 document 会被归一成 script，同样拒绝），错误指向 write_chapter；请求里给单循环 agent 的 create_file 说明不列这两类。同一批早先的同章守卫（create_file 拒绝为已有章号再建正文、指回已有文件让模型用 edit_file 改）由 write_chapter 取代。edit_file 改 draft / script 时在提交前做两道逐字结构检查，不判断语义：
   - 一处 replace 的 old 就是整份原文，或这次只有一处 replace、原文有两段以上而改完一段都没留下：拒绝，整章重写走 write_chapter。几处各自定位的小改动（逐段润色、统一标点）即使碰到了每一段也不拦：作者保存过的章节不能经 write_chapter 替换，逐段修改是它唯一的路径。
   - 改完后有一段（至少 80 字）逐字出现两次以上，而改之前它没有重复：拒绝。原文里本来就重复的段落不受影响。
   - 两种拒绝都整批不落库。资料文件与图的各角色不受影响。
6. **写权限**：不再有路由给出的 read_only / scope_constraints；是否改文件由模型按提示判断，每次写入照旧经过 diff 审阅、撤销与版本保护。create_file 的 `empty=true`（只建空文件）由模型判断，单循环轮次里直接生效。依赖路由的 `requested_body_write` / `no_file_changes` 回执在单循环轮次里不出现，不从文字推断。不加任何关键词或正则意图判断。写作约定（notes）的追加许可在单循环轮次里放开，由模型按提示只在作者要求时追加，只追加、不删改和 `expected_notes` 冲突保护不变。
7. **提示词**：项目类型的 SystemPromptConfig 行 + 共享协议（去掉多角色、交接和并行一节）+ 工作方式规则（来自对照实验的规则，并把原快速模式指令里的写后连贯自查、按真实字数汇报搬进来，不提模式）。系统提示跨轮不变。
   - 工作方式规则：正文按章写，新的一章或整章重写用 write_chapter，只改几处用 edit_file，作者给出的某一章稿子用 write_chapter 写进那一章。作者给的稿子直接写进对应章节，不另存成素材、副本或备份。大纲是节奏的上限也是底线：后面章节才出场的人物、才发生的事件和揭示这一章不写，大纲要求这一章发生的关键情节必须写到；作者改了大纲以作者为准并更新大纲文件。写后自查同时核对关键情节有没有写到。写新的一章（一集）之前，已有大纲按章（集）逐条列出却没有这一章的条目时，先照大纲已有的写法补一条几行的条目（关键事件和转折、这一章还不能揭示的内容）：大纲是一份文件就用 edit_file 补进去，一章一份大纲文件就照已有文件的命名和位置新建一份；分多章写的作品还没有任何大纲文件时，在大纲目录新建一份「分章大纲」，先只写这一章的条目（产品负责人要求：沿用图时期写正文前先写对应大纲的做法）；再写正文。重写已有章节、写进作者自己给出的章节稿、大纲只按卷或阶段粗列、只有一篇正文的短篇、作者说不用写大纲时都不补。这条条目算写这一章的一部分，不受「只改作者点名的文件」限制。正文落库后的续跑说明（`_BODY_SAVED_CONTEXT` / `_BODY_RESAVED_CONTEXT` 及英文版）和 write_chapter 规则 4 让模型「接着写下一章，需要时先补大纲条目，再调用 write_chapter」，不再直接要求调用 write_chapter，免得一轮连写几章时第二章起跳过这一步（2026-11-17 补：图时期的写手有时先写本章细纲，单循环原来从不写；只是提示，没有程序检查）。字数只报工具结果或系统给出的真实字数。作者在消息里给出大纲、人物等资料而项目里还没有时，先用 create_file 把原文逐字存成文件，不改写、不补作者没给的设定；AI 想补充的只写在文件末尾单独一节「AI 补充建议（待作者确认）」里，并在回复里用一句话说明补了哪几项（只是提示，没有程序检查）。
   - 删掉「作者给出自己的稿子时用 edit_file 把它整体替换进该章文件」这条，它正是覆盖错章节的来源。
   - 工具使用规则的单循环版本按 write_chapter 重写「写正文」「改已有文件」「资料文件」三节，其余分段与图共用；图的 `TOOL_USAGE_PROTOCOL` 逐字不变。
8. **上下文**：只追加的对话历史，不按 token 开窗、不做组装器优先级裁剪。每轮只附结构化请求上下文：项目信息与写作约定、焦点文件、附加文件、引用文字、附加素材库条目、选中文字、作者选的技能、本轮回复语言（沿用现有解析器）；另附作者手改（`<author_edits>`，与图同一套计算）：焦点、附加文件和本会话 AI 写过的正文文件（按落库的工具调用取 id，先筛正文类型再计文件数上限）里，作者在 AI 写过之后亲手改了哪几处——只追加的历史里留着 AI 早先的写法，没有这一块时模型会照旧名续写或把作者的改动改回去；项目里其他文件由模型用 query_files 查。往轮的工具调用与结果按显示顺序成对回放，思考内容只在一次 run 内回放；多 agent 图写下的旧行沿用原来的文字折叠。
9. **压缩**（轮与轮之间，从不在工具循环中途）：上一轮最后一次模型调用的实测输入 token 超过 `AGENT_LOOP_COMPACT_AT_TOKENS`（默认 600000）时，本轮开始前用同一个模型写一份中文交接摘要（文件清单与状态、已确认的设定和被作者纠正的旧说法、原样的长期要求、进度和下一步、不编造、不超过 1500 字）。摘要必须非空且没有被输出上限截断，否则降低思考强度重试一次，仍不行就不压缩。摘要不加表结构，写进本轮 assistant 行的 `message_metadata.compaction`（`summary`、`covers_through_message_id`、`created_at`）。没压缩成时记 `message_metadata.compaction_skipped`（原因、当时的实测输入 token），之后输入至少再长 `AGENT_LOOP_COMPACT_RETRY_GROWTH_TOKENS`（默认 100000）才再试；回放给单次 run 的历史另有估算上限 `AGENT_LOOP_RUN_HISTORY_MAX_TOKENS`（默认 800000），超出时丢最旧的项，会话降级而不是每轮超出上下文。本轮没有 assistant 行（例如还没产出就失败）时，这两种记录写在作者那条 user 行的 `message_metadata` 上。之后的历史是：系统提示 + 压缩点之前最近的作者原话（20k token 预算内原文）+ 一条以「【上下文已压缩】」开头的 user 消息（摘要）+ 压缩点之后的全部行。
10. **预算**：沿用请求墙钟 `AGENT_RUN_WALL_CLOCK_TIMEOUT_S`、收尾提醒（单循环用自己的文案：刚调用 write_chapter 或 create_file 还没写 `<file>` 正文的先写完，不提它没有的 parallel_execute；图的原文不变）、单次 run 的工具轮数上限、请求级模型调用上限与失控退还语义。一轮里同一个 agent 只因结构化事实再跑：空文件纠偏（含定下整章替换却没收到正文：经 `FILE_BODY_RESUME` 为那一章恢复捕获再跑一次，补不成就作废定位、原文不动）、停在写完的 `</file>` 上的续写、运行中插话；最多 `AGENT_COLLABORATION_MAX_ITERATIONS` 次。写正文的那次回复到 `</file>` 就结束，续跑说明充当写入的工具结果：写明保存了哪些文件和落库字数，并要求先按工作方式自查（对照大纲、前一章、角色卡，用 edit_file 改正，不整章重写），再写下一章或回复作者；同一个文件只要求自查一次，之后再写它只说已保存（防止「自查 → 整章重写 → 再自查」一直转到时限）。本请求里 write_chapter 已经写完并保存过正文的章节（StreamAdapter 确认落库、不含截断补全），再次 write_chapter 它时工具拒绝（`chapter_written_this_turn`），指向 edit_file，见 [同一请求里不整章重写刚写好的章节](../bug-fix/2026-11-16-loop-write-chapter-once-per-request.md)。在等正文时模型写出、以工具调用协议标记开头的残片（没有执行的文字版工具调用）不倒进聊天。墙钟暂停卡保留计费认定的 layer，`last_agent` 为空。正常结束时与图一样按本请求实际写出的文件收尾任务板；前几轮连续停在输出上限的次数从历史行的 stop_reason 数出；次数大于 0 时，本轮第一次 run 的输入末尾附图里同一条「截断后的本轮交付」指令（简短思考、直接调用工具或开始写、任务大时先交付第一部分），只对本轮生效、不写回历史。
11. **生成模式**：单循环路径不读 `generation_mode`，请求结构照旧接受（网页端已不再发送，旧客户端仍可能带上）。回滚到图时没带模式的请求默认不自动送审（`AGENT_ENABLE_GRAPH_AUTO_REVIEW` 默认改为 false）。（图删除后这个变量不再读取，见 [remove-graph-agent](../simplification/2026-11-17-remove-graph-agent.md)。）
12. **测试**：AgentService 外壳用例（SSE、停止 / 取消、插话、落库与回执、计费）用 `shell_engine` 夹具在图和单循环两个引擎上各跑一遍（图删除后只跑单循环，见 [remove-graph-agent](../simplification/2026-11-17-remove-graph-agent.md)）；单循环 agent 另有真实工具 + 脚本模型的端到端用例，覆盖整章替换与撤销、edit_file 的撤销元数据、停止时的计费与 stop_outcome、请求时限、工具轮数耗尽的失控退还和运行中插话。

## Alternatives considered

- **保留多 agent 图。** 最强理由：路由给出的只读与范围合同是程序可核验的结构化事实，审稿人能独立抓到前后矛盾，这些路径经过一个多月的生产修补，已知问题都有回归测试。未采用：成本和延迟的大头正来自这套结构本身（送审 + 返修、换角色重读、缓存断开），跨轮记忆受窗口限制，而对照里单循环在质量上不输；继续修补只会让分支更多。图作为回滚路径保留到单独删除。
- **保留图，逐项修复（关掉自动送审、加大历史窗口、合并角色提示）。** 最强理由：改动小、可以一项项上线和回退，不动已有的路由合同与回执。未采用：关掉送审后图里剩下的主要是路由和交接，而它们正是缓存断开和读写范围分支的来源；加大窗口不解决工具结果不回放，合并角色提示后仍要维护交接与计划补写。修到最后等于在图里重建一个单循环，同时背着图的复杂度。
- **单循环 + 可选的审稿工具。** 最强理由：作者明确要求审稿或长篇连写时，独立的审稿视角可能比自查多发现问题，而且只在调用时付费。暂不采用：没有对照证据说明它比写后自查规则更好；作者要求审稿时同一个 agent 可以直接读稿给意见。如果之后的生产数据显示前后矛盾明显增多，再作为一个普通工具单独评估。
- **整章写入只靠提示规则（模型自己找到这一章的文件，用 edit_file 整份替换）。** 最强理由：不加工具，工具清单与图一致，模型可以灵活处理分卷、命名不规范的旧文件。未采用：盲评回放里正是这条规则让模型把稿子写进了别的章节；目标文件由模型挑，程序无法核验，出错时覆盖的是作者已有的正文。
- **write_chapter 把正文内联在参数里（回放原型的做法）。** 最强理由：一次调用完成，没有两次回复协议；替换时可以直接走 edit_file 的提交，不需要 StreamAdapter 补发卡片。未采用：失去编辑器里的实时打字；整章正文进工具参数，流式过程中作者什么也看不到，参数被截断时整次调用失败、一个字也存不下；与现有 `<file>` 协议、空文件纠偏、残稿补存、计费和回合回执的口径分叉。
- **保留 create_file 的同章守卫，指回已有文件让模型用 edit_file 替换。** 最强理由：工具数不变，守卫已经实现并有回归测试。未采用：守卫只拦新建；替换仍要模型对已有文件做整份 replace，这正是覆盖错文件的那条路径。按章号显式定位，比按模型给的标题去猜目标更可靠。
- **「改完一段原文都没留下」对整批编辑生效（几处小改动合起来也算整章替换）。** 最强理由：能拦住把整章拆成几处 replace 绕过第一条规则的做法。未采用：逐段润色、统一标点这类正当的修改也会被拦，而作者保存过的章节又不能经 write_chapter 替换，作者的要求就没有任何路径能完成。拆成几处 replace 的整章重写仍有 diff 审阅、历史版本和撤销兜底。
- **edit_file 的正文守卫用相似度或改动比例阈值。** 最强理由：能拦住「几乎整章重写但留了一两句」的情况。未采用：阈值没有自然取值，对长章节的大段修改会误拦。只拦两种逐字可判定的情况，其余交给 diff 审阅和撤销。
- **作者保存过的章节也允许经对话整章替换（有 diff 审阅和撤销兜底）。** 最强理由：作者明确说「把这一章换成我这份稿子」时少一步操作。未采用：与既有的类型化权限决策（应用内对话不整份覆盖作者保存的正文）冲突，推翻它需要单独的决策；作者可以在编辑器里粘贴，或让 AI 用 edit_file 局部修改。
- **服务端自动压缩（按固定窗口裁剪或在 run 内扩展裁剪器）。** 最强理由：不多一次模型调用，没有摘要写错事实的风险，实现简单。未采用：按窗口裁剪正是现在丢失作者早先要求的原因；在一次 run 内裁剪会让模型在工具循环中途忘掉刚读过的内容、反复重读。轮与轮之间写一次交接摘要、保留作者原话，只在上下文真的很长时付一次摘要的成本。
- **新章没有大纲条目时总是先补，包括短篇。** 最强理由：每一章写之前都有一份可对照的计划，自查和后续章节有据可依，图时期的写手也是这样做的。只采用了其中「分多章写、还没有大纲文件时新建分章大纲」这一部分。未采用的部分：短篇会多出一个作者没要的文件和大约两次模型往返的延迟与费用，却没有测量说明图时期的这一步提高了质量；按卷粗列的大纲会被逐章填满，一章一个文件的大纲会被写进别的章节的文件里，作者贴来的自己的章节稿还会先被写一段 AI 概要。只在大纲本来就逐章列出时补，其余情况照作者原有的大纲写。

## Consequences

- 收益：每轮只有一个模型在跑，没有送审 / 返修和换角色重读；历史只追加，跨轮前缀缓存稳定，作者早先的要求和工具结果都留在对话里；服务端少了路由、交接、CHAT_HOLD、计划补写这些分支（图删除之后）。
- 收益：落库形状只用现有事件类型，前端不改也能渲染；回滚只需切环境变量（已由 [remove-graph-agent](../simplification/2026-11-17-remove-graph-agent.md) 取代：回滚改为从 git 检出删除前的提交重新部署）。
- 代价：不再有程序强制的只读 / 范围约束，「别改文件」这类要求靠模型遵守提示；误写由 diff 审阅、撤销和版本历史兜底。正常收尾不再有「没有改动文件」的回执。
- 代价：长会话的输入更大，直到触发压缩；压缩多一次模型调用，摘要可能漏掉细节（作者原话保留一部分，文件始终是唯一依据）。压缩一直不成时按估算上限丢最旧的历史，较早的工具结果会看不到。
- 代价：往轮工具结果按落库的卡片口径回放（技能正文不落库、失败只留给作者看的说明、create_file 的正文不重复放进对话）；回放时附一句说明这些内容没有保留，模型需要时重新调用 load_skill / read_skill_resource 或重新读取文件。
- 代价：单循环引擎暂时复用图模块里的几个空文件纠偏和续写辅助函数；删除图时要先把它们移出（已完成，见 [remove-graph-agent](../simplification/2026-11-17-remove-graph-agent.md)）。
- 收益：整章写入按章号定位，不会写进别的章节；结果明说是新建还是替换、原来多少字；替换和 edit_file 一样有 diff 审阅、历史版本和撤销。
- 代价：多一个只有单循环 agent 有的工具。前端要渲染 write_chapter 卡片：替换的卡片会在正文落库后收到同一个 tool_use_id 的第二条结果，撤销用其中的锚点。作者保存过的章节不能经对话整章替换。
- 代价：正文分在几个目录里时，替换已有章节必须带 parent_id。整章替换被拒时这一轮直接结束，同一轮里后面计划的章节要作者再说一次。
- 代价：标题开头没有章号的旧章节文件，write_chapter 认不出，会再建一个带章号的文件。edit_file 的两道检查只看逐字结构：换了说法的重复、保留了少量原文的整章重写不会被拦。定位后模型没写正文时原文不动，在纠偏次数内为这一章恢复正文捕获、同一轮再跑一次（核对定位时的版本）；仍没写就作废定位，停在原文。
- 代价：新章补大纲条目只在大纲逐章列出时发生，每章多一次 edit_file（一章一份大纲时多一次 create_file 和一次 `<file>` 写入）的往返与费用；分多章写的作品没有大纲文件时会多建一份「分章大纲」（第一章多一次 create_file 和一次 `<file>` 写入）；粗列大纲、短篇和作者给出的章节稿不补，写这些章时没有逐章计划可对照。是否补由模型按提示判断，没有程序检查。
