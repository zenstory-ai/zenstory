# Agent Note: MiniMax 双 Key 的会话粘性与单 Key 冷却

Status: implemented

调整 [双凭证加权路由](2026-11-05-minimax-dual-key-weighted-routing.md) 的第 2、4 条。关联：[模型供应商主备切换](2026-10-20-llm-primary-backup-failover.md)。

## Problem

双 Key 上线后的线上数据显示两个问题：

- 分桶按 `agent_run_id`，同一会话的相邻两轮可能落到不同 Key。比例 40% 时换 Key 概率是 48%。MiniMax 的缓存看起来按 Key 隔离，换 Key 的首次调用几乎没有命中。
- 一把 Key 的 429 计入整个 MiniMax 槽位。次 Key 额度较少，它的 429 曾打开熔断，把主 Key 的健康流量也切到 DeepSeek，并把会话固定到 DeepSeek 30 分钟。主 Key 限流时也不会用还有额度的次 Key。

只改成按会话固定 Key 会让后一个问题更严重：重度会话可能长期压在额度少的 Key 上。

## Decision

1. **会话 + 时间窗分桶。** 有 `agent_run_id` 时，run 的第一次调用用 `会话 id:时间窗` 决定路由（窗口 `LLM_KEY_ROUTING_WINDOW_S`，默认 1800 秒），之后整个 run 沿用。没有会话 id 的 run 仍按 run id；没有 run 上下文的调用行为不变。run 的路由记在进程内（最多 4096 个 run），因为一个 run 只在一个进程里跑。
2. **分桶带服务端密钥。** 用主 Key 做 HMAC：会话 id 可能来自客户端，调用方不能算出或选择自己的桶。
3. **Key 级失败只冷却这把 Key。** 401/402/403/429 且另一把 Key 可用时，只把这把 Key 冷却 `LLM_KEY_COOLDOWN_S`（默认 300 秒），不计入槽位熔断、不固定会话，后续调用改走另一把。冷却状态与熔断状态同存储（Redis，不可用时退回进程内存）。主次两把 Key 规则相同。
4. **两把都冷却才算供应商失败。** 此时走原有的熔断和会话固定，切到备用供应商。超时、连接错误、5xx、流内错误不是单把 Key 的问题，仍按原规则处理。
5. **不做跨 Key 重试。** 失败的那次调用仍按原规则交给备用供应商或报错；从下一次调用起才换 Key。这一条按主备是不同供应商的部署（生产是 MiniMax + DeepSeek）成立；主备都配成 MiniMax 时，无会话调用的两个槽位可能各取一把 Key，备用槽位接手就等于换 Key。是否固定会话在失败当下决定（`record_failure` 的返回值），不看接手的调用结束时冷却过期没有。冷却期间，进行中的 run 会换 Key，这是「一个 run 固定一把 Key」的唯一例外。
6. **权重 0 表示停用次 Key。** 此时另一把 Key 不算可用，行为与单 Key 部署一致，不读写冷却状态。

## Alternatives considered

- **只按会话 id 分桶，不加时间窗。** 最强理由：实现最简单，缓存最稳。被否：模拟显示按项目分桶时次 Key 的费用占比波动很大，单个重度账号可能压垮额度少的 Key。缓存实测只活 10–15 分钟，窗口再长收益也很小。
- **在 Redis 里记录每个会话当前的 Key。** 最强理由：不受窗口边界影响，可按实际负载分配。被否：每次调用多一次读写和一份状态；窗口边界的代价只是偶尔一次未命中。
- **失败时当场换另一把 Key 重试。** 最强理由：作者感受不到这次失败，还能避开 DeepSeek 拒收缺 reasoning 工具轮的情况。被否：11-05 明确拒绝跨 Key 重试，也违反不自动重试付费调用的约定；只有备用供应商接手这一个已有例外。如果生产上这种中断变多，再单独决定。
- **按累计 token 动态平衡两把 Key。** 最强理由：最贴近实际额度。被否：需要跨进程用量状态，复杂度高；冷却已能兜住额度用尽的情况。

## Consequences

- 收益：相邻两轮在同一窗口内留在一把 Key；一把 Key 限流不影响另一把和其他作者，也不会把会话固定到备用供应商。
- 代价：比例按「会话 × 窗口」计，短期内实际比例会偏离配置，额度少的 Key 靠冷却兜底。每个窗口边界有 2w(1−w) 的概率换 Key（40% 时 48%），损失一次首调缓存。
- 代价：冷却开始时流量集中到另一把 Key，可能接着把它也打满，然后切到备用供应商。这是预期行为。冷却到期后流量回到这把 Key，如果仍然限流会再次冷却。
- 代价：主 Key 轮换会改变所有分桶，影响限于一次缓存未命中。线上账本无法再按 `agent_run_id` 重算分桶，实际比例看 `LLM call thinking before answer` 日志（每次流式 agent 模型调用一行）里的 `key_slot`。
- 代价：流内错误（HTTP 200 里的错误事件）区分不出是否为额度问题，仍按原规则固定会话。
