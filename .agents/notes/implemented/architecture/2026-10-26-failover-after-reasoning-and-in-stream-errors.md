# Agent Note: 只出了思考就失败的调用当场切备用；流内错误算供应商失败；路由被拒试另一边

Status: implemented

关联：调整 [主备切换](2026-10-20-llm-primary-backup-failover.md) 的第 2、3 条（什么时候换、只在没有输出时当场换），不推翻其余规则；失败原因观测见 [供应商失败原因](../bug-fix/2026-10-25-provider-failure-reasons.md)。

## Problem

10-25 04:00 到 10-26 07:00（UTC）的生产日志里，MiniMax 主用的失败有三类没有切到备用：

1. **思考了很久才失败**：3 次读超时（单次调用 176–534 秒），以及 `unknown error, 715 (1000)`、`Internal server error. Please retry` 各一到两次（188–357 秒）。这些调用只流出了思考内容，还没有正文或工具参数，但第一个思考片段就让「已开始输出」成立，整轮以错误结束，作者只能手动重试。
2. **流内错误不算供应商失败**：后两种错误是 HTTP 200 流里的 error 事件，openai 客户端抛出没有状态码的 `APIError`，`is_provider_unavailable` 判为否：既不固定会话也不计熔断，作者重试仍打到 MiniMax。
3. **路由被拒就停**：10-25 12:55 两分钟内 6 次路由调用被 MiniMax 以 422 拒绝（`Router decision failed`，provider_failure），作者这几轮在任何 agent 运行之前就停下了。400/413/422 按设计不切换。

## Decision

- **只有思考内容时也当场切换**（`openai_agents/model.py`）：一次模型调用失败时，只要还没流出正文、拒答或工具参数（`_ANSWER_OUTPUT_EVENT_TYPES`），且供应商不可用，就在同一次调用里改用另一个供应商；已经流出的思考保留，备用的思考接在后面。已流出正文或工具参数后仍按原规则报错，不重复生成。对作者不展示切换提示，只记 `LLM call failing over to the other provider`（`after_reasoning=true`）。
- **流内错误只换这一个会话，不计熔断**（`llm_failover.is_in_stream_error`）：没有 HTTP 状态码的 `openai.APIError`（流里的 error 事件）可能是供应商故障，也可能是针对这次内容的拒绝，事件里没有可靠字段区分。只出了思考时在同一次调用里改用备用，并把这个会话固定到备用（`pin_session_to_other`）；**不计入熔断**，一个作者的内容不会让所有作者都切到备用。`is_provider_unavailable` 不变：只有连接失败、超时、429、5xx、401/402/403/404 计熔断。不从错误文案推断原因。
- **路由被拒时试另一边**（`acreate_chat_completion(fail_over_on_rejection=True)`，只有 router 传）：400/413/422 时改请求另一个供应商，不计入被拒一方的熔断、不固定会话，备用答上也不改会话顺序；两边都失败照旧安全停止。

回归：`tests/test_agent/test_llm_failover.py`（真实 SDK 流处理器：思考后超时由备用答完、流内错误切换、路由 400/413/422 由备用答且会话不固定）；原「流中途读超时归为 timeout」用例改为在正文输出后超时，保留它验证超时分类的原意。

## Alternatives considered

- **维持「首个思考片段即算已输出」**。最强理由：最保守，绝不出现两段思考。被否：思考不会被保存成正文、也不触发工具，切换不会重复任何作者能用的产出；保守的代价是作者在等了几分钟后拿到一张错误卡。
- **思考片段先扣着不发，失败时直接丢弃**。最强理由：前端只看到一个供应商的思考。被否：MiniMax 会先思考几分钟，扣着就让作者长时间看不到任何进展。
- **路由失败时默认交给 writer 快速模式**。最强理由：作者这一轮总能继续。被否：[路由安全停止](../bug-fix/2026-10-18-router-invalid-decision-safe-stop.md) 已决定不在路由失败时静默猜流程；换一个供应商重试路由不违背这一点。
- **根据 MiniMax 错误文案里的业务码区分流内错误**。最强理由：能把内容拒绝类错误排除在切换之外。被否：流内错误的 body 是 error 对象，不带 `base_resp`；按文案猜码与 [失败原因观测](../bug-fix/2026-10-25-provider-failure-reasons.md) 的约定冲突。
- **流内错误也计熔断**（初版做法）。最强理由：真正的供应商故障能更快让新会话改走备用。被否（独立审查指出、作者明确要求避免）：内容审核类拒绝同样以流内错误出现，一个作者反复触发就会让主用对所有作者熔断 120 秒；真正的故障通常伴随超时、5xx 这些仍计熔断的错误。

## Consequences

- 收益：主用在思考阶段卡住或报错时，作者这一轮由备用答完，不再白等几分钟后报错；之后同一会话固定到备用 30 分钟（既有规则）。
- 收益：路由不再因为一边拒收请求而让作者的整轮停在动笔前。
- 代价：失败那次调用的思考 token 已由主用计费，备用重新思考一次；思考面板里会有两段思考，前一段停在半路。
- 代价：流内错误如果其实是请求本身的问题，会多试一次备用，这个会话 30 分钟内都用备用。

后续：备用供应商会因缺 reasoning_content 拒收时不再切换，见 [2026-10-29](../bug-fix/2026-10-29-no-failover-when-backup-rejects-missing-reasoning.md)。
