# 工作台改用 AGPL-3.0

## Problem

工作台仓库自公开起使用 MIT。MIT 允许任何人把完整的 SaaS（编辑器、Agent 编排、计费与额度、管理后台）闭源改名后作为托管服务出售，且无需回馈修改。项目准备公开宣传开源，曝光增加后这一风险会放大；而宣传之后再收紧许可证，会被视为改变承诺，代价更高。

## Decision

- 仓库根目录 `LICENSE` 换为 GNU AGPL-3.0 原文（gnu.org 发布的 `agpl-3.0.txt`）。覆盖 web、server、worker 等工作台代码。
- `apps/cli` 保留 MIT（其目录下自带 `LICENSE`）。它是给用户和 Agent 宿主安装的客户端，宽松许可利于集成，且不构成托管竞品的核心。
- 不改写 Git 历史。
- README 声明 ZenStory 名称与标识不在许可范围内，fork 和自部署服务应使用自己的名称；提供商业授权的联系方式。
- CONTRIBUTING 要求贡献按 AGPL-3.0 授权，并授予 ZenStory 以其他条款（含商业授权）再分发的权利，以保留双授权的可能。变更时所有提交均出自同一维护者。
- 官网数据：工作台项目页显示 `AGPL-3.0`（`projects.json` 的 `license` 字段，缺省回落到 `org.json` 的 `proof.license`），skill 包仍显示 MIT；组织简介不再写“都是 MIT”，页脚分别说明 skill 包和工作台的许可。

## Alternatives considered

- **保持 MIT**：采用阻力最小，企业和开发者最无顾虑，宣传口径最简单。但它对“改名托管售卖”没有任何约束，而这恰恰是商业化 SaaS 最直接的竞争方式。
- **FSL / BSL 等源码可见许可**：能直接禁止竞争性托管，且到期自动转为宽松许可，保护力度最强。但它不是 OSI 认可的开源许可，与“开源”定位和现有组织站口径冲突，技术社区对此反弹明显。
- **开源核心（商业部分闭源）**：可只保护计费、额度等商业代码。但这些代码已在 MIT 下公开，拆分成本高，且会让自部署体验变差。
- **重写 Git 历史**：已有的 fork 和克隆仍保留完整历史，达不到目的；同时会破坏发布标签、按提交 SHA 记录的 CI 与部署证据以及外部链接，并违反禁止强推的仓库规则。

## Consequences

- 收益：他人以修改版提供网络服务时必须向其用户公开源码，正规公司难以闭源套用；仍是 OSI 开源，宣传口径不变；版权集中，保留双授权空间。
- 成本：部分企业因 AGPL 不愿采用或贡献；在实际维权成本高的地区，许可证主要起威慑作用，品牌保护还需要商标注册配合（不在本仓库范围内）。
