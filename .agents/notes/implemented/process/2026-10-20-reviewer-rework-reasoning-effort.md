# Process Note: 审稿人与返修 writer 的思考强度对照评估——保持默认

Status: implemented

## Problem

DeepSeek 成本要降约 70%，但要保留高质量模式：它的自动审稿多数时候抓到的是真实的连续性问题。审稿人（quality_reviewer）和返修 writer 约占每天 ¥44 里的 ¥11。生产里审稿人每次调用平均输出约 4k token，大半是思考（常是英文），思考约占全部输出花费的 85%。审稿人的工作是对照附上的证据核对，返修的改法由审稿人写明，看起来都适合降低思考强度。[2026-10-19 的评估](2026-10-19-reasoning-effort-evaluation.md) 只测了 fast 模式的 writer，而 `AGENT_REASONING_EFFORT` 是全局开关，没法只降这两个角色。降档之前要先用客观的埋点缺陷证明审稿质量不受影响。

## Decision

- 新增两个按角色覆盖的开关（`config/agent_runtime.py`）：`AGENT_REVIEWER_REASONING_EFFORT`（quality_reviewer）与 `AGENT_REWORK_REASONING_EFFORT`（审稿人交回的返修 writer）。默认不设，沿用全局 `AGENT_REASONING_EFFORT`（也默认不设，即模型默认 high）；只接受合法档位，拼错的值忽略。返修 run 由 writing_graph 在跑 agent 前置 `state["review_rework"]`，runner 经 `reasoning_effort_for(agent_type, rework=...)` 取档位。**生产不设置这两个开关。**
- 评估脚本 `apps/server/scripts/eval_review_effort.py` 留在仓库，以后换模型或改审稿提示时用同一套用例复评。

评估设置：走生产的 `AgentService.process_stream` + writing_graph（quality 模式，临时 SQLite 库），只把路由（直接给 writer）和第一个 writer run（写入埋好缺陷的一章，触发自动质检门）固定下来，之后的审稿、返修都是真实 deepseek-flash 调用，审稿人收到的就是生产的送审包（正文、编辑器字数、程序检测证据）。两个题材：小说（第三章，793 字）和短剧剧本（第 3 集，569 字），前两章 / 前两集作为前文。每份埋 5 个生产审稿返回过的客观缺陷：

| 缺陷 | 小说 | 剧本 |
| --- | --- | --- |
| 日期矛盾 | 「十月三日清晨」，前文是十月三日傍晚下船、十月四日抓药 | 字幕「三月十二日」，前一集是三月十三日，台词说「昨天警察放你出来」 |
| 数字对不上 | 四十文 + 二十文写成「一共花去八十文」 | 六十万三人平分写成「每人二十五万」 |
| 与上一章逐字重复 | 25 字雾景句 | 21 字动作行（程序检测也会提示） |
| 残留标记 | 「（本章完）」 | 「（本集完）」 |
| 对白格式 | 一句对白缺引号 | 一句台词缺角色名 |

每档每题材 5 次，交错执行，2026-10-20 北京时间晚间（低峰价），共 50 次、约 ¥2.0。缺陷是否被指出、修法是否正确、返修是否改了别处都逐条人工核对：脚本里的关键词匹配只作初筛，它会把「对白保持引号体例」这类保留说明误算成指出了缺引号。

审稿人与返修同档（30 次，¥1.18）：

| 题材 / 档位 | 埋点缺陷指出 | 修好且修法正确 | 审稿人输出 token（其中思考） | 返修输出 token | 每次审稿+返修成本 |
| --- | --- | --- | --- | --- | --- |
| 小说 default | 25/25 | 24/25 | 2696（1683） | 1891 | ¥0.040 |
| 小说 medium | 24/25 | 19/25 ¹ | 2319（1268） | 2211 | ¥0.040 |
| 小说 low | 18/25 | 19/25 ² | 1560（699） | 1625 | ¥0.035 |
| 剧本 default | 25/25 | 25/25 | 2931（1765） | 2579 | ¥0.044 |
| 剧本 medium | 25/25 | 23/25 | 2963（1973） | 1931 | ¥0.040 |
| 剧本 low | 25/25 | 25/25 | 2251（1267） | 1583 | ¥0.037 |

¹ 其中一次返修因本地 SQLite 写锁三次保存失败（评估环境问题，不是模型），5 处都没改上；排除后为 19/20。
² 含返修 writer 自己发现并改掉的、审稿人漏报的缺陷。

- **low 审稿漏报。** 小说 5 次全部漏掉缺引号的对白，2 次漏掉「（本章完）」（这两处后来是返修 writer 没被要求时顺手改的，其中一次把「老周压低声音说：」这个说话人一起删掉了）。medium 漏引号 1/5。default 也不是满分：两轮合计 15 次 default 审稿漏引号 2 次，「（本章完）」15/15。剧本的 5 个埋点各档都全部指出。
- **前文里没有埋、但真实存在的连续性问题。** 剧本里有两处我写稿时没注意到的真问题：小陈「留下看钱」、沈默却提着旅行袋去江堤、最后又叫小陈「带着钱」换地方；女人的纸条落在鞋面上，下一场沈默却直接展开纸条。default 5 次里指出 6 处（钱袋 3、纸条 3），medium 3 处，low 2 处。这正是作者看重的那类审稿价值，而降档最先丢的就是它。
- **修法本身的正确性。** 审稿人偶尔给出错的改法，返修照做：default 1 次（小说改成「十月四日清晨」仍说「昨天抓的药」）；medium 3 次（小说一次同类，剧本两次把字幕改成「三月十三日」，与「昨天警察放你出来」仍矛盾）；low 2 次（小说改成十月五日却把药说成「前日」抓的）。样本小，看不出档位规律，但降档不会减少这类错误。
- **省下的很少。** 本评估里 low 让审稿+返修每次少约 ¥0.005（12–16%），medium 基本不省（审稿人输出小说 −14%、剧本 +1%）。low 让审稿+返修的输出 token 合计少约 30%；本评估的稿子短、输入占比高，所以成本只少 12–16%。按生产审稿+返修 ¥11/天、输出约占花费八成估算，low 大约省 ¥1.5–3/天，离 −70% 的目标差得远，而代价是漏报和更少的连续性发现。

返修单独降档（审稿人 default，20 次，¥0.82）：

| 题材 / 返修档位 | 审稿人写明的改法照做 | 改了没被要求的地方 | 返修输出 token（其中思考） | 每次返修成本 |
| --- | --- | --- | --- | --- |
| 小说 low | 5/5 | 无 | 1511（522） | ¥0.020 |
| 小说 medium | 5/5 | 无 | 2483（1472） | ¥0.023 |
| 剧本 low | 5/5 | 无（另照做了审稿人标为「可选」的一处） | 1583（566） | ¥0.020 |
| 剧本 medium | 5/5 | 无 | 2364（1304） | ¥0.022 |

对照：返修 default（上表第一轮）输出小说 1891、剧本 2579 token，成本 ¥0.020 / ¥0.023。

- 审稿人写明的改法，low 返修 10/10 全部照做，没有顺手改别处；唯一错的一处（剧本字幕改成「三月十三日」）是 default 审稿人写错的改法。返修只照抄，不会替审稿人纠错，降档也没让它更差。
- 审稿人漏报时（本轮 default 漏引号 2 次），medium 返修一次自己发现了，但没改，在回复里问作者要不要补；没被要求就不改，符合作者范围规则。
- low 返修的输出 token 比 default 少 20%（小说）和 39%（剧本），思考 token 少约 45–60%；但返修要做 3–4 次模型调用，每次都重新送一遍上下文，成本里输入占大头，所以每次只省约 ¥0.001–0.003。medium 返修反而比 default 输出得多。

建议：

- **审稿人：保持默认（不设 `AGENT_REVIEWER_REASONING_EFFORT`）。** low 有确定的漏报，medium 指出的前文问题少了一半且不省钱。
- **返修 writer：质量上 low 可以，但省得很少；本次不在生产开启。** 审稿人写明改法时，low 返修照做 10/10、不扩大改动，输出 token 少 20–39%。按生产审稿+返修 ¥11/天、返修约占一半估算，`AGENT_REWORK_REASONING_EFFORT=low` 大约每天省 ¥0.5–1。要开的话作为单独授权的生产配置变更，在 staging 之外没有真实模型可测，只能在生产观察返修后的二次审稿和作者回滚；不开也不影响降本主线。medium 不建议（更贵、没有质量收益）。

## Alternatives considered

- **只用全局 `AGENT_REASONING_EFFORT` 测，不加按角色开关。** 最强理由是不改代码。未采用：全局开关同时降 writer、planner，测出的差异分不清是哪个角色造成的，也不能单独上线其中一个角色。
- **直接对 quality_reviewer 降到 medium 上线，按生产反馈回调。** 最强理由是审稿人的工作是核对附上的证据，medium 在埋点缺陷上和默认一样是满分。未采用：medium 在剧本里指出的未埋点连续性问题从 6 处降到 3 处，而省下的输出 token 在两个题材上分别是 −14% 和 +1%，没有可兑现的收益。
- **用模型打分（LLM-as-judge）代替人工核对。** 最强理由是能扩大样本。未采用：要判断的是「修法是否与前文自洽」这种需要细读的事实，判分模型本身也会犯审稿人同样的日期推理错误；50 次的量人工核对得过来。
- **埋更多、更难的缺陷。** 最强理由是 default 已经接近满分，区分度不够。未采用：本轮目标是证明生产里真实出现过的缺陷类型不会漏；剧本里意外出现的两处未埋点问题已经提供了更难的样本，而且结论是降档不划算。

## Consequences

- 生产行为不变；两个开关默认不设，单测覆盖只对各自角色生效、未设时沿用全局值，以及只有审稿人交回的那次 writer run 才算返修。
- 审稿与返修的成本不能靠降思考强度省，要靠减少输入（送审包、前文、文件清单）和减少不必要的审稿轮次。
- 样本小（每格 5 次，两份短稿），只能说明方向；稿子比生产短（生产审稿人平均输出约 4k token），长稿里低档的漏报可能更多。返修只在审稿人写明具体改法时测过；生产里也有审稿人只给笼统待办、不写具体改法的交接，low 返修在那种情况下没测。
- 审稿人自己偶尔会写错改法（50 次里 7 次，各档都有），返修照做。样本里看不出与档位有关，是另一个值得单独看的问题。
- 复评时用同一脚本，并继续人工核对修法，不只看关键词命中。
- 评估环境里的 SQLite 写锁偶尔会让返修保存失败（1/50），这是脚本的已知局限，不代表生产行为。
