# 站内公告：产品与交互设计

Status: proposed — 已完成用户产品／商业化产品／架构三方评审；仅设计，尚未实现或发布

最新范围：用户随后给出轻量横幅参考，[轻量公告横幅提案](../../implemented/feature/2026-10-17-lightweight-announcement-banner.md)现已替代本文的首版范围。本文为历史方案，不作为当前待执行开发要求。

交互版本说明：用户查看首轮效果图后要求重新打磨。[第二轮交互提案](2026-10-17-announcement-interaction-refinement.md)替代本文的入口、居中对话框、摘要关闭控件和后台表单表现；本文保留第一轮设计与评审记录，数据／权限／生命周期规则继续有效。当前实现应同时读取第二轮提案，不把第一轮效果图当已批准基线。

## Problem

ZenStory 需要一个由运营发布、用户能够看到并回查的站内公告渠道，用于功能更新、维护预告与使用规则说明。它不是聊天消息，也不是支付、额度或保存错误的即时反馈，不应与这些现有提示混用。

现有事实：

- `/dashboard/*` 共用 Dashboard 壳层；写作页 `/project/:projectId` 是独立路由，不能只接入 Dashboard 后就声称覆盖整个应用。见 `apps/web/src/App.tsx:357–385`、`pages/ProjectEditor.tsx:273–289`。
- Dashboard 有桌面侧栏、平板图标栏和手机菜单；写作页 Header 已有帮助、反馈等次级操作。见 `pages/Dashboard.tsx:373–644`、`components/Header.tsx:167–194`。
- 管理后台已有「内容与运营」分组、超级管理员鉴权和审计日志。见 `components/admin/AdminSidebar.tsx:65–72`、`apps/server/services/core/auth_service.py:310–320`、`services/admin_audit_service.py:15–69`。
- 源码检索未发现可复用的公告实体、读取接口或账号级已读状态。现有 Toast 是瞬时操作反馈，不是公告存储。
- `DESIGN.md` 的 React workbench、Admin controls 与异步状态规范适用。`docs/screenshots/workspace.png` 已查看，但其说明明确标记为历史截图；本设计以源码为当前依据，不宣称已验证线上界面。

## Proposal

### 1. 首版定位与边界

**推荐：公告中心＋未读点＋重要公告摘要条，默认不弹窗。**

经用户产品、商业化产品与架构视角评审，首版推荐范围收敛为：公告面向所有已登录账号；用途以更新、维护和规则说明为主；阅读不需要用户确认同意。不读取套餐来分发公告，不改变额度、订阅或支付规则。此为待实施方案，不代表已经获得开发或上线授权。品牌写作 ZenStory。

| 首版做 | 首版不做 |
| --- | --- |
| 公告列表、正文、逐条已读、账号级同步 | 私信、任务通知、通用消息中心 |
| 普通／重要两种提醒强度 | 登录强弹、强制确认、阻断写作 |
| 后台草稿、预览、立即发布、下线 | 审批流、定时发布、用户分群 |
| 设置提醒结束时间、历史回查 | 邮件、浏览器推送、WebSocket、后台轮询 |
| 中英文 UI、可选英文正文 | 自动翻译、AI 写公告、图片上传、附件 |

公告不是紧急广播或站外状态页。服务不可用时，站内公告本身也可能不可用；本方案不承诺即时触达，更不能充当法律条款同意记录。

**内容章程与商业边界：** 公告服务于已上线能力认知、操作指引、维护预告与规则沟通，不投放纯促销、限时折扣、续费催促或额度耗尽提醒。重要级别仅用于影响既有使用或确需及时知晓的事项，日常功能更新不靠升为重要换曝光。若说明 Pro 专属能力，标题或摘要直接写清适用范围，不制造所有人都可用的错觉；更不能给已付费用户重复推「开通 Pro」。这些是运营规范和发布确认内容，不新增文本分类器或关键词审核。

内容采用「发生了什么 → 影响谁／什么时间 → 可以做什么」的简短结构。允许清楚命名的正文指引链接，不新增 CTA 字段、按钮式付费入口或升级漏斗归因。阶段价值是可信沟通和功能认知，不预设收入提升。

### 2. 用户在哪里看到

**Dashboard：** 桌面侧栏底部、主创作导航之后增加带 Megaphone 图标的「公告」次级按钮；平板保留图标与可访问名称。手机菜单中增加同名入口，有未读时菜单触发器也带小点，不增加新的底部导航。

**写作页：** 在 Header 现有次级操作菜单中增加「公告」。无未读时保持普通入口；有普通未读时，菜单入口及触发器带未读点；有重要未读时，在未展开菜单的触发器旁显示简短「重要」标记，可访问名称带「有重要公告」，不能仅靠颜色区分。桌面与手机均能在不展开菜单时辨别重要态，不增加独立工具栏按钮。查看时不跳去 Dashboard，不改变项目 URL，不刷新页面。

**重要公告：** 仅在 Dashboard 壳层主内容上方展示一条可关闭摘要，覆盖首页、项目列表等 Dashboard 子页。普通公告没有摘要条。写作页不增加横条，不改变三栏、手机面板或键盘布局；用户可从未读点进入查看。若今后需要正在写作的人即时收到维护警告，另行设计触达机制，不把它偷偷加进首版。

```text
Dashboard 主内容
┌──────────────────────────────────────────────────────┐
│ 重要公告  周日维护安排             查看详情       ×     │
└──────────────────────────────────────────────────────┘
原有创作入口、最近项目……保持原顺序

侧栏底部                         写作页「更多」菜单
公告 •                           帮助文档
                                 公告 •
                                 问题反馈
```

每次 Dashboard 壳层挂载，在首次成功的摘要查询后选定最新一条重要候选；本次挂载最多展示这一条。阅读、关闭、提醒到期或获知下线后均只撤掉，不轮换下一条；窗口聚焦、Dashboard 子路由切换都不重置选择。离开 Dashboard（例如进入项目）再返回导致壳层重新挂载，才重新选择。挂载后新发布的公告先更新未读点，不临时插入新摘要；中心仍可查看全部公告。

| 当前摘要的事件 | 本次展示与同步 |
| --- | --- |
| 已读写入成功 | 撤掉摘要，刷新未读状态，本次不补位 |
| 点击关闭 | 本次立即收起；服务端成功后跨设备记住，失败提示未同步，本次仍不补位 |
| 提醒到期 | 按响应 `server_now` 与 `expires_at` 的剩余时长撤掉，后台重新读取仍由服务端校验，本次不补位 |
| 下线 | 下一次成功校验后清除该条摘要／列表／详情缓存，本次不补位；不承诺实时撤回 |

### 3. 公告中心的阅读体验

两个入口打开同一个 Portal 对话框。桌面阅读宽度约 720px；手机为视口内全屏对话框，处理安全区与独立内容滚动，不跳新页面。

```text
┌────────────────────────────────────────────┐
│ 公告                                    ×  │
│                                            │
│ 未读 [重要] 周日维护安排         10月17日   │
│   维护时间与受影响功能                      │
│                                            │
│ 未读 [功能更新] 项目统计更新     10月16日   │
│   可以查看手写与 AI 字数                    │
│                                            │
│   [使用说明] 公告内容示例        10月15日   │
│                                   加载更多 │
└────────────────────────────────────────────┘

点击一条 → 同一对话框的详情视图
← 返回公告                 功能更新 · 发布时间
标题
正文（段落、小标题、列表、链接）
```

以上标题、日期与文案均为线框示例，不是实际发布计划或现有功能证明。

- 默认按发布时间倒序，稳定排序使用 ID 作为同时间的次级键，每页 20 条。不增加搜索、分类筛选、置顶排序或「全部已读」。
- 类别只有「功能更新／维护通知／使用说明」；提醒强度独立为「普通／重要」。重要不意味着故障，也不默认用红色警报。
- 列表展示标题、短摘要、类别、日期和「未读」文字＋点；详情显示完整发布时间。未参与未读提示的历史行不标「未读」。返回列表保留滚动与已加载页。
- 详情响应成功、该条详情视图仍在前台并完成首次提交后，记录该条已读；不等待 Markdown 懒加载完成，也不把渲染完成当成现有组件已经提供的信号。只打开中心、看到列表、详情请求失败或关闭摘要均不标读。这里的「已读」仅代表打开过：即使随后正文渲染失败，也不能据此声称实际阅读或理解。
- 读取与关闭状态由服务端按账号保存。A 账号不影响 B 账号；另一设备下次刷新时同步。退出或切换账号时清除旧 UI 与缓存，迟到响应不得写进新账号状态。
- 初次注册不追着提示全部历史：普通公告仅在 `published_at >= user.created_at` 且提醒未结束时参与未读；当前有效的重要公告不受注册时间限制。历史正文仍可主动查阅。
- 有效且未读的公告产生未读点，当前仍有重要未读时同时保留重要态。普通公告读后去点；重要公告读后也不再显示其摘要条。单独关闭重要摘要只记 `dismissed_at`：摘要不再展示，但未读点／重要态保留，列表仍能找到它。关闭按钮的 tooltip／可访问名称为「收起提醒，仍保留未读」；操作后以非 Toast 的轻量 `role=status` 提示「已收起，可在公告中查看」，不声称已读或已同步。
- `expires_at` 只表示「结束提醒」：到时从摘要候选与未读计算中移除，正文保留在历史列表，不宣称维护已完成或服务已恢复。下线后服务端立即不再向普通用户返回该条，包括直接读取详情；已经显示在客户端的内容，在下一次成功校验时撤下，不承诺即时收回。
- 正文链接由用户主动点击，新标签页打开，不替换当前写作界面。首版不提供触发生成、自动升级或支付的公告按钮。

### 4. 视觉、可访问性与失败状态

- 遵循 `DESIGN.md` 现有浅深主题与用户强调色，不借用组织站纸张／墨蓝皮肤。细边框、克制阴影；不增加大图、轮播、宣传弹层或新组件库。
- 公告列表标题与控件使用现有无衬线规范，阅读正文复用现有排版；重要标记同时有文字，不只依赖颜色。未读点的可访问名称带「有未读公告」。
- 复用 `ui/Modal`、`Button`、`IconButton`、`LazyMarkdown` 和后台状态组件。手机目标至少 44px；长标题、长链接与 Markdown 表格不能撑破视口。
- 从手机菜单打开前先关闭菜单，再打开 Portal。对话框有名称、焦点约束、Escape 和独立滚动；关闭时焦点回到仍存在的菜单触发器，而不是已经卸载的菜单项。
- 首次请求显示骨架；成功为空才显示「暂无公告」；失败显示「公告暂时无法加载」及重试。后台刷新保留现有列表，失败不能伪装成「暂无公告」。
- 每次打开中心／选择详情均触发可见性重新校验。请求中可保留旧列表但标注正在更新，不把未校验缓存正文当成新的有效详情展示；详情校验失败给重试，不展示旧正文。已经打开的详情后台刷新失败时可暂保留，明确提示「暂未更新，内容可能已失效」；成功发现下线后关闭该详情并回到列表。不能一边承诺离线可读，一边宣称下线即时消失。
- 壳层中的公告摘要请求失败时安静降级，不弹错误 Toast、不挡住主内容；用户主动打开中心时才展示可重试的错误。
- 已读／关闭写入失败，不宣称已同步；在中心给出轻量失败与重试提示。允许本次会话临时收起摘要，但后续重新请求以服务端状态为准，不冒充永久关闭。
- 不在用户输入或生成过程中自动打开对话框、移动焦点、刷新页面或取消 SSE。对话框打开不等于卸载编辑器，也不触发任何付费调用。

### 5. 运营如何发布

入口：后台「内容与运营 → 公告管理」，拟用路由 `/admin/announcements`。

列表按状态筛选：草稿／已发布／已下线，展示标题、类别、提醒强度、发布时间、提醒结束时间与操作。提醒已结束的内容仍属于已发布，附「提醒已结束」说明，不冒充一个额外发布状态。

编辑内容：

| 字段 | 首版规则 |
| --- | --- |
| 中文标题、短摘要、Markdown 正文 | 发布时必填，草稿允许未完成；建议上限分别为 80、160、20,000 字符，API 与表单一致校验 |
| 英文标题、摘要、正文 | 可选，但填写时三项必须齐全；否则统一回落中文，标注「中文原文」 |
| 类别 | 功能更新／维护通知／使用说明 |
| 提醒强度 | 默认普通；选择重要时显示影响范围与不过度打扰的说明 |
| 提醒结束时间 | 普通可留空；重要必填且晚于发布时间，避免长期悬挂 |

草稿允许编辑与删除；保存不等于发布。预览使用与用户端相同的渲染器、语言回退规则和浅深主题，可切换桌面／手机宽度。发布前确认展示位置、目标「所有已登录用户」、能力适用范围、正文语言和提醒结束时间，不默认创建或发布示例公告。发布重要公告时，在同一确认页列出当前仍有效的重要公告并明确「用户可能在后续进入工作台时看到新摘要」，管理员勾选确认重要用途后发布；不增加额外的后端 override 状态、硬性只能一条或多级审批流程。

发布后正文固定。需要更正时用「复制为草稿」创建新公告，预览并发布后再下线旧公告；新的公告有新的 ID，按新公告重新提醒，不静默改写已经读过的版本。复制保留来源公告 ID，便于追溯。发布更正和下线原文是两个独立操作，不声称原子替换：若前者成功、后者失败，后台明确显示「更正公告已发布，原公告仍在线」及原公告下线重试入口，不撤回新公告或再创建一份。下线需确认，后续用户读取不再返回该条，但保留管理记录；不提供已发布公告的永久删除或直接重新上线。

管理页将上述动作收束为一个「创建更正」引导入口：自动预填草稿并展示来源；新稿发布成功页就地显示原公告状态与「下线原公告／重试」，不让运营跨页寻找。若新旧两条仍发布，列表通过来源关系派生「原公告待下线」标记；刷新后仍可发现，不新增第四种发布状态。来源已下线时不再提示。

发布成功以服务端返回为准。失败保留编辑内容，重试前重新读取状态，避免重复发布。重复发布／下线同一 ID 不生成第二条公告或重写发布时间。新功能的管理写入均复用超级管理员鉴权与审计，普通用户不能访问草稿、预览或管理操作。

草稿编辑、删除与发布均携带当前 `draft_version`，服务端原子检查「仍是草稿且版本匹配」；不匹配返回冲突，保留本地编辑供重新核对，不能覆盖已发布正文。发布事务固定内容与 `published_at`、转换状态并记录审计；重复确认相同已发布版本返回既有结果，不重新赋时间。

### 6. 最小技术边界（供后续实施，不是本次改代码）

**两张表，不给每个用户预生成收件箱：**

- `Announcement`：ID、中英文内容、类别、提醒强度、`draft / published / withdrawn`、`draft_version`、来源公告 ID（可空）、`published_at`、`expires_at`、创建／更新管理员及时间。数据库只保存发布生命周期；是否提醒有效由当前时间计算。版本只保护草稿并发，不建设已发布正文的多版本系统。
- `AnnouncementUserState`：`user_id + announcement_id` 唯一，`read_at`、`dismissed_at` 均可空。首次阅读或关闭才幂等写入；无需通知队列或逐用户群发记录。账号与公告均使用外键。

迁移使用账号／公告复合主键实现 state 唯一性；公告表至少有 `(status, published_at, id)` 与 `(status, importance, published_at, id)` 的倒序查询索引。约束覆盖状态／类别／重要程度枚举、`draft_version >= 1`，以及已发布／已下线内容必须有发布时间、重要内容必须有晚于发布时间的提醒结束时间；这些发布约束不阻止未完成草稿保存。没有全用户回填。迁移接入执行时的 Alembic head，测试夹具补齐 state → announcement → user 的外键安全清理顺序，不能只注册模型而漏掉显式清理。

草稿改写／删除／发布使用数据库状态＋版本条件更新并检查受影响行数，发布审计用现有 `log_action(commit=False)` 与业务在同一事务提交，失败整体回滚。read／dismiss 使用冲突安全 upsert，只写自己的首次时间且保留另一列；不能让并发「打开＋收起」互相覆盖。并发保证以一次性 PostgreSQL 测试环境的双会话用例验收，不用 SQLite 单会话代替。

**拟定接口：**

| 普通登录用户 `/api/v1/announcements` | 含义 |
| --- | --- |
| `GET /summary` | 当前账号 `has_unread`、`has_unread_important`、一条重要摘要候选与 `server_now`；重要未读与是否收起摘要分别计算，不返回所有正文 |
| `GET /`、`GET /{id}` | 分页历史列表与详情；排除草稿、下线内容 |
| `PUT /{id}/read`、`PUT /{id}/dismiss` | 只操作 token 对应的当前账号；不接受其他 user_id，幂等记录时间 |

管理端拟在 `/api/admin/announcements` 下提供草稿增删改查、发布、下线与复制草稿操作，子 router 复用父级前缀。API 保持薄层，资格过滤、未读与摘要选择统一放在 `services/features/announcement_service.py`，所有用户读取路径使用同一可见性规则。普通端复用 `get_current_active_user`，管理端复用 `get_current_superuser`。预览读取走管理权限，不扩展普通详情接口暴露草稿，也不新增顶层 schemas 抽象层。

- 复用 SQLModel、Alembic、现有认证和 `admin_audit_service`；审计记录操作者、动作、公告 ID 与状态变化。普通已读不写管理员审计，不混入支付／激活指标。
- 时间持久化沿用仓库 UTC 约定，DTO 复用 `UTCDateTime` 对外返回带时区的 ISO 时间；后台编辑与预览明确显示北京时间，用户端沿用既有本地化格式。提醒结束无需定时任务，下次读取按服务端时间过滤；客户端用服务端返回的剩余时长安排本次撤掉提醒，不直接相信设备墙上时钟，窗口重新聚焦时校验。
- 登录后加载轻量 summary；打开中心、选择详情、执行已读／关闭及窗口重新获得焦点时按上述校验规则刷新。现有全局 Query 配置为 5 分钟新鲜、禁用 focus／mount 重取，公告必须显式覆盖：打开／选择／窗口回到前台时实际发起对应校验请求，不让仍新鲜的缓存跳过它。summary/list/detail key 全含账号 ID，queryFn 的 AbortSignal 传入现有 API client；账号切换沿用现有取消／移除／重挂载边界。本次选中的摘要保存在 Dashboard 壳层局部状态，不放成跨挂载全局记录。不做定时后台轮询。已下线或不可见的用户详情统一返回 404，成功校验后同步清除同 ID 的 summary/list/detail 缓存。持续停留且不交互的页面不会承诺立即获知新公告或下线。
- 个性化普通用户响应明确设置 `Cache-Control: private, no-store`，不进入公共 CDN；前端也不共享个人状态缓存。切换账号后旧响应不得更新新账号的 query。
- Markdown 明确跳过 raw HTML，不允许脚本协议、内嵌组件或远程图片；安全链接使用受限协议及 `noopener noreferrer`。正文与预览共用此策略，不靠「只有管理员能写」代替防护。现有 `LazyMarkdown` 提供所需扩展点，无需增加依赖。

**最小可发现性信号：** 复用已有 `lib/analytics.ts` 的显式 `trackEvent`，只新增四个行为事件，不新建分析表／报表：

| 事件 | 触发与允许属性 |
| --- | --- |
| `announcement_center_opened` | 用户主动打开中心一次；仅 `entry_surface` |
| `announcement_detail_opened` | 对应详情成功打开一次；公告 ID、类别、提醒强度、入口位置 |
| `announcement_link_clicked` | 用户主动点击正文链接一次；上述公告属性及 `link_destination_kind=internal/external` |
| `announcement_summary_dismissed` | 用户主动收起摘要一次；公告属性与入口位置 |

属性中不发送标题、摘要、正文、完整 URL、稿件或任意用户文本。列表曝光不算详情打开，React 重渲染与请求重试不重复上报；分析未初始化、被禁用或发送失败均不影响公告功能。只观察入口／详情／链接是否被使用，不把它们称为阅读完成、功能采用、激活或付费转化，不接入 `upgrade_funnel_event`。

### 7. 验收与后续实施顺序

1. **后端先锁定规则：** 两张表、迁移、service、普通／管理 API；先写权限、生命周期与逐账号状态回归。
2. **用户端：** 同一个公告中心先接 Dashboard，再接独立写作页；核实不是靠路由跳转打开。
3. **管理端：** 新路由、编辑预览、发布下线、审计文案及中英文翻译键；不新增独立权限系统。
4. **验证后再讨论发布：** 本次不实现、不触发模型／支付、不改云环境。后续实现先本地与合成数据验证，再按单独授权完成 staging；生产遵守既有 release 门禁。

文件责任、依赖、测试矩阵与停止条件见本次本地执行计划 `.omx/plans/2026-10-17-in-app-announcements.md`；本提案与根 DESIGN 仍是产品规则真值，执行计划不另立一套交互规则。

具体通过条件：

- 普通公告仅有未读提示，不自动弹窗；重要摘要在每次 Dashboard 壳层挂载最多选择一条，已读／关闭／到期／下线后不补位，子路由与窗口聚焦不重置。
- 直接进入写作页时，不展开菜单也能区分无未读／普通未读／重要未读；收起 Dashboard 摘要不会清掉重要未读。关闭按钮明确说明「仍保留未读」，列表与读屏反馈符合语义。
- 打开列表不标读，详情响应成功且对应视图首次提交后才标读，不等待 Markdown 懒加载；关闭摘要不标读；刷新、跨设备、账号切换符合上述规则。
- 新账号不被普通历史公告刷未读；有效重要公告仍能被发现；提醒结束移除未读及摘要但保留历史，下线立即退出服务端所有用户读取路径，客户端在成功重新校验后清除缓存。
- 非管理员的管理请求被拒；普通用户猜测 ID 也不能读取草稿、已下线正文或他人的状态。重复写入、客户端时钟偏差、时间边界、并发草稿编辑／发布、更正部分成功均有回归。
- 在有未保存编辑、正在输入、SSE 生成三种情况下打开／关闭公告，项目、文件、草稿、光标和流保持；不发生意外导航、reload 或重复生成请求。
- 桌面、平板、390×844 手机，浅深主题均检查长标题、长正文、安全区与滚动；键盘检查菜单到对话框及返回触发器的实际焦点。
- 验证首次加载、稳定空态、失败重试、后台刷新失败、已读／关闭写入失败与旧账号请求晚返回。Markdown 安全和中英文回退有回归。
- 验证聚焦与重开中心确实请求校验、AbortSignal 生效、个性化缓存 header 与带时区时间；重要发布确认展示仍在线的重要公告，更正待处理标记刷新后仍可见。
- 四个行为事件按真实动作单次触发，分析不可用时不影响产品，payload 不含内容／完整 URL；不新建公告报表，不把点击信号当成激活或营收证明。
- 后续代码检查按改动范围跑 pytest、Vitest、相关浏览器回归、前后端 lint、CSS token／i18n 检查、TypeScript 与构建。不能用本设计的文档检查冒充实现验收。

首版只以「能发布、能发现、能回查、不打断、权限与状态正确」作为完成条件。打开过的记录不命名为阅读完成率；暂不增加公告运营报表。

### 8. 三方评审收敛

| 评审视角 | 采纳的修改 | 保留的取舍 |
| --- | --- | --- |
| 用户产品（designer） | 编辑器重要未读可直接辨别；收起仍未读的文案／状态反馈；更正流程就地引导 | 维护提示不靠强弹窗触达；不增加编辑器横条；新用户不背普通历史未读 |
| 商业化产品（analyst） | 内容章程与适用范围；四个最小行为事件；正文指引链接；重要并存告警 | 公告是可信沟通而非付费墙；不分套餐、不加促销 CTA／报表；埋点不证明转化 |
| 架构师（architect） | 版本化用户 API；显式 Query 校验与取消；DDL／索引／测试清理；CAS/upsert 与同事务审计；PostgreSQL 并发门禁 | 两张表、一个领域 service、Portal 与既有渲染／分析工具足够；不建新平台 |

有意未采纳「重要公告并存时后端阻塞并要求 override」：它能更强地抑制过度发布，但会新增确认协议和竞态处理，且更正期间本就允许两条并存。首版只在最终发布确认中重读并列出现有重要公告、提示后续触达效果并要求用途确认；这是运营摩擦，不宣称数据库单例或硬频控。

## Alternatives considered

- **首次登录自动弹公告。** 优点是曝光直接，适合确实需要确认的事项；但容易打断输入、抢焦点，且「看到弹窗」并不等于同意。首版不用，强制确认作为独立产品需求处理。
- **统一做铃铛消息中心。** 优点是未来可放任务完成、私信、支付等通知；但当前没有这些统一投递需求，也没有可复用通知实体。先做明确命名的「公告」，不提前建设通用通知平台。
- **增加公告列表和详情路由。** 优点是链接可分享、浏览器历史自然；但现有写作页是独立路由，简单跳转会卸载编辑器与聊天。首版用同一个对话框，分享链接和 overlay route 留待实际需求。
- **Markdown 文件随版本发布。** 优点是无数据库功能、内容可 review；但运营发维护通知也要走代码发布，且已读和关闭仍需独立账号状态。选择最小后台管理。
- **用 localStorage 记已读。** 优点是实现少；但不跨设备、易串账号，清缓存后重现。只允许本次会话临时降级，不作为同步事实来源。
- **已发布内容随时编辑，再给每版分别记已读。** 优点是错字修订方便，也能强提醒实质变更；但引入版本、二次提醒、旧版回查和关闭失效规则。首版选择发布固定、更正新发，代价是修订多一步。
- **首版就做定时发布与分群。** 优点是维护预告和套餐通知更精准；但带来时区、订阅变化与资格规则。先做立即发布、统一受众和提醒到期，不引入调度系统。

## Consequences

收益：运营无需跟随代码发布即可通知用户；历史可查、账号间隔离、跨设备同步；现有写作与主题体系不受干扰，数据和组件边界足够小。

成本与限制：新增数据库迁移、API、管理页面及两处用户入口；公开后更正需要另发；英文正文需要人工维护；公告不是实时投递渠道，用户一直留在写作页时可能延后发现通知。若将来需要紧急维护、套餐定向或强制确认，应分别扩展规则，而不是默认把公告升级成阻断流程。
