# 美元收款：接入海外代收平台（Merchant of Record）的路线图

Status: proposed（阶段 1 已实现，只改英文页面；阶段 2 起尚未开始）

## Problem

ZenStory 目前唯一的收款渠道是 Zpay 代收支付宝，只收人民币（Pro ¥49/月、¥399/年，见 `implemented/feature/2026-10-05-zpay-alipay-checkout.md`）。应用已有英文界面，但海外用户既没有支付宝，也看不到美元价格，想付费也付不了。

选择收款方案时，主要受这几条约束：能接受中国大陆的卖家；不需要自己在各国登记缴税；结算款能回到国内；开发上能复用现有的「收款事实先落库、claim 后开通」链路。

现有代码里有几处只按 Zpay 和人民币写，接第二个渠道前必须先改：

- `payment_order` 没有 `provider` 和 `currency` 字段，`amount_cents` 默认就是人民币分；`trade_no` 是全表唯一。
- `services/usage/admin_growth_service.py` 有两处 `sum(PaymentOrder.amount_cents)` 统计收入，一旦有美元订单，美元和人民币会被直接加在一起。
- `ZpayService.create_order` 只接受 `payment_method == "alipay"`。前端 `PaymentCheckoutModal` 只认 Zpay 的表单 POST 地址。价格展示用的是 `formatYuan`。
- `subscription_plan` 只有一组价格（`price_monthly_cents / price_yearly_cents`）。旁边的 `stripe_price_id_*` 和 `user_subscription.stripe_*` 是早期预留的字段，从未使用。
- 条款第 8 节写的是「付款原则上不予退款」。代收平台审核要求有明确的退款政策，Paddle 对生成式 AI 卖家要求 14–90 天的退款期，并且不允许写「概不退款」。

## Proposal

**选型：用代收平台（MoR），不直接接 Stripe。首选 Creem，Paddle 作为备选。两家同时提交申请，先接通过审核的那一家；如果都通过，用 Creem。** 代收平台以自己的名义向买家收款，各国的 VAT 和销售税由平台申报缴纳，ZenStory 只收结算款。

截至 2026-10-21 的官方资料：

- Creem 明确接受个人或公司卖家，支持中国大陆收款，费率每笔 3.9% + $0.40，提现到中国大陆本地银行的手续费为 7 美元与提现额 1% 中的较高者。webhook 以 `creem-signature` 头做 HMAC-SHA256 签名，失败后按 30 秒、1 分钟、5 分钟、1 小时重试。
- Paddle 只排除受制裁国家，中国大陆卖家不在排除名单内；费率每笔 5% + $0.50。审核要求：定价页和条款不登录也能访问，条款写明经营者名称，退款政策满足上面的要求。

### 阶段 0：开户、定价与政策（经营者办理，和阶段 1 并行，约 1–3 周）

1. **定价。** 已定为 $9.99/月、$79/年，年月比和人民币价相近。$9.99 一单的手续费在 Creem 约 $0.79，在 Paddle 约 $1.00。
2. **美元订单的退款政策。** 已定为 14 天内无理由退款，人民币订单的政策保持不变。
3. **提交审核。** 同时申请 Creem 和 Paddle，提交 `app.zenstory.ai/pricing` 和条款页。Creem 的审核规则如下（截至 2026-10-21）：
   - 店铺在测试模式下就能创建，测试 API key 可以直接用来开发；商户信息填完后会停在 Review & submit，不需要马上提交。
   - 通过审核之后才能收真实款项。审核清单要求产品已经可以上线，定价、服务条款、隐私政策和客服邮箱都要在网站上公开可见；「产品还没上线」是常见的被要求修改原因。
   - 文档写的是审核员「可能」做一次有限的测试购买，会用一次性 100% 折扣码，所以后台可能出现零元订单。文档没有说明在开通真实收款之前这次购买怎么进行，也没有要求网站在审核时已经接入 Creem 结账。我们的推测是：零元订单不需要真的扣卡，审核员可以先走通结账、看付款后能拿到什么。这一点提交前要找 Creem 客服确认。
   - 「Generative AI」类目属于受限类目，需要补充更严格的尽调材料：此前用过的支付渠道（Zpay 支付宝）、退款率和拒付率、更换渠道的原因，以及过往的交易记录。
   - 结果分「要求修改」和「拒绝」两种。「要求修改」改完后可以申请复审；「拒绝」对这个店铺是最终结论，确认框写明 3 个月内不会再审。
4. **结算账户与税务。** 由经营者在仓库之外确定，不写进代码库。

### 阶段 1：审核所需的公开页面（开发，约 1–2 天，最先做）

已实现的内容：

- `/pricing` 不登录即可访问。英文界面的 Pro 显示美元价格（`apps/web/src/config/usdPricing.ts`，年付优惠按美元价格计算）；中文界面仍显示目录里的人民币价格，输出与改动前完全一致。美元价格要等阶段 2 才进套餐目录。英文定价页底部的说明写明美元卡付即将开放、支付宝人民币现在可用；点 Pro 按钮仍打开现有的支付宝结账。
- 英文服务条款区分了支付宝人民币订单（一次性付款、不自动续费，退款规则同现状）和银行卡美元订单（代收平台是 Merchant of Record，负责收款、计税和开票；14 天内可全额退款）。英文隐私政策补上了支付服务商，并说明我们拿不到完整卡号。
- 中文文案一字未改：中文界面只卖人民币，所以中文条款不涉及美元订单。i18n 检查要求中英文词条一一对应，所以只改已有词条的英文内容，不新增词条。
- 这一阶段只改页面，不改支付代码，可以单独发布。阶段 1 完成后就可以提交 Paddle 的域名审核。Creem 至少也要等阶段 1 完成后再提交；要不要等到阶段 2 也完成，以 Creem 客服的答复为准。

### 阶段 2：美元收款主链路（开发，约 1 周，接最先过审的平台）

首版**只做一次性的 30 天和 365 天开通**，与现在的 Zpay 订单一样，不做自动续费，这样整条开通链路都能复用。

后端：

- **迁移。** `payment_order` 增加 `provider`（`zpay | creem | …`）和 `currency`（`CNY | USD`），旧数据回填为 `zpay / CNY`；`trade_no` 的唯一约束改为 `(provider, trade_no)`。`subscription_plan` 增加 `price_monthly_usd_cents / price_yearly_usd_cents`，后台套餐编辑器同步支持。未使用的 `stripe_*` 字段不动。
- **抽出与渠道无关的结算逻辑。** 把 `ZpayService._settle_paid_order` 的两步（条件 UPDATE 写入 paid 并立即 commit；claim `fulfillment_status` 后开通）移到 `services/subscription/payment_fulfillment.py`。Zpay 和新渠道都调用它，`SubscriptionHistory.event_metadata.source` 取 provider。幂等规则和并发语义保持不变，原有回归测试必须继续通过。
- **新渠道适配。** 建单时调用平台的结账接口，传入一次性产品 ID（按月或年）、`out_trade_no`（作为幂等 ID）、订单 ID（放在 metadata 里）和现有返回页地址，平台返回跳转地址。webhook 路由为 `POST /api/v1/payments/<provider>/webhook`：用原始请求体验签，按事件 ID 幂等处理，并核对产品、金额、币种和 `out_trade_no`。**与 Zpay 一样，开通只认 webhook 和我们主动发起的查单，返回页 URL 上的参数一律不参与判断。**
- **查单补偿。** 用户侧和后台的 `sync` 接口接到平台的查单 API。Creem 的 webhook 重试窗口只有约 1 小时，比 Zpay 的约 3 小时还短，所以返回页超时后主动查单这一步更重要。
- **退款与拒付**（Zpay 那份记录里的已知缺口，卡支付必须补上）。退款 webhook 把订单记为 `refunded`，按这笔订单的天数扣回会员期（不早于当前时间），并写入 SubscriptionHistory。拒付记为 `disputed`，并计入后台的 `needs_attention`。
- **后台统计按币种拆分。** 收入和付费转化分别统计 CNY 和 USD，绝不相加；`paid_conversions` 的口径要包含新的 source。**这一项必须在第一笔美元订单之前完成。**
- **配置。** `<PROVIDER>_ENABLED / _API_KEY / _WEBHOOK_SECRET / _PRODUCT_ID_PRO_MONTH / _PRODUCT_ID_PRO_YEAR`，外加测试模式开关。沿用 `PaymentSettings.configuration_problems()` 作为唯一的配置规则，`scripts/release_preflight_check.py` 也调用它。`/payments/options` 返回每个付款方式对应的币种。

前端：

- `PaymentCheckoutModal`：在现有的表单 POST 之外，增加跳转式结账，跳转目标只允许白名单主机。默认付款方式跟随界面语言：中文界面为支付宝人民币，英文界面为银行卡美元，两者都可以手动切换。
- `BillingPage` 和 `PricingPage`：价格按币种格式化，替换写死的 `formatYuan`。
- `PaymentReturnPage` 不区分渠道。漏斗事件（`checkout_started` 等）加上 `provider` 和 `currency`。

验证：

- 本地 mock 平台。staging 使用平台的测试模式，不产生真实扣款，符合 staging 不开真实支付的约定。回归覆盖这些情况：验签失败、重复事件、金额或币种不符、退款扣回、webhook 丢失后由查单补开通、两个渠道的订单互不干扰。
- 生产环境用最小金额完成一笔真实付款，再走一次退款。

### 阶段 3：上线观察（2–4 周）

- 英文界面默认显示美元付款，中文界面保留切换入口。
- 观察指标：英文界面的 `checkout_started` 到美元付费的转化、退款率、拒付次数。
- 退出标准：4 周内美元付费少于 5 单，就维持现状，不进入阶段 4，也不追加投入。

### 阶段 4（有条件）：自动续费

阶段 3 有稳定的美元付费之后再做：订阅型产品和 `subscription.*` webhook、`cancel_at_period_end`（字段已存在）、平台自带的客户自助管理入口、扣款失败的宽限期。老的一次性订单剩余天数保留。备选平台只有在首选平台出问题时才接入，复用阶段 2 抽出的结算层。

## Alternatives considered

- **直接接 Stripe。** 最强理由：费率最低、API 和文档最好，模型里还预留了 `stripe_*` 字段。否决原因：Stripe 不向中国大陆主体开放，需要香港公司或通过 Atlas 注册美国公司（注册费、年费、美国申报）；而且作为直接卖家，各国 VAT 和销售税都要自己登记申报。以现在的体量，这些固定成本远超费率上省下的钱。美元收入做大以后可以再评估。
- **首选 Paddle。** 最强理由：最老牌，合规和风控成熟，资金放在大公司更安心。没有选它做首选、只作备选，原因是：对生成式 AI 卖家审核严格，有被拒的案例；费率更高；结算主要走电汇到美元账户，需要万里汇等账户承接，而万里汇要营业执照；官方资料没写清楚是否接受个人卖家。
- **Lemon Squeezy。** 最强理由：开发者体验好，同样是代收平台。否决原因：2024 年被 Stripe 收购后产品方向不明确，官方文档也没写清楚中国大陆的结算路径。
- **用万里汇作为收款方。** 最强理由：蚂蚁旗下，换汇和提现到国内都方便。否决原因：它是跨境收款账户，不是面向买家的收单产品。在本方案里它只是阶段 0 可选的结算账户。
- **首版就做自动续费。** 最强理由：海外 SaaS 默认就是订阅制，续费率更高。否决原因：要额外处理续费、取消、扣款失败、宽限期和客户自助管理入口。首版先复用现有的一次性开通链路，验证有需求后再做（阶段 4）。
- **同时接两家平台。** 最强理由：一家出问题时收款不中断。否决原因：开发、对账和配置都要翻倍。阶段 2 抽出的结算层已经让第二家随时可接。

## Consequences

- 收益：海外用户可以用银行卡付美元；各国的税由代收平台承担；开通链路沿用已经验证过的幂等结算，没有另起一套；抽出的结算层也为以后接入支付宝官方商户或 Stripe 铺好了路。
- 代价：每单手续费约 7–10%，另有提现费。Creem 是年轻公司，资金留在平台上有对手方风险，需要定期提现。卡支付会带来退款和拒付。条款要新增对美元订单的退款承诺。后台统计要分币种。
- 代价：英文和中文条款不再逐句对应，以后改条款时要分别核对两种语言。
