# 站内公告：第二轮交互打磨

Status: proposed — 设计与独立原型，未实现产品功能

最新范围：用户随后明确希望更轻量，[轻量公告横幅提案](../../implemented/feature/2026-10-17-lightweight-announcement-banner.md)已替代本稿。抽屉原型保留为探索记录，不作为首版实施要求。

## Problem

用户查看第一轮效果图后明确反馈「交互不自然，UIUX 不够好」。这份反馈优先于第一轮评审结论：初稿虽定义了权限和状态，但把入口藏在次级菜单、在菜单旁悬挂「重要」、用居中对话框承载连续阅读，又用关闭按钮解释「收起仍未读」，形成了不必要的寻找与理解成本。后台并排展示两个界面的效果图，也没有证明真实操作路径。

本稿修订[第一轮提案](2026-10-17-in-app-announcements.md)的入口、阅读容器、摘要操作及后台编辑表现；该提案的数据、权限、时间、并发、发布／下线、语言回退和商业边界继续有效。本文是交互部分的新真值，不把旧稿改写成从未提出过的相反决定。

## Proposal

### 1. 一条阅读路径，一个容器

**独立公告入口 → 列表 → 同容器正文 → 返回列表或关闭回原页。**

- Dashboard 桌面侧栏在主导航结束、账号区之前设置独立工具位，不沉到用户菜单内；平板保留清楚的图标入口。手机在顶栏显示公告图标。
- 写作页在现有 Header「更多」前放独立 Megaphone 按钮，桌面和手机一致。触控区域 44px，不新增一行工具栏，也不挤压／卸载下方编辑器。
- 入口无未读时无徽记；普通未读为小点；重要未读为入口本体上的 `!` 小徽记。三种状态都有不同的可访问名称，不再把「重要」两个字悬挂在另一个菜单按钮旁，不显示数字。
- 桌面统一打开右侧覆盖式抽屉，阅读宽度约 440–480px。Dashboard 和编辑器使用同一种 surface，不再出现一处居中 Modal、一处侧栏的两套心智。抽屉覆盖而不压缩原面板。
- 手机统一为视口内全屏层，处理安全区；不跳 URL、不重挂载写作页。320px 与 390px 均验证图标和项目名空间，不能把 44px 按钮缩小来凑数。只有真实界面在 320px 测得拥挤，才考虑将入口降级到带徽记的菜单。
- 列表首屏直接是公告，没有额外介绍页；行内用类别、标题、短摘要、日期，未读用小点与短文字。只有重要程度有克制的琥珀色标签，不把每个属性都做成彩色徽章。
- 点一行在同一抽屉原位切换详情。详情顶部「← 公告」只回列表并恢复其滚动；右上关闭或 Escape 在任意层级都退出公告。没有第二层对话框和底部「知道了」主按钮。
- 用户主动打开才移动焦点。关闭回到仍挂载的公告触发器；原正文 DOM、输入、选区、聊天和 SSE 生命周期保持。手机浏览器系统返回的历史集成不在本轮偷偷增加，实施时沿既有导航契约验证，不能让它无预警离开作品。

### 2. 摘要操作本身说清含义

- Dashboard 仍只显示一条重要摘要，写作页不加横条；普通公告不升级为摘要。
- 摘要两个文字动作是「查看影响／查看」和「稍后看」。前者直接在同一抽屉打开对应详情；后者只收起本条摘要，入口 `!` 与列表未读保留，不需要用 Toast 解释一个反直觉的 `×`。
- 「稍后看」不是定时重推：本条收起按账号保存，后续可从仍未读的公告入口主动查阅。不引入 snooze 时间、调度任务或新投递状态。
- 每 Dashboard 壳层挂载只选择一条候选、读／关／到期／下线只撤不补位的规则不变。详情「已读」仍仅代表成功打开，不证明阅读完成。

### 3. 后台是完整流程，不是拼图

- 列表与编辑一次只显示一个完整管理页面；列表只保留首版状态筛选，不扩展搜索／类型筛选或统计卡。
- 新建与创建更正进入同一个编辑器：顶部标题、草稿状态、返回列表；元数据在上，正文在下；桌面右侧是用户看到的阅读预览，窄屏改为编辑／预览切换，不堆两套表单。
- 中英文用同一表单的语言标签切换，沿用英文可缺省回落中文的规则。未完成草稿可保存。
- 一个主操作「预览并发布」，次操作「保存草稿」。发布前确认目标、影响、期限与仍在线的重要公告；编辑动作不直接发布。
- 创建更正带来源，发布结果就地展示「原公告仍在线」和下线／重试。保留部分成功的真实状态，不把两步包装成一次替换。
- 发布和保存都只在原型内模拟；原型常驻标明不连接真实服务，不展示假运营成绩。

### 4. 视觉约束与可验证原型

沿用现有真实品牌标记、浅深主题角色、细边框、轻量控件与用户强调色，不加入小说封面、装饰插画或新的营销皮肤。公告是阅读工具，内容比容器与徽章更突出。第一轮生成图只作为探索记录，不作为精确 UI 基线。

独立可点击原型位于 `.omx/design/announcements/v2/`：用户端 `index.html`、后台 `admin.html`，均不改 `apps/`、无真实 API／分析／支付／模型请求。预览是代码原生 HTML/CSS 的浏览器截图，不依赖生成图猜测控件行为。

原型验证范围：

- 320／390／1440px 无整页横向溢出，手机公告按钮达 44px，项目名仍有可用空间。
- 稍后看不标读；打开列表不标读；进入详情、返回列表、关闭路径通顺，关闭焦点回到入口。
- 抽屉打开前后写作面板尺寸不变，示例正文节点、输入、选区与 URL 保留。
- 前后台切换、发布确认、更正下线失败与重试均可操作，且无外部网络请求。

这些检查仅证明独立原型，不证明真实产品的 SSE、保存、权限、数据库或 staging 已验收。后续实施仍需原开发计划中的完整门禁。

## Alternatives considered

- **继续微调居中 Modal 的配色和圆角。** 优点是改动最少，现有焦点原语可直接复用；但没有解决连续阅读过重、入口弱和返回层级不清，故先改交互结构。
- **公告继续藏在更多菜单。** 优点是不新增 Header 按钮，窄屏更稳；但重要状态与公告入口被拆开。改为独立按钮，只有真实 320px 布局证明无法容纳时才降级。
- **把公告做成常驻右侧第四栏。** 优点是无需遮挡原界面；但会挤压编辑器／聊天与手机切换。选择覆盖式抽屉，原面板不重排。
- **摘要直接取消收起功能。** 优点是状态最少，不存在「关了怎么还未读」；但有效期长的公告会持续占位。保留语义明确的「稍后看」与独立打开状态。
- **点击后跳公告列表路由。** 优点是历史导航和分享简单；但现有独立写作路由会卸载工作区。首版继续局部容器，不增加路由与分享需求。

## Consequences

收益：发现、浏览、返回形成一条可演示路径；重要状态直接附在入口；桌面保留写作上下文，手机只有一个全屏层；后台能按一次完整操作检查，而不靠拼图推测。

成本：实现时需给现有 overlay/focus 原语增加合适的侧边布局或在公告容器局部复用其契约，不能只把居中对话框改个宽度；Header 增加按钮后必须做真实 320px 适配。底层服务、发布生命周期、商业边界与本轮无功能实现的范围不变。
